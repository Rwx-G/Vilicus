# Story 3.9: Module availability states and fault isolation

As a project maintainer,
I want the Core to track one availability state per module file and to contain every module fault,
So that callers and the event bus never guess whether a file can serve, and a panicking module never takes the Core down.

**Acceptance Criteria:**

**AC1 (AD-54)**
**Given** a module file
**When** any caller asks for it
**Then** the Core reports one of `locked`, `opening`, `re-keying`, `migrating`, `ready`, `failed migration`, `faulted`, `deactivated`, `newer than code`
**And** every non-ready state answers typed API calls with `module_unavailable` and the retry class of the AD-54 table (`retryable` for the first four, `not_retryable` for the rest).

**AC2 (AD-54, FR-23)**
**Given** a consumer whose file is not ready
**When** an event is due to it
**Then** the event stays in the source outbox and does not count as a failed delivery.

**AC3 (AD-54, FR-11)**
**Given** a partition becoming available
**When** its keys are derived
**Then** the Core reports it usable at once and moves each file through re-key, migration and outbox delivery in the background, in that order.

**AC4 (AD-9)**
**Given** a handler, undo handler or event consumer
**When** it panics on the file's writer thread
**Then** the Core catches it with `catch_unwind`, rolls back the transaction, marks the module `faulted` for that partition and returns a typed instance admin alert
**And** release builds use `panic = "unwind"`, and the panic never unwinds into the Core.

**AC5 (AD-9)**
**Given** a handler call that exceeds its time budget
**When** the budget expires
**Then** the module is marked `faulted` for that partition and receives no further calls there.

**AC6 (AD-9)**
**Given** a module faulted in one partition
**When** other modules and partitions are called
**Then** they keep serving normally (test with a deliberately panicking handler).

**Decisions and why** (drafted decision and document texts under Open points)
- *Where the states live* (AC1): in the Core's memory, one `ModuleStates` shared by its threads, keyed by module and partition, every caller reading it; a file the Core never heard of is `locked`, so nothing unknown serves. A file's state is `deactivated` while its module is off for the partition, else `faulted` once it faulted, else the stage its bring-up reached; a deactivation shows over a fault because it is the household's choice and the one an adult can act on. Only the failed migration is kept across starts (below): the others are re-derived at each unlock, or, for a deactivation, come from AD-47's activation setting, which no story stores yet.
- *The answer to a typed call* (AC1): `ModuleUnavailable`, a `ClientFacingError` of the Core whose code is `module_unavailable` and whose retry class is the state's, `retryable` for the four states on the way to serving and `not_retryable` for the four that wait for something else; the module, the partition and the state stay on the server side. The error enum of the client boundary in `vilicus-proto` comes with the pipeline (Story 10.3), which maps this one.
- *How long a fault lasts*: as long as the Core process. Locking and unlocking the partition does not clear it, so a module that faulted gets no further call in that partition, as AD-9 says, and a member cannot clear a poisoned handler by relocking; a Core restart, a host act of root, does, and is the recovery until an explicit one exists. Gives up: a module faulted by a transient overrun (a host under load) stays down until the restart.
- *A failed migration held across starts* (Story 3.7's open point): the runner writes a mark beside the file, never in it, naming the identity of the code it failed under: the SHA-256 of the Core's version, the frozen hashes of the Core track and the module's declaration, its migrations included. While a run's code is that code, the file is `StillFailed`, with no copy, no migration and no second alert; a forward release changes the code, by its version (anti-rollback, Story 13.3, makes each release's version higher) or by the declaration, so its first run tries again; a mark of another code, a malformed mark and a mark beside a file with nothing to migrate are cleared. Only a failure the same code would meet again is held: a statement refused or failing on the file's content, a changed migration, a copy outside its declaration, an FTS5 index that fails its check. A failure of the host's state (`is_environmental`: the disk, a lock, a copy raced, cold copies no verified backup covers, a key or an epoch) is not held, so freeing space or a verified backup is enough for the next unlock. A mark that cannot be written leaves the failure to be met again, harmless since a migration runs on a copy. The mark holds no secret: an identity, a track and a version. Only a migration that failed on its copy is marked (review item 6): a failure found before any copy (a changed migration, a file's record of frozen hashes, a file that does not open) is met again before the mark is read, so a mark would hold nothing. The identity hashes the declaration's `Debug` text and the Core crate's version: a change of either (a compiler that prints `Debug` differently, a release) changes the identity and tries the file again, the safe direction; it cannot hold a file a release fixed. A denied file system permission (`SQLITE_PERM`) is a failure of the host's state, not held (review item 7).
- *The writer held across the migration run* (D149, Story 3.7's open point): no writer thread exists before Story 5.1, so the availability states are the lock. A file is put to `re-keying` or `migrating` only when no call of module code is registered on it and no re-key or migration holds its writer already (`StageRefused::CallsInFlight`, `StageRefused::WriterHeld`), and no call starts on a file that is not `ready`; the bring-up opens no handle of a file until its migration ran, and the bus delivers only to ready files. *Unlock generations* (review item 2): each unlock and each lock of a partition starts a new `Generation`; every stage change of a bring-up carries the generation of its unlock, and one of an earlier generation is refused (`StageRefused::Stale`), except that it still releases the writer its own bring-up took, so a bring-up still running when its partition is locked never moves a file of the later unlock, nor leaves a locked partition's file `ready`, and a second bring-up never migrates a file the first still migrates. A bring-up that finds its partition locked stops: it opens nothing more, closes what it opened and delivers nothing (`FileOutcome::PartitionLocked`). A file whose writer is busy, or whose re-key failed, is put `locked` with `FileNotServed` (review item 7): it answers `retryable`, the next unlock tries it again, and it no longer stays `opening` or `re-keying` for the whole unlock.
- *The time budget* (AC5): a synchronous handler cannot be interrupted, so the budget is a deadline, `HANDLER_TIME_BUDGET` after the module's code starts, on the one monotonic clock the availability states own (`ModuleStates::with_clock`), which the boundary and `expire_overdue` both read (review item 5). The window is the module's code only (review item 3): the Core's work before it (the write lock, the deduplication, the call's start time) and after it (the `_consumed` row, the commit) is not counted, the deadline being cleared as soon as the code returns, so a slow commit never faults a module; the writes the code makes through the record port inside the window are counted, as part of its work, each bounded by the busy timeout of its file (D136), and pausing the budget across them would let a module issue writes without bound. A call whose code returns after it is rolled back and faults its module; `ModuleStates::expire_overdue(now)`, which the Core's supervisor calls on a timer, faults at once the module of a call still running past it, so no further call reaches the module meanwhile, and the call, when it returns, is rolled back without a second alert. A handler that never returns keeps its writer thread and its file; the other threads, files and partitions go on. 5 seconds is far above the 100 ms p99 of one action through the pipeline (D116, D136) and above any wait a writer meets on its own file (a backup pause, D136), so only a handler that loops or blocks reaches it. SQLite's progress handler, which could interrupt a long statement, is not used: the Core's own statements are bounded, and a handler's loop in Rust would not be interrupted by it anyway.
- *The boundary* (AC4): `catch_unwind` around the module's code only, inside `run_call`'s transaction, so a panic rolls the call back (the transaction guard of Story 3.5) and never unwinds into the Core. The panic's payload is the module's too: it is dropped with the thread marked and inside `catch_unwind`, each payload a panicking drop yields dropped the same way, at most 8 times before the last is leaked (review item 1). A panic of the Core in the record port that the module's code catches and goes on from is still the Core's: the boundary unwinds when the code returns, the call rolled back and the module not faulted (review item 4). The record port the code writes through is the Core's: each of its methods runs with the thread unmarked and notes a panic there as the Core's, which the boundary lets unwind on, the module not faulted. The thread mark (`in_module_code`) is what D131's panic hook reads in the Core process to abort on the Core's panics only; the hook itself comes with the key pool (Stories 4.2, 5.1). `panic = "unwind"` is the release profile's, and `vilicus-core` fails to compile under `panic = "abort"`, so no build can ship a Core that a module's panic aborts.
- *The handler table* (Stories 3.3 and 3.8): each module's code is a `const ModuleCode` of `fn` pointers bound by name to its declaration, checked by `const fn` in the module's build (`assert_bound`) and again when the binary builds its `Handlers` from its registry, so a tool, an undo handler or a consumer without a function stops the build. A handler receives what it acts on and the record port, nothing else (no handle, key or thread). A tool receives the arguments the pipeline validated (Story 10.3), an undo handler the tool, the call id and the outbound effects that call requested, which the module cannot read from the Core tables; outputs of reads wait for the module read handle (Story 10.3). The bus keeps its `ConsumerCode` port, which `Handlers` implements.
- *Delivery* (AC2, D150): a consumer is ready only when the states say `ready` and its handle is open and at the code's versions; otherwise its events stay, and the outcome carries the state. Consumers run inside the boundary: a panic or an overrun counts one failed attempt (AD-29 counts a panic of the consumer's code) and faults the consumer's module, with an alert, after which its events wait like any not-ready consumer's, without further attempts. An event older than `OUTBOX_RETENTION` (strictly), still pending for a consumer in a lasting state, is moved to that consumer's dead letters without an attempt, with `EventExpired`, and holds back none of the consumer's later events; behind a state on its way to serving it stays, however old. An event whose row does not decode has no creation time to age by and stays behind a lasting consumer.
- *The bring-up* (AC3, FR-11): `unlock_partition` puts every file `opening` at once, which is when unlock completes; `bring_up` then runs, in the Core's background, phase by phase across the partition's files: re-key what must be (a `Rekey` port; nothing in V0.1, `NothingToRekey`), migrate each file in a run of its own (so the free space is read again before each file, and a current file never waits on another's space), open and check each, and only then deliver each ready file's outbox, so the consumers are ready before their events. Each file's order is re-key, migration, delivery; no inbox is ingested in V0.1 (AD-37 starts with the home milestone), and household key wraps, last in AD-54, are the unlock path's. A file that cannot serve stops in its state with its alert: `failed migration` for a failed or held migration, a migration that did not start (`NoSpaceToMigrate`, `FileNotServed`) or a file that does not open, `newer than code`, `locked` for a failed re-key or a busy writer. A registered module whose file is not given is reported (`FileOutcome::NotGiven`) and `locked` with `FileNotServed`; two files of one module are refused before any file is touched (`BringUpError::DuplicateFile`).
- *A snapshot and a fresher read* (Story 3.8's review item 9): an implicit input the call also read afresh (`Call::read`) counts as the two combined: the most restrictive labels, the union of the data types, the free text of both, and the author that leaves the record trusted for fewer readers; two different authors cannot both be the reader, so such a record counts `external`, as a `trusted` record of another member does for a derivation (AD-7). It applies whether the module names the record or not.

**Deviations**
- *AC1, "when any caller asks for it"*: `ModuleStates::state`, the only place a state is read; `vilicus status` and `vilicus upgrade check`, which report it to the operator, are Stories 11.1 and 13.4. *"typed API calls"*: the calls of module code through the boundary (`Handlers::call_tool`, `call_undo`, the consumers) and the gate `ModuleStates::check` for the cross-module typed API, which no story builds yet; the client sees `module_unavailable` once the pipeline maps the Core's error (Story 10.3).
- *AC3, "in the background"*: `bring_up` is a synchronous function the Core runs on its blocking pool, which Story 5.1 builds; the test calls it after `unlock_partition` returned, which is what "usable at once" is here. *"re-key"*: through the `Rekey` port; no file is re-keyed in V0.1 (rotations come with recovery and sub-keys), and the test re-keys through a probe.
- *AC4, "returns a typed instance admin alert"*: returned (`HandlerError::Faulted`, `DeliveryReport::alerts`); sending it is the alert path's (Epic 8). *"the panic never unwinds into the Core"*: a module's panic does not; a panic of the Core inside the record port unwinds on by design, to D131's hook, which aborts in the Core process and is not built yet.
- *AC5, "when the budget expires"*: the supervisor's call to `expire_overdue`; its timer is Story 5.1's. The budget covers the module's code, its record-port writes included, not the Core's work around it (Decisions). A handler that never returns cannot be stopped: its module is faulted and gets no further call, its thread stays.
- *AC6*: shown on unit tests with deliberately panicking tool, undo and consumer handlers and two partitions; AD-9's release-gate test, that a panicking reference handler leaves unlocked members unlocked, needs the reference module and the unlock path (Stories 3.10 and 14.1).

- *Story 5.1* (the Core process): one writer thread per open file running `Boundary::run`; the supervisor's timer calling `ModuleStates::expire_overdue`; `bring_up` on the blocking pool after each unlock; the lock path waiting for, or abandoning, the calls still running before it drops a partition's keys (a call that outlives a lock keeps the next bring-up from migrating its file, `FileOutcome::CallsInFlight`); D131's panic hook reading `in_module_code`.
- *A fault's recovery*: only a Core restart clears it. An H action or a root CLI command to clear a module's fault in one partition, audited, would let an adult resume a module without restarting the house; it needs a decision.
- *Deactivation*: `ModuleStates::deactivate` exists for AD-47; the activation setting and its storage (Core metadata) are the activatable modules' story.
- *Re-key*: the `Rekey` port has no implementation but `NothingToRekey`; recovery's DEK rotation (Story 9.14) and sub-key revocation implement it.
- *Epic 10*: the pipeline validates a tool's arguments before `Handlers::call_tool`, maps `ModuleUnavailable` into the client error enum of `vilicus-proto`, and issues no token naming a tool of a module that is not ready (AD-54), reading `ModuleStates::check`; a tool's result and a module's reads come with the module read handle.
- *Operators* (Stories 11.1, 13.4): `vilicus status` reports each file's state, and `vilicus upgrade check` reads the marks of failed migrations (`maintenance::failed_migration_mark`), the alert of a held failure being given once.
- *Backups*: the mark is a clear file beside the module file; whether a backup carries it, so a restore under the same release keeps the file held, or leaves it out, so a restore tries again, is Story 12.2's choice; either is safe, a migration running on a copy.
- *A changed migration*: a migration edited after it was frozen fails before the mark is read (the frozen check comes first, Story 3.7), so it is alerted at each run until the release is fixed.
- *`migrate_file` and `migrate_files`*: the bring-up migrates one file per run; `migrate_files`, with its single space check for the run, stays for callers that migrate many files at once (the acknowledged upgrade of `core.db` and `wrappers.db`, Story 13.2).
