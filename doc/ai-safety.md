# AI safety principles

Status: design phase, no code yet. Revision 2. Structure and processes are in [architecture.md](architecture.md) (sections 9 to 11) and the [architecture spine](architecture-spine.md); every action and its tier is in [capability-matrix.md](capability-matrix.md); requirements are in [prd.md](prd.md); this document holds the rules and the tests that enforce them. Revision 2 aligns it with decisions D34 to D61, its 2026-10-16 update with D62 to D68, the revalidation of the same day with D69 to D86, later updates with D87 to D96 and D97 to D100, and the second revalidation of the same day with D101 to D115 ([decisions.md](decisions.md)).

Prompt injection is not solved. These principles assume an injection will eventually succeed and aim to bound what it can do. The question is never "will the model be fooled", it is "what is the worst thing a fooled model can do here".

## 1. Principles

### P1. The model is an untrusted component; the Core decides

Treat model output like user input. The model proposes typed actions; deterministic code in the Core validates, authorizes and executes them. The model never holds keys, credentials, or ambient authority. The current date and time zone are injected by the Core; the model never infers them.

### P2. Never combine the lethal trio in one context

A context must not simultaneously have access to private data, exposure to untrusted content, and the ability to communicate or act externally. Roles:

- **Quarantined reader.** Reads untrusted content. No write, send or pay tool, no network access, no private data beyond the object it reads. It returns only **closed enums, bounded numbers and opaque identifiers that the Core resolves**. It never returns a free string that reaches the planner. Output is validated by the Core against a schema and marked `external`.
- **Planner.** Has the tools. Never sees raw `external` text: it works on reader output and on trusted data. Data written by another member in the household partition, structured or free text, reaches it as quoted data within each field's declared length and with its taint (see D37); its free text taints the session, its structured fields (values from a set fixed at build time, see D104) do not (see D70). A member-approved assistant draft, stored `external` (see D99), reaches it as quoted data within its maximum length and taints the session (see D104).
- **Drafter** (optional). Reads untrusted text in order to write a reply. Has no send tool. Its token reads the object being answered and the structured records the member selects for the reply; it has no partition-wide read tool. Before a draft is shown, the Core runs the outbound content check (P5) on it and marks matching fragments. Its output is a free-text draft object marked `external`, stored locally and shown to the human, never forwarded as text to the planner. Sending is tier 2 with the whole text displayed.
- **Researcher** (after V0.1). Reads the open web to answer one question (see D63). It holds the untrusted content and the network, so it is denied the third element: private data. It receives only the member's question as typed, never partition data, memory or conversation context, and the screen says the question leaves the instance. Its first query is built by a Core template stage; afterwards it may only ask the Core to follow a link that appears verbatim in a page already fetched for the same task. It makes no request itself: every request is made by the **trusted fetcher**, which runs no model and no page code, after the Core checks the URL: GET only, no query string composed by the model, a capped URL length, no cookies, and internal addresses blocked (see D73). The researcher has no network of its own. Pages are parsed inside the sandboxed researcher, never in the Core; the researcher browser plugin, if kept, has no network at all and only renders bytes the trusted fetcher returned. It has no write tool; its report is `external`, shown to the human only, and never handed to the planner as text.
- **System notifications** are static templates with parameters resolved by the Core, never model text, never URLs from a model.
- **Replies on a secondary channel** come from templates or stay within that channel's ceiling, an allowlist of data types (see D82, D103), pass the outbound content check (P5), and point to the primary channel for details (see D42).

~~An external MCP assistant is treated as a planner whose host Vilicus does not control. It gets reader output rather than raw untrusted bodies by default; a raw read is an explicit per-member opt-in and taints the session from that point.~~ Withdrawn: Vilicus exposes no MCP endpoint and no other API to outside AI assistants; MCP is internal, between Vilicus's AI processes and the Core (see D49).

### P3. Capability tokens per task

The Core issues tokens scoped to a task, a member, a module, a partition, a set of actions and a budget. Tokens are short-lived (10 minutes, see D113), revocable and logged. A token is accepted only from the peer unit it was issued to, and the Core binds each AI process instance to one role, member and provider (spine AD-11, AD-24). An assistant acting for member X can never exceed X's scope. Partition isolation is enforced by keys held in the Core, never by instructions in a prompt. Creating or revoking tokens is not a tool.

Tokens bind AI processes and plugins. A scheduled task acts as an AI task with one capability token per run (PRD FR-87). Four principals act without a token bound to one member, each under a scope fixed by the Core: a home rule validated by a human, a playbook validated by a human, a household display, and a device adapter, checked against the validated rule or playbook, the display scope, or the adapter's manifest and grant (see D54, D55, D58, D65).

**Tool policy.** Each member has a tool policy, a subset of the capability matrix that the Core intersects with every token issued for that member (assistant sessions, scheduled tasks, plugins and bound channels) and applies to the playbooks that act for that member (see D66). It only narrows: it never adds an actor to an action and never raises a tier. Only the member widens their own policy, with a step-up; another adult may narrow it, and the member is notified. An activatable module that is off exposes no tool, starts no plugin and opens no file.

### P4. Three action tiers, and a precise meaning of "reversible"

| Tier | Examples | Rule |
|------|----------|------|
| 0 Read | List tasks, read an event, query the budget, read device state | Allowed within scope, logged |
| 1 Reversible write | Create a task, move a personal event, add a shopping item, prepare a cart in the member's own store account, switch a light or move a shutter, send a digest to the member's own address | Allowed within scope, journaled, undoable. Elevated when the session is tainted |
| 2 Irreversible, third-party or cross-partition | Pay, send, delete for good, share, answer an invitation, move an event that has guests, sync to an external account, write from a personal partition to the household or to another member, and, once the native app exists, unlocking, disarming, opening and cutting power to the infrastructure (see D69) | Signed confirmation from a paired native app, every time |
| H Human-only | Pairing, recovery, rights changes, plugin install, exposure, controller thresholds, device adapter grants, confirming or changing a device's safety class, a home rule acting on a safety-relevant device, enrolling a household display, adding a remote access peer, creating a delegation sub-key, creating a disclosure grant, activating a module for the household, configuring a model provider | Never exposed to the AI; step-up bound to that one action, or signed confirmation |

Before the native app exists, tier 2 actions are not registered at all, rather than degraded to a weaker confirmation (see D46). The same holds for unlocking, disarming, opening and cutting power to the infrastructure: Vilicus does not offer them at all before the native app, and the household uses the device vendor's app or a physical gesture (see D69). Every step-up assertion signs a challenge derived from the canonical hash of exactly one pending action and cannot be replayed for another action or a time window (see D71); it still does not prove what the browser displayed, which is why D69 keeps letting someone in off the web. Ordering and payment in a store always stay with a human on the store's website; Vilicus never places an order (see D44). An elevated tier 1 call goes, while no alignment controller exists, to a queue in the primary channel and needs a light confirmation (see D38).

**Spoken confirmation.** A spoken "yes" approves an elevated tier 1 request that carries no I13 exception class, and nothing else: never a cart, an own-account delivery or a restorable physical action, never a rule, a scheduled task, a playbook, an H action or tier 2 (see D68). Audio is transcribed locally only, because its data type is unknown before transcription. Before a spoken yes, Vilicus reads the request back from a fixed template filled only with its structured fields, never from model text; the yes approves only the request read back, bound to its hash (see D100). A spoken yes is recognized by the Core's speech stage on the local transcript, never by an AI process; the transcript of a confirmation window is not sent to the planner, and no tool approves a request. After the read-back of exactly one request ends, the Core opens a confirmation window of a few seconds; any other audio played by Vilicus closes it. A voice conversation can approve only requests it created. A label of a referenced record is spoken only if it is `trusted` for the member; otherwise the request is not voice-approvable. A spoken approval proves that someone near a voice client said yes, not who said it, which is why its reach stops at elevated tier 1.

**Reversible means reversible without effect on a third party.** Undo cannot recall an email, an RSVP or a synchronized change. Any outbound network effect is therefore tier 2, except for the system notification path and the named exception classes of I13, a closed set (see D67):

- **System notification path:** static template, the member's own channel, rate limited. Replies on a bound secondary channel stay within its ceiling (see D42).
- **Reversible external state** (`reversible_external_state`): a change in the member's own external account that no third party sees and that Vilicus can undo, namely cart preparation, tier 1 with light confirmation (see D44).
- **Restorable physical action** (`restorable_physical`): a device action undone by restoring the previous target state (lights, shutters, heating setpoint within a set range, and similar), tier 1 (see D56). It never applies to moving a safety-relevant device away from its safe state (P13).
- **Own-account delivery** (`own_account_delivery`): a write to an account the member owns that nobody else sees (mail to the member's own address, a file in a dedicated folder, an unpublished blog draft), tier 1 with light confirmation, or, for a playbook run, the owner's standing approval for that destination, revocable and listed in the member's settings (see D67, D89). Its tool takes no destination argument: the Core resolves the destination from the member's account registered by an H action, and the destination is hosted unless its host resolves to the Vilicus host or to an address range the household declared private by an H action. Its body is plain text, or HTML rendered by the Core from a template that references no remote resource (see D81). It follows the provider policy by data type and passes the outbound content check; local-only data types are never delivered to an account hosted by a third party (see D81). Publishing, or sending to anyone else, is tier 2.

Rules for tier 2:

- The confirmation screen is generated on the device from the real parameters, not from the model's description, using a locally shipped template per action type.
- The channel is a **paired native app**. The device computes and displays the canonical hash and signs it with a hardware-bound key that requires biometrics or device credentials; the Core recomputes and verifies; the Gateway only relays. Details in `architecture.md`, section 10.
- A confirmation is bound to exactly the confirmed parameters, single use (nonce), and expires in under 2 minutes.
- The web client never confirms tier 2, because WebAuthn does not prove what was displayed and the Gateway is not trusted. No chat reply, no spoken answer, no secondary channel, no household display and no web click can confirm.
- Confirmations are bounded: one pending at a time by default, batching of homogeneous requests, a separate queue for requests from tainted sessions, repeated refusals suspend the task.

### P5. Provenance and taint

Taint is mandatory metadata on every record of every module, not only on memory. Each record carries a `source` and a `taint` (`trusted` or `external`); the Core adds `member` at read time when a member's assistant reads data authored by another member. `member` is a read-time view, never a stored label. The order is `trusted` < `member` < `external`.

- Derived data inherits the most restrictive label. A summary of external data is external.
- A session becomes tainted when it consumes any `external` datum, including a reader's typed output, or any `member` free text. Structured fields of `member` taint do not taint the session (see D70). A field is structured only if its value set is fixed at build time: a compiled enumeration, a bounded number, a date, an opaque UUIDv7, or a label of a reviewed vocabulary that an adult confirmed (at most 32 characters from a restricted alphabet); every other field, run-time vocabularies included, is free text (see D104).
- Effects of taint: tier 0 allowed; tier 1 elevated; tier 2 goes to the separate tainted queue and the confirmation shows the origin; H denied; kill switch not available to the session. These effects apply to AI and plugin principals only, scheduled tasks included; a member, CLI, home rule, playbook, household display, device adapter or event call is never gated by taint, but its writes still store the computed taint (see D58, D65). A playbook is not gated because it has no model step and reaches at most tier 1; a playbook or a scheduled task proposed by the assistant keeps its origin and the taint of the session that proposed it.
- Anything arriving from a plugin (a device adapter report, a secondary channel message) is stored `external`, whatever the plugin claims.
- A record written by a tainted session inherits that session's taint, so unapproved tainted writes cannot launder into `trusted`. The exception is a write the member makes or explicitly approves (their own action, or a light confirmation of an elevated request): its structured fields are stored `trusted` with that member as author and provenance pointing to its inputs (see D70), while free text drafted in a tainted session keeps `external` whatever the approval and however edited; only text the member writes in full in an empty field of the approval screen is stored `trusted` (see D99). A member-written field that contains 8 or more consecutive words of the assistant's draft is stored `external`; this is a verbatim test, not an edit ratio (see D104). Pasting or importing external text into a trusted field is still a promotion.
- A record kind exempt from the elevated queue accepts only structured fields from an AI principal, and a household write from a session that has read personal free text is elevated (see D104).
- Data written by another member, structured or free text, reaches the planner as quoted data within its declared length and with its taint (see D37); only its free text taints the session (see D70). `external` free text reaches the planner only as typed reader output, or not at all, except a member-approved assistant draft, which reaches it as quoted data within its maximum length and taints the session (see D104).
- Promoting tainted data to a lower label happens only from the host CLI, for data the member authored or imported; never through the Gateway (see D45). Batch promotion, by category after reviewing a sample, applies only to records whose fields are all structured; a free-text record is promoted one by one, or retyped (see D112).
- Data written by another member is treated as untrusted for the assistant of a member: it may be read as data, never followed as instructions.
- Any write from a personal partition into the household partition, or into another member's partition, is tier 2, and stays unregistered until the native app exists (see D46). The single exception is a **disclosure grant** (see D64): an H action by which a member lets the Core compute one minimal value from their own data with a derivation function registered in code (no model) that returns closed types only, and seal it into another adult's inbox. The value keeps the data type of its source (a value derived from health data stays health data, local model only), is stored with the taint of its inputs (I9) and the granting member as author, so the recipient's assistant reads it as `member` taint, never appears on a secondary channel, and is audited without the value (see D104). Ingestion accepts it only under a live grant the recipient was notified of, authored by the grant's owner and matching the grant's registered derivation (see D93). The granting member can revoke it at any time. The assistant may use the requesting member's context to propose a household write, executed as that member, without copying any free text of the member's personal partition into the household record (see D50).
- **Outbound content check.** Before a tier 2 send leaves the instance, the Core scans the outgoing body for fragments of private partitions that should not be there, and blocks a send to a non-member when such fragments appear in a confirmation derived from a tainted session. Replies on a secondary channel and own-account deliveries pass the same check (see D81). This is a heuristic backstop (exact and fuzzy match of stored values), not a proof.

### P6. Memory is an attack surface

- Facts derived from untrusted content are tagged, quarantined, and not used for planning until a human promotes them from the host CLI (see D45).
- Provenance is recorded per conversation turn (PRD FR-95): a fact drawn only from the member's own words typed in the primary channel stays `trusted` and usable for planning. A transcribed turn carries `spoken` provenance: it does not taint the session, but a fact drawn from it is stored `external` until the member confirms it in the app with one tap (see D112, I42). A fact drawn from a turn that consumed any `external` datum or `member` free text, the data that taint a session (P5, D70), is `external`.
- Consolidation builds each model context from inputs of one label: a context of trusted turns and trusted facts only, whose outputs are `trusted`, and separate contexts for the rest, whose outputs are `external`. The provenance of a consolidated fact is the set of records placed in its context, computed by the Core; the model never states where a fact came from.
- Memory consolidation runs only inside its owner's unlock window, never through a delegation sub-key and never with the member's data key held outside it. Briefings and other output of a delegated run are stored `external` and shown as such (see D93, D111).
- Automatic retrieval returns `trusted` facts only. An `external` fact reaches a planner only as the result of an explicit search tool call, which taints the session. Quarantined facts live in a separate index. Embeddings are a model call under the provider policy (P10).
- Memory imported from a previous assistant is `external`, and a knowledge graph extracted by a model is not used for planning (see D41); its free-text records are promoted one by one, never by batch (see D112).
- Facts carry source, taint, date and validity. They are invalidated, not silently overwritten, and can be rolled back (`MemoryStore` interface).
- The assistant cannot rewrite its own instructions or policy through memory.
- Memory is partitioned like the rest: one store per member and one for the household, each under its partition key.

### P7. Contain exfiltration

- No automatic fetching of URLs or images produced by the model. Because a member's mail client or file preview may fetch what Vilicus does not, model-composed text in an own-account delivery, a deposited file or a draft contains no URL except URLs that appear verbatim in the source records it cites, and a deposited HTML, Markdown or SVG file or a draft references no remote resource (see D81).
- A URL that a Core stage will fetch (recipe import, a watched feed, any future subscription) is never supplied by an AI principal: the tool accepts it from a `Member` principal, or from text the member typed in the current turn, verbatim, never composed or edited by a model.
- No model connector enables a provider-side capability: server-executed tools, remote MCP or account connectors, response or file storage on the provider. API connectors build request bodies from an allowlisted set of parameters, and a connector test asserts the exact body against a test double; E30 checks the Claude subscription connector's request bodies the same way (see D97, D110).
- The researcher follows only links found verbatim in pages already fetched for its task, under the rules of P2; a URL it composes is refused (see D63), and every request is made by the trusted fetcher, not by the researcher (see D73).
- AI processes and plugins reach the network only through the egress proxy with an exact-hostname allowlist. The proxy resolves every name itself and refuses internal addresses for every caller (spine AD-16). Two exceptions: a device adapter holding a named grant of a USB device, a Unix socket path, a shared private namespace with a named managed daemon, or a private address range with ports enforced per unit by an nftables rule, which is an H action (see D54, D115); no unit is granted a loopback address, and the adapter's internet access still goes through the proxy; and the trusted fetcher, whose requests go through the proxy in researcher egress mode, which allows any public host but blocks internal addresses and applies per-host request budgets (see D63, D73). Researcher egress mode applies to the trusted fetcher only, never to an AI process or a plugin; the researcher and the researcher browser plugin have no network at all. Core-originated traffic (push webhook, backup upload, remote audit sink, heartbeat) may also reach a private host and port the instance admin named by an H action; that destination is allowed to the Core and the backup caller only, never to an AI process or a plugin (see D105).
- The local model runtime has no network and is reached only over per-role Unix sockets (see D83). The quarantined reader and the researcher never share a runtime process with the planner or the drafter (see D110).
- Per-host request budgets in the egress proxy are shared by every caller that reaches a host, so no combination of tasks gets the household's address blocked by a site (PRD FR-105).
- Outbound messages go to allowlisted recipients or require tier 2 confirmation.
- Output rendered to humans is sanitized, with external content in a sandboxed iframe.
- Notifications are templates, rate limited, so they cannot carry freeform data.
- ~~**Messaging plugins are outbound only, and only for notifications.** An inbound message is untrusted content that triggers no action. No tier 2 confirmation ever transits through a messaging plugin.~~ Superseded by D42. **Secondary channels** carry inbound and outbound messages for a sender bound to a member by a challenge from the primary channel, in one-to-one conversations only. Inbound content is untrusted and taints the session; a bound channel triggers tier 0 and tier 1 only, never tier 2, H, pairing, recovery or a binding change; unbound senders and group conversations are dropped. Outbound content stays under the channel's ceiling, which never includes `budget`, `mail_raw` or `health`. The ceiling is an allowlist of the data types Vilicus may send on that channel: `presence`, `home_state`, `alarm_state`, `calendar` and `child` are excluded unless an adult adds them (see D82). It is applied as input gating: a token issued for a session whose output may reach that channel cannot read a data type outside the ceiling (see D103). No tier 2 confirmation ever transits a secondary channel.

### P8. Plan for a wrong model, not only a hostile one

- Strict schemas on every tool call; invalid calls are rejected, not repaired.
- **Idempotency keys derived deterministically from the business parameters** (for example the cart contents), so a retry or a duplicate proposal does nothing twice.
- Default caps (to tune): amounts, orders and messages per period, tool calls per task, token and cost budget per task and per member. Values in the capability matrix, section 11; in V0.1 a token's budget is a number of tool calls (see D113).
- Loop and repetition detection with automatic suspension.
- Dry-run mode that shows what would happen.
- A **kill switch** that revokes all tokens and suspends the assistant, the rules, playbooks and scheduled tasks of assistant origin, and the plugins that declare a network effect. It never stops a device adapter or a rule of human origin, so the house keeps running (see D58, D65; PRD FR-87). It also stops the Claude subscription connector units. Only a human can trigger it, from a web session or as root at the host CLI with `vilicus killswitch` (see D101), never a tainted session; a Core detector suspends only the offending task or AI session (see D86); resuming requires a passkey.
- A **daily digest** of the assistant's writes, read by a human, including what scheduled tasks and playbooks did while nobody watched.
- Defined behaviour when the AI provider is unavailable (queue with a timeout, then fail with a notification, no silent switch of provider).
- Pinned model versions; a version switch runs the evaluation suite first (section 4). For the Claude subscription connector, the binary's hash and tested version ship in the signed Vilicus release, and the suite runs per binary hash, model identifier and prompt template (see D110).
- No free-form SQL, shell, file system or network access for the model.

### P9. Everything is audited

Each proposal, validation, confirmation and execution is written to the tamper-evident log with: actor (member and assistant, or the rule, playbook, display or adapter principal), task, token id, action, tier, opaque identifiers and canonical parameter hash (not the parameters), taint, and outcome. Home rule runs and adapter reports are audited in aggregated entries per period; an action on a safety-relevant device is always an individual entry. Each computation of a disclosure grant is audited without its value (see D64). The household can review what the assistant did through the digest and module journals.

### P10. Provider policy by data type

The provider policy is evaluated per data type before any model call (see D48). `health` (children's included), `journal` and `budget` go to the local model only and can never be widened to a remote provider. `meals`, `meal_plan`, `stock` and `shopping_list` may go to a remote provider configured by an adult. Any other data type follows the strictest rule that applies to it. Remote providers receive only what the task needs, under a policy the household can inspect. A call routed to a provider that is not configured fails closed with a notification; there is no silent fallback to another provider.

The rule needs every datum to know its data type (see D80). "Data type" is one closed set held in `vilicus-types` (see D103). Each record kind declares the data types its fields may hold, every record stores the set of data types it contains, and a derived record's set is the union of its inputs' sets, computed by the Core like taint (I43). A conversation that touched a local-only type stays on the local model, and its history is never loaded into a remote or Claude-connector session. When the Core issues a capability token, it binds the session's provider from the data types that token may read, so a session that may read a local-only type is bound to the local model before it reads anything; a call or a tool result the binding does not allow fails closed rather than being downgraded. Children's dietary constraints are health data and stay local: the Core applies them as a deterministic filter before and after a remote meal-planning call, and the remote model never receives them. Own-account delivery follows the same policy (P4, see D81). The local model runtime that serves the local-only types is its own component, with no network and no cache shared across members or roles (see D83).

Three cases follow from this rule. Audio is transcribed locally only, because its data type is unknown before transcription (see D68). The researcher's question is classified at the strictest rule unless the member picks a data type, since the question leaves the instance (see D63). The Claude subscription connector serves only the sessions of the member whose plan it uses, and that provider falls under this same rule (see D97). It is its own provider-policy entry and allows no data type by default: the member opts in data types of their personal partition, and each household-partition data type needs the agreement of every adult; the plan's account identifier is recorded at sign-in and checked at every start (see D110).

### P11. The alignment controller reduces friction, never replaces the human

A small local model (CPU, under 16 GB of RAM) answers a constrained question about a proposed elevated tier 1 action: accept or ask the human, with a probability and a confidence. It is the third layer: deterministic rules first (allowlists, caps, tiers), then the controller, then the human. It is not part of V0.1; until it ships, every elevated tier 1 call goes to the queue in the primary channel (see D38).

Rules:

1. **Structured input only.** It receives the user's original request as recorded by the Core on a trusted channel, the action type, enums, identifiers and diff metadata, and provenance flags. It never receives raw untrusted text or free-text fields, never decides on them, and is advisory only for tasks without a trusted original request.
2. **Closed output.** The answer comes from a closed set, enforced by grammar. Doubt, error, timeout, low confidence or unavailability mean "ask the human" (fail closed).
3. **Limited role.** It can lift only the elevation friction of tier 1. It never replaces confirmation of an irreversible, financial or third-party-affecting action, so tier 2 and H are out of its reach.
4. **Fixed thresholds.** It cannot modify its own thresholds, and neither can the assistant; a human sets them.
5. **Measured.** Metrics on a household evaluation set of legitimate and trapped cases: false accept rate (primary), false reject rate, expected calibration error. The false accept rate is a release gate.
6. **Realization (v1, planned).** A 3 to 4 billion parameter model in GGUF Q4 (Qwen or Gemma families), grammar-constrained output (GBNF), reading the log-probabilities of the options, recalibrated on the household set, with conservative thresholds. A fine-tuned encoder classifier is a v2 option. The commercial Jev model by TypeSafe AI (Choice, Score, Noul) is a conceptual reference, not a dependency: proprietary, API only, English first, not self-hostable; at most an optional connector for non-sensitive data.

### P12. The human is also a component with limits

A user who approves everything defeats tier 2. A light confirmation approves one request, or a batch whose every line is shown and whose canonical hash covers all lines; no model-written justification is shown on an approval screen. Confirmations must stay rare and legible, show taint origin without clutter, and be counted: a rising weekly tier 2 rate or a rising approval-without-delay rate is reported in the digest as a safety signal.

### P13. The house moves only toward safety without a human

Home automation acts on the physical world, so the worst case of a fooled model or a wrong rule is a door that opens, not a wrong record.

- Home rules are deterministic code in the Core, running without a model and without a member key, under the rule principal (see D57).
- On a safety-relevant device, home rules and tier 1 callers only move toward the safe state: lock, arm, close, camera on. Unlocking, disarming, opening and cutting power to the infrastructure are never done by the assistant. Before the native app Vilicus does not offer them at all, to anyone: the household uses the device vendor's app or a physical gesture, and Vilicus arms, locks, closes and alerts. Once the native app exists they are tier 2, confirmed on it (see D56, D69).
- Life safety comes first (see D91, amending D56): the safe direction protects against intrusion, not against fire, water or frost. While a smoke or water alert is active, lock, close and cut commands are suspended for every principal, shutters may open, and every adult is alerted; Vilicus still unlocks and disarms nothing. A heating valve is never closed below a floor temperature, and a closing command on a gate or a garage door is refused when the device reports no obstacle detection of its own.
- A device is safety-relevant from discovery when it is a lock, an alarm, a camera, a gate, a garage door or a cover of unknown kind, before any adult acts. An adapter cannot change the class of a confirmed device, and reclassifying a device is an H action (see D72).
- An unclassified `switch`, `plug` or relay output accepts no command from a household display, the assistant or a rule until an adult classifies it, because a gate, a garage door or a door strike wired to a relay reports as a switch. A `momentary` capability is safety-relevant from discovery and never tier 1; when it drives an opener it follows the unlock and open rules above (see D69, D109).
- When household presence turns to someone home while the alarm is armed, Vilicus alerts the adults and points them to the vendor's app or the device; once the native app exists it sends a disarm proposal completed as tier 2 on it (see D69).
- The assistant may propose a home rule. At validation, the rule is re-created from its structured fields and keeps its origin; every rule of assistant origin is suspended by the kill switch. A rule acting on a safety-relevant device is created or changed only by an H action, and runs only while its structured form matches the approved one.
- A playbook that touches a safety-relevant device follows the same rules as a home rule (see D65).
- A household display acts under its own principal: home domain only, tier 0 and tier 1 on devices that are not safety-relevant, modes that concern no safety-relevant device, never an H action and never member or household data outside the home domain (see D55).
- Device state reaching an AI session is `external` (P5), so an assistant that reads the house is tainted.

### P14. Unattended work is structured, owned and bounded

Scheduled tasks and playbooks act while nobody watches, so what they may do is fixed before they run, never decided at run time from free text (PRD FR-87, FR-98; see D62, D65).

- A **scheduled task** is a structured definition (kind, trigger, tools, caps, delivery, origin, owner) with an optional instruction text. Its `kind` comes from a closed set, each with a prompt template shipped with Vilicus. The instruction is `trusted` only when the member typed it in full (D99); text drafted by the assistant in a tainted session stays `external` after validation. Each run starts with the session taint of its definition: tainted if any free-text field of the definition is `external`. Each run gets one capability token as an AI task, limited by the owner's tool policy and by caps per task. After a restart or a missed time, it runs at most once late, within its staleness limit, or is cancelled and recorded. Results land in the primary channel; a secondary channel receives only a template or content within its ceiling after the outbound check (D42). A task that reads external content goes through the quarantined reader, so such tasks wait until the reader ships.
- A **playbook** is a declarative, versioned, schema-validated chain of tool steps run by the Core under the playbook principal, with no model step. Each step goes through the action pipeline and reaches at most tier 1 or a safe-direction home command; it sends outside only through the system notification path or own-account delivery. A message step picks a template from the closed set shipped with Vilicus, or uses text the member typed in full (D99); its parameters are Core-resolved values of data types allowed on the destination channel, and text drafted by the assistant is never a notification template. A playbook triggers only on records written by a `Member`, `Rule`, `Adapter` or `Cli` principal (see D109, I41).
- A member creates their own tasks and writes or validates the playbooks that act for them. The assistant may propose either; the proposal keeps its origin and taint and is validated only by the member it runs for.
- Neither can be validated by a spoken confirmation (see D68).
- Without a delegation sub-key, a task waits for its owner's next unlock within its staleness limit, and the owner gets a content-free notification. A delegation sub-key, opted into per task by an H action, opens one module file in one partition and nothing else (see D62). For a delegated task, the Core keeps a run descriptor in `core.db`: the fire time and staleness limit in clear, the structured definition sealed under the delegation sub-key; the run's output is stored `external` (see D94, D111). A member-owned plugin runs only while its owner is unlocked (see D111).
- The kill switch suspends every task and playbook of assistant origin (P8); caps, the digest and the audit log bound the rest.

## 2. Process isolation

The AI runs in its own sandboxed processes (reader, planner, drafter and researcher as separate instances): separate dynamic user, no access to module databases or keys, no ambient network, a socket to the Core only, egress only through the proxy. Several researcher processes may run in parallel, each with its own token and budget; the researcher and the researcher browser plugin hold no secret, no household data and no network, and parse or render hostile pages inside their own sandbox from bytes the trusted fetcher returned (see D63, D73). The trusted fetcher runs no model and no page code. The local model runtime is a separate unit with no network, reached only over per-role Unix sockets, with no cache shared across members or roles and model files pinned by hash (see D83). The quarantined reader and the researcher never share a runtime process with the planner or the drafter; within each group one runtime instance serves every role and member, with cache reuse disabled and requests serialised, and per-member instances run only where E25 shows the memory fits (see D110). Each AI process instance is bound to one role, member and provider, and its egress allowlist derives from that provider alone (spine AD-24). The Claude subscription connector runs as one unit per connected member under its own user; for each session it starts one child of the unmodified binary, never reused across sessions, roles or members, whose only MCP server is a per-session bridge to the Core, and revoking the token kills the child (spine AD-53, see D97, D115). Every Vilicus unit hides other processes (`ProtectProc=invisible`). Plugins run in separate sandboxed processes with the same fixed profile; a device adapter additionally holds only the named grants of its H action (see D54). The profile is imposed by the Core and tested in CI (`architecture.md`, section 4).

## 4. Evaluation

- An evaluation suite is versioned in the repository: injection corpus, controller cases (including French), tool-call correctness, idempotency under retry.
- The suite and the prompt-injection regression corpus, member-authored injection cases included, run in CI before any conversation ships (PRD FR-64), with the pass criterion of section 3: an effect outside a case's expected outcome fails the release, whatever the model did.
- A new model version, a new controller threshold or a new prompt template must pass the suite before it is used; results are stored with the version. For the Claude subscription connector, the suite runs per binary hash, model identifier and prompt template (see D110).
- Controller calibration is re-measured on the household's own labelled cases after enough real data exists.

## 5. What this does not solve

- A fooled model can still produce wrong tier 0 and tier 1 results within its scope (a bad summary, a wrong task, a misfiled transaction, a light switched at the wrong time). The journal, undo and the daily digest are the answer, not prevention.
- A user who confirms without reading defeats tier 2 (P12).
- A compromised host defeats these controls (`threat-model.md`, T12).
- A compromised phone with malware controlling the screen defeats the displayed-parameters guarantee unless Android Protected Confirmation is in use on that device.
- Taint is label tracking: a wrong or missing label at the source defeats downstream decisions. Producers are therefore few and trusted (Core, reviewed modules), and plugins cannot lower a label.
- The controller can be wrong; its role is limited so that a wrong answer costs a bit of friction or an elevated write, not an irreversible action.
- Before the native app, the human guard is a tap in a browser served by the Gateway: a compromised Gateway can alter what a light confirmation shows and make the device key sign it (`threat-model.md`, T24). A step-up bound to one action (see D71) cannot be replayed, but the Gateway can still show one H action while the member approves another; pairing, remote access peers and plugin grants stay browser step-ups until the native app, which is why letting someone in is not offered before it (see D69; `threat-model.md`, T52). Lifting a suspension also stays a browser step-up (see D87), so a compromised Gateway can redirect it; the delay, the veto and the out-of-browser alerts bound it (see D101; `architecture.md`, R40).
- Injection between adults is contained by taint, human approval and undo, not prevented: the other adult's household text reaches the planner as quoted data (see D37), and a write the member approved stores its structured fields `trusted` (see D70), while model-drafted free text stays `external` (see D99), so the approval is the guard for structured data and taint remains the guard for text.
- The dietary filter around remote meal planning is only as good as the constraints recorded; the remote model never sees them, so it cannot help catch a missing one (see D80).
- A bound secondary channel taken over by its attacker acts as the member within tier 0, tier 1 and the channel's ceiling (see D42).
- Tiers govern what goes through Vilicus, not what devices accept from elsewhere: a radio daemon, a vendor app or a compromised adapter can drive devices directly.
- The researcher's containment limits exfiltration through its choice of links to the member's own question and to links found in fetched pages; the trusted fetcher makes that rule enforceable (see D73), it does not eliminate the leak, and every visited site sees the household's address and the fetcher's fingerprint (see D63).
- The local model runtime processes every local-only data type and every document the quarantined reader sees; its unit, socket and cache separation bound what a hostile document can reach through it, they do not make it trusted (see D83; `threat-model.md`, T58).
- A disclosure grant reveals a derived value over time, from which the source can be partly inferred, and nothing technical stops one adult from pressuring the other to grant one (see D64).
- Scheduled tasks and playbooks act while nobody watches; caps, the digest and the kill switch bound them, they do not supervise them (P14).
- A spoken confirmation proves that someone near the voice client said yes, not who: a child, a visitor or played audio can approve an elevated tier 1 request (see D68; `threat-model.md`, T48). Played audio can also issue tier 1 commands in an untainted voice session; facts drawn from it stay `external` until the member confirms them, and voice-session writes are listed separately in the digest (see D112; `threat-model.md`, T65).
- An allowlisted provider hostname does not bind the household's account, and a remote provider's multi-tenant hosts are outside Vilicus's isolation (see D110; `architecture.md`, R39, R53).
- Delegated data is readable by whoever controls the host or holds a backup and its backup secret (`threat-model.md`, T45), and the schedule times of delegated tasks are visible to the instance key holder (see D111).
