## 2. Assumptions

| Assumption | Why it matters | Risk if wrong |
|------------|----------------|---------------|
| A household volume (thousands to low millions of rows) fits SQLite comfortably | Allows file-per-module-per-partition | Performance rework |
| A 3 to 4 billion parameter quantized model can classify structured states well enough after recalibration | Controller viability | Controller dropped to a deterministic-only path |
| Users will keep a printed recovery secret | Recovery model | More lost partitions |
| Households with children will run one adult at least as admin | Admin model | Admin recovery complexity |
| Android is the first native platform | Tier 2 | iOS households cannot confirm until a native iOS app exists (open: not planned) |
| A small number of tier 2 requests per week is acceptable | Fatigue | Friction, shadow IT |
| Modules compiled in the Core process are acceptable at v1 | Simplicity | R2 |

## 4. Open design questions that depend on experiments

- When PRF unlock is added after V0.1, and whether on Android (E1, E2).
- Which Apple and Android clients get the hybrid exchange (E3); the desktop and command-line clients are recorded, and the README names only those.
- Whether the controller ships in v1 (E6).
- Whether Tauri is used on Android (E7).
- Cart preparation is no longer tier 2 (see D44); E18 still decides whether an official store API exists before the meals module starts.
- Whether passkeys, PWA installation and the port-based separate origin work with each naming option (E24, E26).
- Whether the elevated tier 1 rate stays under the threshold under the taint rule of D70 as amended by D99, or the E23 fallback is needed.
- Whether the device adapter sandbox and the remote access endpoint hold on the target host (E27, E28).
- Whether real-time voice works in the installed web client on Android, in the background and in a car (E29).
- Whether the Claude subscription connector holds in the shape of D97: built-in tools off, no transcript kept, no provider-side capability, network through the egress proxy only (E30).
- Whether a signed boot policy works on the household's host, which decides whether it can drive physical security devices (E31, D108).
- Whether the Core's threading model keeps home rules responsive during unlocks and backups (E32).
- Whether the `hpke` crate agrees with an independent HPKE implementation and the RFC 9180 test vectors, as the cross-test in CI required by D61 must show (done state in D107; the independent implementation is `hpke-rs` 0.8.0 with its RustCrypto and libcrux providers, and the review, vectors and cross-test passed in `spikes/hpke-review/` (D120); the CI job of Story 2.2 passed on its first run, 2026-10-18: https://github.com/Rwx-G/Vilicus/actions/runs/39157276092/job/117762975775); **settled** for V0.1, pending the owner's approval of the review's dispositions (D120); the external review of D61 comes before V1.
- ~~How a member's first receipt of the household key is confirmed.~~ Resolved by D121: a confirmation key derived from the enrollment key and wrapped under the new member's DEK authenticates the first HK, then a DEK-keyed commitment covers every later unlock.
- How every remaining member confirms a new HK version after a rotation (PRD FR-9), which is a new first receipt that D121 does not cover; a candidate is a signature by adults whose public keys are pinned under each member's DEK, as MLS does for GroupInfo (RFC 9420) (R55, T68). **open**, before FR-9 code.
- ~~Whether the private-network naming option fits FR-4 and FR-6.~~ Resolved by D137: 100.64.0.0/10 is private only on one overlay interface the operator names, with the Gateway's socket bound to it.
- Whether Firefox with a real authenticator accepts an allow list of two credentials; its WebDriver virtual authenticator refused every such list (E24). Blocks the E24 gate of V0.1. **open**.
- How the enrollment test notification (D105) proves receipt now that the push payload carries no token (D135): the candidate is confirming the payload's opaque reference in the member's signed-in client, which alone acknowledges nothing. **open**, before Story 8.1.
- Whether FTS5 shadow tables stay read-only to module SQL under `SQLITE_DBCONFIG_DEFENSIVE` and pass `integrity-check` after a migration, as D127 requires (E15, and the E11 suite rerun with defensive mode on). **open**.
