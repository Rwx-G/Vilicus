# Story 1.12: E14: egress proxy domain filtering

As the owner,
I want CONNECT-based exact-hostname filtering tested against real client traffic,
So that the egress proxy of Epic 5 is the network control it claims to be.

**Acceptance Criteria:**

**AC1 (E14, FR-55, AD-16)**
**Given** a prototype proxy under `spikes/e14-egress/` accepting `CONNECT host:port` over a Unix socket with an exact-hostname allowlist, resolving names itself and connecting to the checked address
**When** a reference client makes HTTP/1.1 and HTTP/2 requests to an allowlisted host, attempts QUIC, and follows a redirect to a host not on the allowlist
**Then** allowlisted traffic works, QUIC cannot leave without the proxy, and the redirect target is refused

**AC2 (E14, AD-16, I4)**
**Given** a test resolver that answers a public address for a name on the first lookup and an internal address on the second
**When** the client connects to that name through the proxy
**Then** the proxy refuses the internal address at connect time

**AC3 (E14, I4)**
**Given** the client tries a direct outbound connection without the proxy under `IPAddressDeny=any`
**When** the attempt runs
**Then** it fails
**And** if any bypass of the allowlist is found, the fallback (per-plugin IP ranges as a second filter) is recorded in `doc/decisions.md`

**Spike plan:**
- Question: does CONNECT-based domain filtering hold for real traffic (HTTP/2, QUIC, redirects) (E14)?
- Method: reference client and prototype proxy; a rebinding resolver; direct-socket negative test.
- Pass criterion: no bypass of the allowlist; no breakage of normal flows.
- Timebox: 3 working days.
- Fallback on failure: per-plugin IP ranges as a second filter.
- Result record: E14 status in `doc/research-notes.md`; the test set kept for Story 5.5.

**Dependencies:**
- None.

## Implementation Notes

**What was built.** A standalone crate, `spikes/egress-filter/` (own empty `[workspace]`, edition 2024, Apache-2.0, `publish = false`), never part of the product workspace, plus a Docker Compose test network.

- `src/lib.rs` and its modules, `#![forbid(unsafe_code)]`:
  - `address`: the address check of AD-16 as a pure function, `check(address, policy)`. It returns the address to dial or the refusal. IPv4 is refused by table; IPv6 is accepted only inside global unicast (`2000::/3`), minus `2001::/23` and the documentation ranges. IPv4-mapped addresses are dialled as plain IPv4; NAT64 addresses (the well-known `64:ff9b::/96` and any network-specific `/96` set by `nat64-prefix`) and 6to4 (`2002::/16`) addresses are judged on the IPv4 address they embed. Deployment prefixes (`blocked`) are refused on the dialled and on the embedded address.
  - `target`: one parser for the CONNECT target and for allowlist entries, so both compare as equal strings. It accepts a DNS hostname only (lowercase ASCII LDH labels, no trailing dot, a last label starting with a letter, so no `inet_aton` form) and a canonical decimal port.
  - `config`: a line-based configuration (callers with kind and uid, `allow`, `private`, `sni-check`, `blocked`, `nat64-prefix`, `budget`, `budget-default`, `header-timeout`, `caller-connections`, `tunnel-idle`, `tunnel-lifetime`, `dial-deadline`, and `documentation-ranges-public`). A named private destination is refused at load for any caller other than the Core or the backup caller (D105), and its range must lie in RFC 1918 or unique local space. `documentation-ranges-public` is accepted only in a build with the `test-network` cargo feature; a release build refuses it at load.
  - `budget`: per-host budgets keyed by hostname (every port counts), counted in tunnels per sliding window, shared by every caller. Every host has a budget, its own or the default one, and part of each budget is reserved for the Core and the backup caller (finding 4).
  - `sni`: a minimal parser of the tunnel's first TLS record. For a caller with `sni-check`, it must be a single-record ClientHello whose SNI equals the CONNECT host, with no Encrypted Client Hello extension (finding 2).
  - `proxy`: one Unix listener per caller (`<caller>.sock`, the shape of AD-55). Per connection, in order:
    - a slot under the caller's connection limit (503 when none is free);
    - the peer uid (`SO_PEERCRED`) must be the caller's;
    - one `CONNECT host:port` in HTTP/1.0 or 1.1, a request line in visible ASCII, a header of at most 8 KiB, all read within one header timeout;
    - the target must be on the caller's allowlist or be one of its named private destinations, decided before any lookup;
    - one lookup of the absolute name, then a check of every address returned (one refused address refuses the name), with a named destination's address also required to lie in its range and in RFC 1918 or unique local space;
    - the host budget;
    - a dial of exactly the checked addresses, IPv6 and IPv4 interleaved, the next one started every 250 ms while earlier ones are pending, all under one deadline;
    - the tunnel, closed when idle and at its maximum lifetime.

    The accept loop survives `EMFILE`, `ENFILE` and `ECONNABORTED` with a 100 ms back-off. The name is never resolved again for a tunnel. Each decision is logged on one line; a target off the caller's allowlist is logged as its length and a hash, never by name. Resolver and dialer are traits, so the integration tests can script lookups, black-hole addresses and record dialled addresses.
- `src/bin/egress-proxy.rs`: the proxy binary.
- `src/bin/egress-resolver.rs`: a scripted UDP DNS server (standard library only). Its zone gives fixed answers, and `rebind` names answer a public address to the first A query and an internal one to every later query. Every query is logged, which `run.sh` reads to show what the proxy resolved and what it never asked for.
- `src/bin/egress-probe.rs`: a protocol-level client (standard library only): CONNECT over the Unix socket followed by plain HTTP inside the tunnel, raw request bytes, direct TCP, a direct DNS query, a loopback canary listener, and `hold`, which keeps N tunnels open. The fake upstreams answer plain HTTP on their TLS port with `upstream=<name>` (nginx error 497), so a check knows which server it reached.
- Tests: 43 (19 unit, 21 integration in `tests/proxy.rs` with a scripted resolver and a recording dialer, 3 doc tests). The address tests iterate the refused tables and check the first and last address of each prefix, plus the IPv4-mapped, NAT64 and 6to4 forms of both ends of every IPv4 entry.
- `Dockerfile`: the cargo gates image, `rust:1.99-trixie` pinned by digest `sha256:e259494b14672950a909b4c54527e19d29cae6ebf980672114c8bb85e5594e4a`, plus clippy and rustfmt.
- `compose/`: the runtime image (multi-stage: the same Rust image builds the binaries with `--features test-network`; `debian:trixie-slim` pinned by digest `sha256:a29215f6a35e51e22adffa17f89e9d2ef06214e64a2bad10d765c46aea49f11f` runs them, with the Debian packages `systemd`, `dbus`, `curl`, `socat`, `nginx-light`, `python3`, `openssl` and `iproute2`), the test CA and leaf certificates generated at image build, the proxy configuration, the zone, the nginx configurations, a standard library websocket backend, and `compose.yaml`.
- Test network (`compose.yaml`), two Docker networks, both `internal: true`, so nothing reaches the real internet:
  - `internet`, `203.0.113.0/24` and `2001:db8:113::/64` (documentation ranges stand for the public internet, because Docker offers no globally routable addresses): the scripted resolver (`.53`), the proxy (`.2`), the allowed upstream (`.10`: HTTP/1.1, HTTP/2 and HTTP/3, redirects, a websocket, a 64 MiB file), the forbidden upstream (`.11`), and the internal target's second address `.20`, standing for the household's public address.
  - `lan`, `10.77.0.0/24` and `fd00:77::/64`: the proxy (`.2`) and the internal target (`.10`, ports 443 and 8443, the latter standing for a named private destination such as a push server).
  - `client`: `network_mode: none`, so loopback only. It runs curl behind `socat` forwarders on `127.0.0.1:3128` (as uid 2001, to `plugin-a.sock`) and `127.0.0.1:3129` (as uid 2002, to `plugin-b.sock`, the caller with `sni-check`): the forwarder shape of D115, where the proxy sees the forwarder's uid. Two more forwarders, on `127.0.0.1:4443` (plugin-a, to `allowed.test:443`) and `127.0.0.1:4444` (plugin-b, to `other.test:443`), relay into a fixed CONNECT tunnel, so a TLS client can send any SNI over it.
  - `sandbox`: systemd 257 as PID 1 (privileged, private cgroup namespace) on both networks, so a transient unit with `IPAddressDeny=any` or `RestrictAddressFamilies=AF_UNIX` runs next to a control unit with full routes.
  - The proxy container also runs loopback canaries on `127.0.0.1:8443` and `[::1]:8443`, and resolves only through the scripted resolver, with a search list (`corp.test`) and `ndots:5` that a relative lookup would apply.
- `run.sh`:
  - runs the cargo gates in the cargo image (named volumes `vilicus-egress-filter-target` and `vilicus-cargo-registry`): fmt, clippy with and without the `test-network` feature, the release-build refusal of `documentation-ranges-public`, and the tests; it fails when a test is ignored or the number of passing tests differs from `EXPECTED_TESTS` (43);
  - builds and starts the compose project `vilicus-e14`, waits for readiness, and prints one `PASS` or `FAIL` line per check;
  - ends with `RESULT PASS` or `RESULT FAIL`, exits non-zero on any failure, and removes the compose project and its volume on exit.

**Decision tasks.** The story names none explicitly. Four choices the spike had to make are settled with the recommended answer and proposed below (update 2):
- Per-host budgets count tunnels, not requests (finding 4). Recommended because the proxy cannot see requests without TLS interception, which the design excludes. What it gives up: inside a tunnel, a plugin's request rate to an allowlisted host is unbounded by the proxy, limited only by the tunnel lifetime and idle timeout; the trusted fetcher and the Core egress mode open one tunnel per request, so their budgets do count requests.
- A named private destination stores a private address range as well as a host and a port (finding 7). Recommended because it keeps a rebinding name from redirecting the Core's exception to another LAN host. What it gives up: a destination whose address moves outside its range must be named again.
- The AC3 fallback (per-plugin IP ranges) was evaluated against the one bypass found, domain fronting (finding 2), and found ineffective: the tenants of a shared front end share its addresses. It is not adopted. The candidate mitigation for Story 5.5 is the SNI check, implemented here per caller: SNI must equal the CONNECT host and Encrypted Client Hello is refused on the first ClientHello after the 200. It closes SNI-based fronting only; Host-header fronting stays a named risk.
- HTTP/1.0 CONNECT stays accepted next to HTTP/1.1, and the proposed spine text says so (finding 12).

**Findings.**

1. **No bypass of the proxy's own controls.** Every attempt on the story's list was refused or reached only the allowlisted address: IP literals (IPv4, IPv6, IPv4-mapped, decimal, hexadecimal), alternate ports, a trailing dot, userinfo, absolute-form HTTP, HTTP/2 prior knowledge, an h2c upgrade, a CONNECT-UDP upgrade, HTTP/2 as the CONNECT version, a control byte in the request line, a second request after a refusal, DoH by name and by IP literal, a websocket to a forbidden host, redirects to a forbidden host and to an IP literal, other callers' entries and other callers' sockets. Twenty-one allowlisted names resolving to internal forms were refused at connect time. Seven of those addresses have a host on the test network (`10.77.0.10`, `fd00:77::10`, `::ffff:10.77.0.10`, `127.0.0.1`, `::1`, `0.0.0.0` and the household address `203.0.113.20`), and each was shown reachable from the proxy's own namespace, so those refusals come from the check, not from routing. The other refused addresses (link-local, CGNAT, multicast, benchmarking, NAT64, 6to4, Teredo) have no host here; the refusal reason, not reachability, is the evidence.
2. **Domain fronting is a bypass of the hostname allowlist.** The proxy controls which address is reached, not which service answers there. `Host: forbidden.test` inside a tunnel to `allowed.test`, a `Host` header on the CONNECT request itself, and SNI `forbidden.test` over a tunnel to `allowed.test` all reached the allowed upstream with the forbidden name (`upstream=allowed host=forbidden.test`, `sni=forbidden.test`). On a shared front end (a CDN or a multi-tenant provider) that routes by SNI or Host, an allowlisted hostname therefore carries requests to a service that is not on the allowlist. The E14 fallback, per-plugin IP ranges, does not close it, since the tenants share addresses. The SNI check closes the SNI half: with `sni-check`, a ClientHello naming another host, one offering Encrypted Client Hello, one without SNI, or a non-TLS first record closes the tunnel before any byte reaches the upstream (`sni.*`, `test.sni_check_passes_a_matching_client_hello_and_closes_on_anything_else`). The Host half remains: with a matching SNI, `Host: forbidden.test` still reached the upstream (`sni.host_header_fronting_not_detected`); closing it needs TLS interception, which the design excludes. Most large front ends now refuse a Host that differs from SNI, but Vilicus cannot rely on that (not tested here). Proposed as a named risk (update 4).
3. **QUIC cannot leave without the proxy.** CONNECT tunnels are TCP. curl refuses `--http3-only` over an HTTP proxy ("HTTP/3 is not supported over an HTTP proxy") and, with `--http3`, falls back to HTTP/2 inside the tunnel. A direct HTTP/3 request works from an unrestricted unit (`proto=HTTP/3.0`, the control) and fails under `IPAddressDeny=any` (the UDP send returns `EPERM`), under `RestrictAddressFamilies=AF_UNIX`, and from the client namespace with no network.
4. **The proxy sees tunnels, not requests.** With HTTP/1.1 keep-alive and HTTP/2 multiplexing inside an encrypted tunnel, the proxy cannot count requests. The budget therefore counts tunnels per sliding window, per hostname whatever the port; every host has one (its own or the default), it is taken only after the address check, and a reserve is kept for the Core and the backup caller, so plugins cannot starve them (`budget.*`: 5 tunnels for two plugins, then 429 for both, then the Core's reserved tunnel, then 429 for the Core). The request rate inside one tunnel stays unbounded; the tunnel lifetime and idle timeout bound how long one tunnel lasts. PRD FR-105 says "request budgets"; update 2 states what the proxy can enforce.
5. **A refused name never reaches the resolver nor the log.** The allowlist decision precedes the lookup, so the resolver log shows no query for `forbidden.test`, `dns.google`, `cloudflare-dns.com` or `exfil-secret-payload.test`, although callers asked for each; and the proxy log shows those targets only as `redacted(len=..,hash=..)`. The hash is the standard library's keyed SipHash with a key drawn per process: enough to correlate refusals within one run, not a commitment across restarts.
6. **Rebinding is defeated by one lookup per tunnel.** A name that answered a public address to an advisory lookup and an internal one to the proxy was refused at connect time. A name that answered the public address to the proxy was dialled at that address and resolved once by the proxy (resolver log), although it answered the internal address to the next lookup. An answer mixing a public and an internal address is refused whole.
7. **`0.0.0.0` reaches the proxy host's own listeners.** The control connected from the proxy namespace to `0.0.0.0:8443` and reached the loopback canary, so refusing the unspecified address, which AD-16 already requires, is necessary. Named private destinations are the one place the proxy dials a private address; the spike pins each to a range and checks again at connect time that the address lies in RFC 1918 or unique local space and outside the blocked list, so neither a rebinding name nor a configuration that bypassed the load check reaches loopback.
8. **The system resolver is not neutral.** `getaddrinfo` consults the hosts file and the name service modules before DNS, and applies the search list to a relative name. The proxy resolves the absolute name (`host.`), and the resolver log shows that no query carried the `corp.test` search suffix although `ndots:5` would have applied it to every name. The hosts file and the name service modules still answer first: the container's own hostname resolves to the proxy's own address. The address check makes this safe here, but Story 5.5 should make the proxy query only its configured DNS servers.
9. **`IPAddressDeny=any` drops, it does not reject.** A direct TCP connect under it times out (`TimedOut` after the probe's 3 s) rather than failing fast; `RestrictAddressFamilies=AF_UNIX` fails at socket creation. A plugin that ignores its proxy setting hangs until its own timeout, and the negative connection test of AD-16 must treat a timeout as enforcement.
10. **Special-purpose ranges beyond AD-16's list.** The prototype also refuses `192.0.0.0/24`, `192.88.99.0/24`, `198.18.0.0/15`, `240.0.0.0/4` with the broadcast address, `64:ff9b:1::/48`, `100::/64`, `2001::/23` (Teredo, benchmarking, ORCHID), site-local, everything outside `2000::/3`, 6to4 and NAT64 forms of internal addresses (network-specific NAT64 prefixes included), and the documentation ranges, which only a `test-network` build may unblock. A static `blocked` list cannot follow a dynamic WAN IPv4 address or rotating IPv6 addresses: the product must block the household's whole delegated IPv6 prefix and track the host's and the WAN addresses at run time (update 3).
11. **One caller cannot take the proxy down.** Each caller socket has its own connection limit (64 here): with plugin-a holding 64 tunnels, its next connection got 503 while plugin-b and the Core were served, and plugin-a recovered when the tunnels closed (`limit.*`). Tunnels close when idle and at their maximum lifetime, a dial phase has one deadline over all addresses, and a black-holed IPv6 address does not stall the IPv4 one (`test.a_black_holed_address_does_not_stall_the_next_one`, `test.one_deadline_bounds_every_dial`). The accept loop treats `EMFILE`, `ENFILE` and `ECONNABORTED` as recoverable; that path is code only, not exercised by a test. A lookup that times out is abandoned by the proxy but keeps its blocking thread until `getaddrinfo` returns: Story 5.5 needs an asynchronous resolver with in-flight cancellation.
12. **HTTP/1.0 CONNECT is in real use.** `socat`'s `PROXY` address sends `CONNECT host:port HTTP/1.0`; a proxy limited to HTTP/1.1 broke the relays of the test network. The prototype accepts HTTP/1.0 and HTTP/1.1, refuses every other version, and the proposed spine text names both (update 3).

**Not run here.**
- The Debian 13 VM (AD-33): the `IPAddressDeny=any` checks ran under systemd 257 in a privileged container on the WSL2 kernel. Procedure for Story 5.5: in the Debian 13 VM, run each `ac3.*` command of `run.sh` as `systemd-run --wait --pipe --property=User=<caller uid> --property=IPAddressDeny=any [--property=RestrictAddressFamilies=AF_UNIX] egress-probe ...` against a reachable public address, a LAN address, a loopback canary and a DNS server, each next to an unrestricted control unit; every restricted attempt must fail and every control succeed.
- File descriptor exhaustion: procedure for Story 5.5: run the proxy with `LimitNOFILE=64`, open connections until `accept` fails with `EMFILE`, release them, and check that the same listener then answers a new connection.
- A real CDN front end for finding 2: not reproduced; the mechanism (the proxy sees SNI only with `sni-check`, and never the Host header) is shown on the test network.
- Encrypted Client Hello end to end: curl 8.14.1 on Debian 13 (OpenSSL 3.5.7) cannot send ECH; the refusal is covered by the parser and in-process tests with a synthetic ClientHello.
- `SO_PEERPIDFD` unit identification: Story 5.3.

2. `doc/decisions.md`: add a new decision record, amending D105, and its row in the table. Text: "Amends D105. Context: E14 (Story 1.12) found that the egress proxy sees tunnels, not requests, so the per-host request budgets of PRD FR-105 cannot be counted inside a CONNECT tunnel; that a named private destination given by host and port alone lets a rebinding name redirect the Core's exception to another private host; that the refused address set of spine AD-16 left out special-purpose ranges; and that domain fronting on a shared front end bypasses the hostname allowlist. Decision: per-host budgets count tunnels per sliding window, per hostname, shared by every caller; every host has a budget, its own or a default one; part of each is reserved for the Core and the backup caller; the budget is taken after the address check. Inside a tunnel, a plugin's request rate is not bounded by the proxy, only by the tunnel lifetime and idle timeout; the trusted fetcher and the Core egress mode open one tunnel per request, so their budgets count requests. A named private destination records a host, a port and the private range (RFC 1918 or unique local) that its resolved addresses must fall in, checked at connect time. The allowlist decision is taken before any lookup, and one refused address refuses the whole name. IPv6 is accepted only inside global unicast, and every IANA special-purpose range that is not globally reachable is refused. The E14 fallback, per-plugin IP ranges, was evaluated and is not adopted: it does not close domain fronting, because the tenants of a front end share its addresses. Instead, the proxy checks the first TLS ClientHello of each tunnel of a caller that reaches a shared front end: its SNI must equal the CONNECT host and Encrypted Client Hello is refused; fronting by the HTTP Host header stays a named risk. Consequences: a plugin that reuses one tunnel for many requests counts once per tunnel; naming a private destination asks for its range; a client that cannot send SNI cannot use a checked caller's tunnels."
