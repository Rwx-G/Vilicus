# Story 3.8: In-partition events and outbox delivery

As a project maintainer,
I want modules to exchange typed, versioned events through the Core with stamped emitters and outbox delivery,
So that cross-module consistency never needs a cross-file transaction and a failing consumer never blocks a partition.

**Acceptance Criteria:**

**AC1 (FR-24, AD-29)**
**Given** a module declaring a topic `<module>.<entity>.<past_verb>`
**When** it emits an event
**Then** the Core stamps the real emitter and a payload version, a claim of another emitter is rejected, and per-topic ACLs decide which consumers receive it
**And** consumers accept every earlier payload version.

**AC2 (AD-10, D20)**
**Given** a change and its outbox row
**When** the module commits
**Then** both are in one transaction in one file
**And** after a simulated crash the undelivered rows are delivered once the partition unlocks.

**AC3 (FR-24, AD-29)**
**Given** events in a source file's outbox
**When** the Core delivers them
**Then** delivery happens only after the file's migrations, at least once, in commit order per source file and consumer
**And** a consumer processing the same event twice produces one effect through `_consumed`.

**AC4 (FR-24, AD-29)**
**Given** a consumer that fails the same event 5 times
**When** the fifth delivery fails
**Then** the event moves to `_dead_letter`, a typed instance admin alert is returned and later events proceed
**And** the consumer tolerates the gap in order.

**AC5 (AD-10)**
**Given** an outbox row requesting a cross-module link
**When** the Core delivers it
**Then** the Core registers the link in the link table of the partition that owns the data, never in the module's transaction, and no link crosses partitions.

**AC6 (AD-27, D107, DC-62)**
**Given** a consumer that writes in reaction to an event
**When** it writes
**Then** the write carries principal `Event`, the emitting call's id, its author and the most restrictive taint of its inputs, and is at most tier 1
**And** in V0.1 no event is delivered outside its source partition (test with two partitions).

**Decisions and why** (drafted decision and document texts under Open points)
- *The real emitter* (AC1, D20): a module emits only topics its own declaration holds, and a declared topic's name starts with the module's name (`ForeignTopic` at build time); at run time a topic of another module is `WriteError::ForeignTopic`, an undeclared one of its own `UnknownTopic`. The emitter is then the module whose call emits and whose file holds the row, which only the Core writes, so no emitter column is stored: it could only repeat the file's module. The consumer receives it in `Event::emitter`.
- *The payload version* (AC1, AD-29): `Topic::version`, from 1, stamped on the row at emission from the emitting module's declaration; the row keeps it across upgrades and the consumer receives the stored version. "Consumers accept every earlier version" is a rule for consumer code; the Core's part is to deliver every stored version, unchanged and in order, which the tests check with a row written under an earlier declaration.
- *The access list per topic* (AC1, D20): each `Topic` names the modules whose consumers may receive it; the registry refuses, at build time, a consumer the list does not name, and the receivers of an event are the consumer of the topic of each module the list names, in its order. The list is the emitter's: a module decides who reads its events. A module has at most one consumer per topic, so a delivery to a module is one call.
- *What an event is about*: a record the emitting call inserted, updated or deleted (`UnchangedRecord` otherwise), so every emitting call has a journal row and a repeated call is deduplicated by it (AD-26) without counting events among what a call wrote; and so AC2's "a change and its outbox row" always holds. The event carries the provenance of that record as the call leaves it (for a delete, as read just before it), without free text, raised to the call's own floor: its session taint, the taint an AI or plugin session consumed, and `external` for a plugin or an adapter (D20, "plugin events always `external`"). With it, the emitting call's author and member.
- *The consumer's call* (AC6, AD-27, D147): principal `Event`; `call_id` the emitting call's id; `source` `event(<event id>)`; authority unapproved, with the emitting call's author as author and its member as the member it acts for, so a record another member authored reads as `member` for it and stores `external` (AD-7); session taint the event's label; the event's snapshot as its implicit input, which every write counts and the journal records as implicit. The deduplication key (D148) is then unique per event and consumer module: the source names the event, and a module has one consumer per topic. `source` carries the event id rather than the call id of the conventions (`event(call id)`): `Source::Event` holds a UUIDv7, the emitting call's id may be the name-based id of a rule (AD-39), and that id is already the call id of every journal row of the consumer's call.
- *At most tier 1* (AC6, D20): a consumer's call requests no outbound effect (tier 2 under I13 unless an exception class, which a consumer does not declare) and emits no event (no cascade, so no cycle between modules); both are `NotInConsumer`, which fails the delivery. Its record writes and link requests stay in its own file and partition. Gives up: a consumer that notifies through an effect, or that chains events, waits for a decision.
- *Delivery and its record* (AC2, AC3, AD-10): the consumer's call commits in the consumer's file with its `_consumed` row; the source file records the delivery afterwards, in a transaction of its own, since the two are two files. A crash between them leaves the event pending in the source, and the next pass delivers it again: the consumer's call is answered by the journal (it wrote) or by `_consumed` (it wrote nothing), and runs nothing, so delivery is at least once and the effect once. An event is closed `delivered` once each receiver has it delivered or dead-lettered.
- *Order* (AC3, AD-29): per source file and consumer. The pass reads the pending rows in `seq` order; an event a consumer did not receive in the pass (a failure, a file not ready) holds back that consumer's later events, and only that consumer's. One attempt per event and consumer per pass; scheduling passes, and any backoff, is the caller's.
- *Not ready* (AD-54): `ConsumerFiles::ready` returns no handle (the partition locked, the module faulted, deactivated, migrating), or the file is not at the code's two versions: the event stays, and no attempt is counted.
- *Failures and dead letters* (AC4): a refusal of the Core, an error of the consumer's code, a panic (caught around the call, which rolls back as it unwinds) and an event whose stored provenance does not decode each count one attempt. The fifth moves the event to the source file's `_dead_letter` in the transaction that records it, returns `InstanceAdminAlert::DeadLetter` (file, dead letter, event, topic, consumer), and the consumer's later events proceed in the same pass, so it sees a gap. A malformed event fails rather than stops the pass, which would block the outbox forever (AD-29, Prevents).
- *Migrations* (AC3): the pass refuses a source file whose Core or module track is not at the code's version (`DeliveryError::NotMigrated`), before reading anything.
- *Links* (AC5, AD-10): a link request names a record the call inserted or updated, another module and that module's record; it commits with the call. The pass registers it in the partition's link table through the `LinkTable` port, outside any transaction, once it finds the target in one of the target module's tables in its file of the same partition, and closes the request; a target absent there (a record of another partition included) or a module not registered is refused, closed `refused`, with `InstanceAdminAlert::LinkRefused`; a target file not ready keeps the request pending. Registration is at least once, by the request's id.
- *Partitions* (AC6, D107): the files a pass is offered must be of the source file's partition and of the module asked for; otherwise the pass stops with `CrossPartition` or `WrongModule`, fail closed, before the consumer's code runs.
- *Retention* (AD-26, Story 3.6's open point): `purge_expired_outbox` deletes, 30 days after their creation, closed events and link requests and `done` effect intents, with the deliveries of those events, under `secure_delete` = ON and a TRUNCATE checkpoint, as the journal's purge does; an event that still has a dead letter is kept for its replay, and `pending`, `failed` and `unknown` intents stay, since the Core still performs, retries or reports them. A deleted `done` intent no longer blocks a repeat of its key (D148).
- *Core migration 1 edited*: no file is released, as Story 3.7 decided for `_migrations`; the frozen hash follows.

**Deviations**
- *AC1, "the Core stamps the real emitter"*: by the file and the topic, with no emitter column (Decisions). *"consumers accept every earlier payload version"*: the Core delivers every stored version as written; whether a consumer's code reads it is that code's (Decisions).
- *AC2, "after a simulated crash the undelivered rows are delivered once the partition unlocks"*: the crash is simulated by closing every handle before any delivery, and the unlock by opening the files again; no unlock path exists before Epic 9, and a locked partition is a `ConsumerFiles` that offers no file.
- *AC3, "through `_consumed`"*: a consumer's call that wrote records is answered by the journal's deduplication first, since its key repeats; `_consumed` answers one that wrote nothing. Both run nothing a second time.
- *AC4, "a typed instance admin alert is returned"*: returned in the report; sending it is the alert path's (Epic 8). A panicking consumer counts as a failed delivery; marking its module faulted (AD-9, AD-54) is Story 3.9's.
- *AC5, "registers the link in the link table of the partition that owns the data"*: through the `LinkTable` port; `core.<partition>.db`, which holds that table (`doc/architecture.md` section 5.1), is built by no story yet (Open points).
- *AC6, "the write carries ... the emitting call's id"*: as the consumer's `call_id`; the `source` is `event(<event id>)`, not `event(<call id>)` (Decisions). *"at most tier 1"*: a consumer's call requests no effect and emits no event; a record write has no tier of its own outside a tool.
