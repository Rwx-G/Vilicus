# Story 4.1: Crypto suite and versioned wrappers

As a project maintainer,
I want one crypto suite in `vilicus-crypto` with versioned wrappers and key types that cannot leak,
So that every key the Core holds is wrapped with audited primitives and stays inside the kernel.

**Acceptance Criteria:**

**AC1 (AD-18, D28)**
**Given** the `vilicus-crypto` crate
**When** a key is wrapped or a key is derived
**Then** wrapping uses AES-256-GCM with a random 96-bit nonce and derivation uses HKDF-SHA-256, both from aws-lc-rs
**And** no cryptographic primitive is implemented in Vilicus code (a review checklist item and a dependency check list the only primitive sources)

**AC2 (AD-18)**
**Given** any wrapper produced by the crate
**When** it is serialized
**Then** it carries a format version, the algorithm identifiers (KDF, KEK derivation, AEAD), its parameters, salt or credential reference, nonce, ciphertext, tag, creation time and wrapper id, as `doc/key-management.md` section 9 lists
**And** a wrapper with an unknown version or algorithm identifier, or a lower version than the Core accepts, is refused instead of being downgraded

**AC3 (AD-4, FR-13)**
**Given** the key types defined in `vilicus-crypto`
**When** the crate is compiled
**Then** no key type implements `Clone` or `Debug`, and every key type zeroizes its buffer on drop (unit test inspects the buffer after drop through a test-only hook)
**And** every key type is defined in `vilicus-crypto` and nowhere else

**AC4 (FR-13, AD-4)**
**Given** a module crate that tries to name a `vilicus-crypto` key type
**When** the workspace builds
**Then** a compile-fail test shows the type is unreachable, because `vilicus-crypto` is a dependency of `vilicus-core` only (crate graph of AD-3)

**AC5 (NFR-7, AD-18)**
**Given** the crate's documentation
**When** it describes the suite
**Then** it names aws-lc-rs as the source of AES-GCM and HKDF and states the version 1 identifiers, and claims nothing about the transport beyond D27

**AC6 (D28, D120, D123, D129)**
**Given** the primitive source list of AC1
**When** the dependency check runs
**Then** it lists aws-lc-rs, `hpke` 0.13.0 with the primitive crates it depends on (D120), `argon2` 0.6.0 and `blake2` without the `parallel` feature (D129), and `opaque-ke` 4.0.1 (D123), each with its recorded exception to D28
**And** the crate documentation states that inside HPKE the `hpke` crate brings its own primitive crates, and never calls `hpke`, `argon2` or `opaque-ke` audited at its pinned version.

**AC7 (D131, AD-4)**
**Given** an AEAD or HKDF operation with a key held by the crate
**When** it runs
**Then** the aws-lc-rs objects (`LessSafeKey`, `Prk`) are built from the key slot for that one operation and dropped before it returns, because a live object keeps the key, the HKDF input and the GHASH key on the unlocked heap (Story 1.10, `*-asis-key-object-on-unlocked-heap`)
**And** key bytes are never held in heap memory the Core does not wipe or lock.

**Decisions and why** (drafted decision text under Open points)
- *What the KDF and KEK derivation identifiers name* (section 9 lists both without defining them): the KDF names how a secret a person holds was stretched (none, or Argon2id with its costs); the KEK derivation names how the KEK was obtained from that output or from a parent key (as is, or HKDF-SHA-256 under a versioned label). A passphrase KEK is `Argon2id` + `Direct` (D128: Argon2id gives the 32-byte KEK), an enrollment key wrap of key management section 2 is `None` + `HkdfSha256`. The crate records them; the caller that derived the KEK chooses them.
- *Identifiers and encoding*: one `u16` per field, numbered from 0x0001 so that zeroed bytes name nothing; a fixed big-endian layout, not canonical CBOR, because `vilicus-crypto` depends on `vilicus-types` only (AD-3) and the bytes are stored, never exchanged. Version 1 wraps 32-byte keys only, so the ciphertext has no length field; another key length is another format version. The layout is stated once, in the crate documentation, and `the_encoding_is_the_documented_layout` reads that table and compares it with the encoder.
- *Additional data*: every field before the ciphertext, then the purpose of the wrap (a `Label` and its end byte), then a context the caller gives, which may not be empty. Section 2 asks the enrollment key wrap to bind its format version, algorithm identifier, HK version and member identifier; the header carries the first two and the context the others. A wrapper whose header is edited, or opened for another purpose or another record, does not open (review, finding 2: the member DEK wraps both the member private key and the personal inbox private key for one member, which the purpose tells apart). The purpose is bound, not stored, so the layout table is unchanged; an empty context is refused because two wrappers of one purpose under one KEK would otherwise open in each other's place.
- *Downgrade*: the Core reads versions from `OLDEST_ACCEPTED_FORMAT_VERSION` to `FORMAT_VERSION`; older is refused as `OlderThanAccepted`, newer as `UnknownVersion`, and an identifier the version does not define as unknown; nothing is read another way. The Argon2 version is part of the KDF's identity: anything but 0x13 is refused. The Argon2id costs are carried, not judged: their floor and ceiling are Story 4.4's (D128).
- *One key type*: `SymmetricKey` is every 256-bit key of the suite for now. Role-specific types (DEK, HK, file key) belong to the hierarchy of Story 4.3; they wrap the same `Slot`.
- *Key bytes behind closures*: no public accessor exists; `Slot::with_bytes` and `with_bytes_mut` are crate-private, so Story 4.2 can take each slot from the locked pool and put its guard around these closures without changing a signature outside the crate (AD-4, D131, Story 4.2 AC8).
- *"Defined in `vilicus-crypto` and nowhere else"* (AC3): a key type must wipe its buffer on drop (AD-4); where unsafe code is forbidden, `zeroize` is the one dependency of the Stack that does it reliably, since volatile writes need `unsafe`. `[restricted.zeroize]` lets only `vilicus-crypto` and `vilicus-storage` (its SQLCipher key text, a buffer and not a type) declare it, and, since the review (finding 5), `[restricted.<source>]` lets only `vilicus-crypto` link aws-lc-rs, `hpke`, `argon2`, `opaque-ke` and `zxcvbn`, with aws-lc-rs's two test users named as dev-dependencies, so no other crate can run a key operation on a key type of its own. It is a proxy, stated as one: the crates where D140 allows unsafe code could still write volatile wipes by hand, which review sees.
- *Primitive sources* (AC1, AC6): `ci/primitive_sources.toml` lists each source with its record; a source or a `[not_primitive]` entry may be absent from the tree, since the list also records what is approved for code to come (`hpke`, `argon2`, `opaque-ke`, `base64ct`); a pin and a forbidden feature are checked once the package is in the tree. Which packages are cryptographic is read from their publishers' crates.io classification (category `cryptography`, keyword `crypto` or `cryptography`); `aws-lc-sys` declares neither and is listed by name; `zeroize` and `base64ct` are classified and listed under `[not_primitive]`. `hpke` and `argon2` carry `brings_primitives`: a classified package is covered by one of them when every path from a workspace member to it, by package id, goes through it (D120 for `hpke`; for `argon2`, the scope the D153 draft records as an amendment of D129, so `blake2` is covered through `argon2` and is no longer a source of its own). Only aws-lc-rs and `aws-lc-sys` go without an exception; every exception a source names is one of those D28's status lists in its "exceptions in" clause, or a decision the table records as amending one (D120 amends D61), and every exception of D28 has a source, so the list and the decision table cannot drift apart.
- *The compile-fail test of AC4*: `compile_fail` doc tests with their error codes, as Stories 2.4 and 3.2 to 3.4 do; trybuild is not a dependency. They sit in the reference module, the one module crate of the workspace: naming `vilicus_crypto::SymmetricKey` fails with E0433 (an unlinked crate, not an unknown type, which would be E0412), and `extern crate vilicus_crypto` with E0463. A probe on a copy of the tree, after a workspace build had put `vilicus-crypto`'s rlibs in `target/debug/deps`, showed that a module crate's own build also refuses `extern crate vilicus_crypto` (E0463): the search path does not reach it.
- *AC7*: shown on the source, not on memory. `aws_lc.rs` alone names aws-lc-rs; there every function is `#[inline(never)]`, no signature names an aws-lc-rs key object or an `impl` type, and no item outside a function body names one. `key_objects_live_for_one_operation` checks this and `the_key_object_check_refuses_each_way_out` shows the check refusing each way out. The memory inspection that shows no copy after drop is Story 4.2's regression test (AC10), derived from E16.

**Deviations**
- *AC1, "a dependency check list the only primitive sources"*: the check sees the packages their publishers classify as cryptographic; a primitive crate that declares no such category or keyword is caught by the review checklist item, which says so.
- *AC3, "inspects the buffer after drop"*: the hook copies the buffer inside `Drop`, after the wipe and before the allocation is freed; reading the allocation once freed would be undefined behaviour in the test. *"nowhere else"*: held by the `zeroize` rule above, a proxy.
- *AC6*: `hpke`, `argon2` and `opaque-ke` are not dependencies: they are listed with their records, and their pins and `argon2`'s forbidden `parallel` feature are checked from the day they enter the tree. `blake2` is listed inside `argon2`'s entry, covered only through `argon2` (review, finding 4), not as a source of its own. The crate documentation states them as sources to come.
- *AC7, "key bytes are never held in heap memory the Core does not wipe or lock"*: the crate's own buffers are wiped on drop, not yet locked (Story 4.2); the seal works on a crate buffer, so a failed seal leaves no plaintext copy; during one operation aws-lc-rs holds the key schedule and the HKDF input in its own allocations; with objects built and dropped per operation, Story 1.10 found the key only in the pool once the operation had returned (`*-core-no-key-object-at-rest`).

- *Story 4.2* (locked memory): `Slot` is the one buffer type, built by `Slot::zeroed()` and reached through `with_bytes` and `with_bytes_mut`. Backing it with a slot of the pool makes `Slot::zeroed()` fallible (pool exhausted), a crate-private change; every public constructor already returns a `Result`, and `CryptoError` gains a variant (it is not `#[non_exhaustive]`; no crate matches on it yet). The guard of AC8 (stack scrub, `vzeroall`) goes around those closures and the `#[inline(never)]` functions of `aws_lc.rs`. A wrap uses one transient slot for the seal, an unwrap and a derivation one slot for the new key: the planned slot count's transient slots. The test hook `key::wiped` and the AC7 shape test stay; the memory inspection of 4.2 AC10 adds the evidence they do not give. Copies made by `copy_from_slice` into the seal buffer may leave key bytes in registers and on the stack until the scrub.
- *Story 4.3* (key hierarchy): role-specific key types (DEK, HK, partition roots, file keys) over `Slot`; a public closure accessor, under 4.2's guard, to key a SQLCipher file, replacing the `&[u8; 32]` `vilicus-storage` takes today; a constructor that reads the instance key from its systemd credential into a slot and wipes the source; the context layout of each label (fixed widths, one variable-length field) and the `wrappers.db` record set.
- *Story 4.4* (passphrase KEK): `Kdf::Argon2id` carries the costs and `from_bytes` reads any value (an empty salt, m = `u32::MAX`, t = 0 and p = 0 parse); the floor and ceiling checks of D128, and the 16-byte salt, are validated inside the one derivation entry point of `vilicus-crypto` before the derivation is queued, not in each caller (review, deferred item). When `argon2` enters `Cargo.lock`, the primitive source check holds it to 0.6.0 without `parallel` and covers `blake2` and the crates it brings through it. The passphrase-strength library of D113 is restricted to `vilicus-crypto` under the name `zxcvbn`, the candidate the review named; choosing another library, or placing the check in `vilicus-core`, changes `[restricted.zxcvbn]` with its reason.
- *FR-8 and FR-16 stories* (`hpke`, `opaque-ke`): when `hpke` enters, its classified dependencies reached only through it are printed with it and covered; `opaque-ke` has no `brings_primitives` because D123 does not say its exception covers the crates it depends on, so its classified dependencies not reached only through `hpke` (for example `voprf`) need an entry or a decision then. By owner decision the `hpke-rs` cross-test oracle lives in a separate crate outside the workspace, so this check never sees it; a later oracle that enters the workspace as a dev-dependency needs an entry with its record.
- *Derivations that are not key to key* (stories 4.3 to 4.5 and the enrollment and passkey stories): `derive_key` takes a `SymmetricKey` and no salt. HKDF with a salt, or over input that is not a key of the crate (the enrollment token, a PRF output with its credential salt, the printed recovery secret), needs an entry point of its own that takes that input into a slot and wipes the source, with its label.
- *Passkey wrappers* (after V0.1, E1, E2): a passkey KEK needs both a PRF salt and a credential id, and a version 1 wrapper holds one salt or credential reference; that wrapper is a new format version or a field of its own (D153's consequences).
