# Threat model

Status: design phase, no code yet. Revision 2. Written to be attacked: every assumption below is a claim to challenge. Components are defined in [architecture.md](architecture.md) and the [architecture spine](architecture-spine.md); keys in [key-management.md](key-management.md); the assistant's rules in [ai-safety.md](ai-safety.md); requirements and accepted residual risks in [prd.md](prd.md) (section 8.2). Revision 2 aligns it with decisions D34 to D61, its 2026-10-16 update with D62 to D68, the revalidation of the same day with D69 to D86, later updates with D87 to D96 and D97 to D100, and the second revalidation with D101 to D115 ([decisions.md](decisions.md)). An update of 2026-10-17 adds threats T67 and T68 from the V0.1 spikes (D121, D134).

## 1. Scope

One Vilicus instance serves one household (one to several members). It stores sensitive personal data (finances, mail content, calendar, locations, children's information), holds credentials for external services, and hosts an AI assistant allowed to take actions on the household's behalf. From the home milestone it also drives the house's devices through device adapters and home rules, with every member locked (see D53, D57). It is reachable from the household's devices on the local network, from away through a WireGuard endpoint managed by Vilicus (see D60), and possibly from the Internet through another exposure the operator chooses. It exposes no API to outside AI assistants (see D49). After V0.1, scheduled tasks and playbooks act while nobody watches, and the researcher reads the open web through a trusted fetcher (see D62, D63, D65, D73). Backups run unattended to off-host S3-compatible object storage (see D85, D106).

Out of scope for this version: multi-tenant hosting, physical attacks on a running unlocked machine, adversaries who target the household specifically with state-level resources, CPU side channels. Physical access to the household display is in scope (T35).

| A3 | Malicious or compromised plugin | Runs inside the instance with the permissions it was granted; includes device adapters and messaging plugins |

| A10 | The operator | Misconfiguration, accidental exposure, weak passphrase |

## 4. Trust boundaries

1. Client (browser, app) to Gateway: untrusted network.
2. Gateway to Core: the Gateway is exposed, so it is lower trust than the Core and holds no keys. Before the native app, it serves the code of every browser confirmation, step-up and pairing (see D35); each step-up is bound to one action (see D71), and unlocking, disarming, opening and cutting infrastructure power are not offered at all (see D69).
3. Core to modules: modules are trusted code in the Core process; isolation is by data (own database, scoped handles), not by memory. Home rules run here, without a model and without a member key (see D57).
4. Core to AI processes and the alignment controller: untrusted by design. MCP is spoken only on this boundary (see D49).
5. Core to plugins: untrusted, separate sandboxed processes.
6. Instance to external services (mail, AI providers, stores, device vendor clouds): third parties, reached through the egress proxy.
7. Instance to disk and backups: at-rest boundary.
8. Paired native app to Core: the app pins the Core's public key; this channel carries tier 2 confirmations independent of the Gateway's honesty. Until the native app exists, tier 2 actions are not registered at all (see D46).
9. Core to device adapters and devices: adapters are plugins acting under their own principal with named grants of a USB device, a Unix socket, a namespace shared with a managed daemon, or a private address range with ports enforced per unit, never a loopback address grant (see D54, D115); devices also accept commands from sources Vilicus does not control.
10. Internet to the remote access endpoint: one UDP port forwarded on the router to a WireGuard interface owned by the host network configuration; a dedicated unit with network administration rights applies the peer list the Core sends (see D60).
11. Household display to Core: a paired device without a member, physically reachable by anyone in the house (see D55).
12. Secondary channel to Core: a messaging plugin reports a sender identity; only a binding proven by a challenge from the primary channel ties it to a member (see D42).
13. Researcher to the open web: the trusted fetcher, which runs no model and no page code, makes every request after the Core checks its URL, through the egress proxy in researcher egress mode (any public host, internal addresses blocked, per-host budgets); hostile pages are parsed only inside the sandboxed researcher or rendered by the researcher browser plugin, which hold no secret, no household data and no network (see D63, D73).
14. Core and AI processes to the local model runtime: a separate unit reached only over per-role Unix sockets, with no network, no cache shared across members or roles, and model files pinned by hash (see D83).
15. Instance to the off-host backup target: S3-compatible object storage with write-only or object-lock credentials receives backups encrypted to the backup public key, whose private key stays offline (see D85, D106).
16. Core to the Claude subscription connector: the unmodified Claude Code binary runs for one member in its own unit, untrusted like an AI process, one child per session, reaching the network only through a forwarder to the egress proxy (see D97, D110, D115).

## 5. Security assumptions

- Passphrases are reasonably strong; recovery secrets are stored offline and apart from devices.
- After unlock the key material is in the Core's memory: at-rest encryption protects against A6, not against A7. The system is **not zero-knowledge**. The unlock window keeps a member's key in memory after the web session ends (see D36).
- Audited cryptographic libraries are used; no custom protocols. The `hpke` crate is an exception, reviewed internally and never called audited (see D61).
- A paired native phone is not fully compromised at the time of a confirmation (otherwise only Protected Confirmation, where present, helps).
- The operator follows the exposure guidance; the default does not expose the instance to the Internet. Remote access through WireGuard forwards one UDP port that is silent to unauthenticated packets (see D60).
- The operator is usually one of the adults. Isolation between adults against the operator is a matter of policy, audit and friction, not a cryptographic guarantee (T38).
- The home partition is readable with the instance key: by root on the host, and by the thief of a disk from a host without a TPM (see D53). The secrets that let a device open the house are the exception: they are entered only at the host CLI and sealed to the TPM under PCR 7 plus a signed PCR 11 policy, a host without a TPM and unified kernel images cannot run such adapters, and they are not in backups (see D78, D108).
- The backup secret, generated by the Core, is kept offline; the host holds only the backup public key, so a backup can be written without it and read only with it (see D85). After V0.1, a module file opened by a delegation sub-key is readable the same way while the sub-key exists, and also by the instance admin with a backup and its backup secret; the household accepts this internal risk (see D62).
- Devices accept commands from sources other than Vilicus. Vilicus's tiers govern what goes through Vilicus, not what devices accept from elsewhere.
- Modules are reviewed code; the supply chain controls hold (A8).

## 7. Data flows to review first

1. Inbound mail to quarantined reader, to typed output, to planner, to proposal.
2. Tier 2 proposal to Core checks, to signed request, to native app, to signed confirmation, to execution and audit.
3. Bootstrap and pairing (bootstrap token, instance name and certificate before any passkey, enrollment token, PAKE-bound code for browsers, validation, delay) (see D76).
4. Unlock: PRF output or passphrase, KEK derivation, DEK in memory, unlock window.
5. Plugin to external service and back, through the egress proxy.
6. Recovery and household key rotation.
7. Backup on a timer, encrypted to the backup public key, to the off-host target; `vilicus backup verify`; restore and anchor reconciliation (see D85).
8. Device adapter report to the home module, to a home rule, to a command back through the adapter.
9. Household presence to a mode change or an alert pointing to the vendor's app before the native app, to a disarm proposal confirmed as tier 2 afterwards (see D69).
10. Secondary channel message to binding check, to tainted session, to a reply under the channel's ceiling.
11. Device pairing to a remote access peer, to the peer manager unit.
12. Member's question to the Core template stage, to the researcher, to the Core's URL check, to the trusted fetcher and the egress proxy in researcher egress mode, back to the researcher as bytes, to a report shown to the human (see D73).
13. Scheduled task trigger to a capability token limited by the tool policy, to a delegation sub-key when the owner is locked, to delivery in the primary channel.
14. Disclosure grant to the registered derivation function in the owner's partition, to the recipient's inbox, to audit without the value.
15. Capability token issuance to the provider binding by data type, to the local model runtime or a remote connector, through the dietary filter for remote meal planning (see D80, D83).
16. Upgrade to `vilicus upgrade check`, to a migration on a copy of each file, to the swap or the per-file failure and its alert (see D84).
