# Story 1.9: E19: canonical CBOR in Rust and TypeScript

As the owner,
I want canonical CBOR hashing proven identical between the Rust Core and the TypeScript decoder that renders light confirmations,
So that what a member approves in the browser is bound to the same bytes the Core hashes.

**Acceptance Criteria:**

**AC1 (E19, AD-13)**
**Given** the AD-13 profile (deterministic CBOR per RFC 8949 section 4.2.1, no floating-point value, no indefinite-length item, listed tags only) and a large generated corpus of hashed and signed types, under `spikes/e19-cbor/`
**When** the Rust encoder produces the bytes and the TypeScript decoder decodes and the Rust side hashes them with SHA-256
**Then** bytes and hashes are identical across both implementations for every item of the corpus

**AC2 (E19, AD-13)**
**Given** a fuzzed set of non-canonical inputs (unsorted map keys, non-minimal integer lengths, indefinite lengths, floats, unlisted tags)
**When** each decoder receives them
**Then** every decoder rejects exactly the same inputs

**AC3 (E19, D19)**
**Given** the corpus passes
**When** the spike ends
**Then** the test vectors are committed for reuse by Story 2.5 and later decoders (the Kotlin part runs before the native app milestone)
**And** if bytes or rejections differ, the fallback (switch the canonical form) is recorded in `doc/decisions.md`

**Spike plan:**
- Question: is canonical CBOR hashing identical between the Rust Core and the TypeScript decoder (E19, Rust and TypeScript part)?
- Method: cross-language test vectors and fuzzing under the AD-13 profile.
- Pass criterion: identical bytes and hashes on a large corpus; every decoder rejects the same non-canonical inputs.
- Timebox: 4 working days.
- Fallback on failure: switch the canonical form.
- Result record: E19 status in `doc/research-notes.md` (Rust and TypeScript part), vectors committed, both crate and package choices added to the spine Stack with pinned versions.

**Decision tasks:**
- [ ] Decide the Rust CBOR crate between `cbor4ii` and `dcbor` (spine Deferred). Recommended: `dcbor`, because it enforces the deterministic profile and rejects non-canonical input natively, which is the property AD-13 relies on. Gives up: `cbor4ii` speed and serde integration, so closed-type mapping takes more code in `vilicus-proto`.
- [ ] Decide the TypeScript CBOR decoder package (approved by D113). Recommended: `cbor2`. Gives up: a smaller decoder that would need its own canonical checks.

**Dependencies:**
- None.

## Implementation Notes

**Location.** The spike lives in `spikes/canonical-cbor/`, not `spikes/e19-cbor/` as AC1 names it; the path was set when the spike was assigned. Story 2.5 and later decoders take the vectors from `spikes/canonical-cbor/vectors/`.

**What was built.**

- A standalone Rust crate (its own empty `[workspace]`, edition 2024, Apache-2.0, `publish = false`). Pinned dependencies: `dcbor` =0.25.2 (licence BSD-2-Clause-Patent), `sha2` =0.11.1, `serde_json` =1.0.154 (vector files), `hex` =0.4.3 and `unicode-normalization` =0.1.25 (both already in `dcbor`'s tree, named directly; the second is pinned exactly because its Unicode version, 17.0.0, is part of the canonical form, see finding 5).
  - `src/profile.rs`: the AD-13 profile on top of `dcbor`. `decode` runs, in order: a non-recursive head scan that refuses more than `MAX_DEPTH` (32) nested arrays, maps or tags (each counts a level), any tag outside `LISTED_TAGS` (empty), any float and any byte after the first item; `dcbor` decoding; a value check (no float, no unlisted tag, integers not below -2^63, NFC text, the depth bound); and `require_round_trip`, which refuses an input whose re-encoding differs from it. `encode` runs the value check, so it refuses non-NFC text instead of letting `dcbor` normalize it silently, then `dcbor`'s encoder. `insert_unique` builds maps and refuses a key equal to an earlier one once canonicalized, where `dcbor`'s `Map::insert` silently replaces it (finding 7).
  - `src/corpus.rs`: the seeded corpus in three families. `boundary` (122 values, derived from the profile constants): integers at and around every head-length boundary of both signs within [-2^63, 2^64 - 1], byte strings up to 257 bytes and text up to 65 536 bytes (the four-byte length head is crossed with text only, to keep the committed files small), text reaching the 24 and 256 byte boundaries with two, three and four-byte characters, special texts in their NFC form (decomposed accents, Angstrom and Ohm signs, conjoining jamo, unordered combining marks, a composition exclusion, BOM, NUL, noncharacters, private use), arrays and maps across the 24 and 256 length boundaries, map key orderings that tell bytewise sorting from length-first sorting and mix every key type, and nesting at exactly `MAX_DEPTH` with arrays, maps and both. `shaped`: maps shaped like a light confirmation, a step-up challenge and audit parameters, with random contents; `vilicus-proto` does not exist yet, so they model expected shapes, not the real types. `random`: recursive values of every kind, with text drawn from Unicode classes chosen to stress UTF-8 and normalization, the full code point range included. Valid text is in NFC under the Rust tables; map entries are written in generation order, so each encoder has to sort by itself. `encode_invalid` lists what the encoder must refuse: each non-NFC special text, alone and as a map key next to its NFC form, containers one level over the bound, and the integer -2^63 - 1.
  - `src/fuzz.rs`: mutations of corpus encodings up to 128 bytes. Targeted mutations (`must_reject`) break one rule each: non-minimal head, indefinite length, misordered or duplicate map key, float for an integer, tag, trailing bytes, truncation, invalid simple value, integer below -2^63, non-NFC text, invalid UTF-8; plus seven derived cases: one level over `MAX_DEPTH` with arrays, maps and both, `deep` levels of arrays, maps and tags, and one item followed by `deep` array heads. Blind mutations flip a bit or replace, insert or delete a byte; their verdict is whatever the Rust profile decides.
  - `src/bin/gen_vectors.rs` writes `corpus.json`, `encode-invalid.json`, `fuzz.json` and `SHA256SUMS`; `tests/vectors.rs` replays a vector directory and, for the committed one, refuses a file that differs from a fresh generation.
- A TypeScript package, `spikes/canonical-cbor/ts/` (`"private": true`, Apache-2.0, `cbor2` 2.4.0 pinned exactly, `package-lock.json`, no other dependency). It runs on Node's built-in type stripping and test runner, so no TypeScript compiler was added; the code is executed, not type-checked.
  - `src/profile.ts` mirrors the Rust profile: the same head scan (tags counted, trailing bytes refused), `cbor2` decoding with its dCBOR options plus `convertUnsafeIntsToFloat: false`, `rejectFloats`, `rejectBigInts`, `ignoreGlobalTags` and `preferMap`, then `requireRoundTrip`; every error of `cbor2`, re-encoding included, surfaces as a `Rejection`. `encodeCanonical` refuses non-NFC text before encoding.
  - `test/profile.test.ts` holds the unit tests of the layer; `test/corpus.test.ts` and `test/rejections.test.ts` replay the vector files.
- Vector files in `spikes/canonical-cbor/vectors/`, 1.93 MB in all (`.gitattributes` marks them `-text` so a Windows checkout keeps their bytes): `corpus.json` (722 values: 122 boundary, 200 shaped, 400 random), `encode-invalid.json` (19 values), `fuzz.json` (2 507 inputs: 1 083 targeted, 1 424 blind, derived cases nested 10 000 levels), `invalid.json` (90 hand-written inputs, each with the rule it breaks) and `SHA256SUMS`. Each generated file carries a `profile` header derived from the Rust constants (`max_depth`, `listed_tags`, integer range, `unicode_version`). The header is a gate: the Rust test refuses a file whose header differs from the constants and the pinned tables, and the TypeScript test refuses one whose depth or tags differ and, under `run.sh`, one whose Unicode version differs from the runtime's.
- `spikes/canonical-cbor/run.sh` and its `Dockerfile`: Debian 13 with `rust:1.99-trixie` and `node:22.23.2-trixie-slim`, both pinned by digest, Node copied into the Rust image. It replays the committed vectors on both sides, then a fresh, larger generation that is never committed: corpus seed 2026101601 with 4 000 shaped and 20 000 random values, fuzz seed 2026101602 with 100 000 mutations and derived cases nested 100 000 levels.

**Findings.**

1. *`dcbor` 0.25.2 accepts integral floats that dCBOR forbids.* Its float validation tests integrality through a saturating cast to `i32` (single) or `i64` (double), so an integral single at or above 2^32 or below -2^31, and an integral double in [2^63, 2^64), pass. Such a double is then reduced to an integer: `fb43e0000000000001` decodes to the integer 2^63 + 2048, whose canonical encoding is `1b8000000000000800`, so two byte strings decode to one value. The fuzzer found it (8 `float_for_int` mutations accepted before the fix). The profile refuses every float in the head scan, and `require_round_trip` is the backstop for any gap of the same kind; a unit test on each side feeds it exactly this pair.
2. *`dcbor` decodes recursively without a nesting bound.* Checked with a throwaway release build outside the repository: `CBOR::try_from_data` on 10 000 nested arrays (10 KB) aborts the process with a stack overflow on the development host's main thread, as it does at 100 000 and 1 048 576 levels; a 1 MiB control frame of AD-12 could hold a million levels. The head scan bounds the nesting before `dcbor` runs, tags included, so listing a tag later does not reopen the overflow.
3. *The raw libraries disagree.* On the 90 hand-written inputs, `dcbor` alone accepts 19: floats (5), the integral floats of finding 1 (4), tags (8) and integers below -2^63 (2). `cbor2` alone, with its dCBOR options, accepts 13: the same floats and tags; it refuses the integral floats and the integers below -2^63. With the profile layer on each side, both refuse all 90.
4. *`cbor2` pitfalls.* Its `maxDepth` (default 1024) does bound recursion (checked: 2 000 nested arrays, maps or tags and 100 000 nested maps are refused), but it counts an array level twice and a map or tag level once, so the profile's bound of 32 is applied by the same head scan as on the Rust side. Its dCBOR preset sets `convertUnsafeIntsToFloat`, which turns integers above 2^53 into inexact numbers; a signer must display the exact value, so it is turned off and such integers stay `bigint`. On encode, `ignoreGlobalTags` also drops the built-in Array, Map and Uint8Array encoders, so arrays encode as empty maps.
5. *NFC depends on the Unicode version.* `dcbor` normalizes and checks NFC with `unicode-normalization` 0.1.25, which carries Unicode 17.0; Node 25.4 on the development host carries Unicode 16.0 (ICU 77.1), Node 22.23.2 in the container Unicode 17.0 (ICU 78.2). With equal versions, everything agrees. The direction matters:
   - A signer on *older* tables than the Core accepts the Core's bytes: a code point new to it is unassigned, a starter that blocks nothing, so the Core's order passes its NFC check. With the Unicode 16 runtime, every Rust encoding of the fresh corpus decodes with the same SHA-256. The only disagreement is the reverse case, an input the Core refuses and the older signer accepts: 1 fuzzed input of 100 007 (`fuzz-036084`, U+1AD5 followed by U+032C), which the Core never emits.
   - A signer on *newer* tables than the Core may refuse the Core's bytes: a Core on Unicode 16 leaves a mark new in Unicode 17 where it is, and a signer on Unicode 17 must reorder it, so it refuses the bytes and fails closed. Tested with the texts of the first run's skewed items, `random-00145` and `fuzz-036083` (`a` U+1AE1 U+0337 and `a` U+1AD5 U+032C, as a Unicode 16 Core encodes them): the Unicode 17 runtime in the container and the Rust side refuse both (`a signer with newer Unicode tables refuses marks an older Core left unordered`, `marks_new_in_the_core_unicode_version_are_ordered_on_decode`), the Unicode 16 runtime accepts both.
   - In neither direction does a signer hash other bytes than it received. Browsers and Android ship their own ICU, so the newer-signer case cannot be avoided in production; it is a liveness cost, not a safety one. A change of the Core's own tables is different: values re-encoded under new tables can give other bytes than those already hashed, so the version is pinned exactly and a change is a format change (proposed decision record, item 1 below).
   - The TypeScript tests detect the relation of the two versions: equal versions are compared strictly (`run.sh` requires it); an older runtime tolerates a difference only at code point positions where one side holds a code point it does not assign, and in a verdict disagreement only when the refusing side's reason is NFC, and reports each case; a newer runtime is refused as unclassifiable.
6. *Dependency weight.* `cargo tree -e normal -p dcbor --prefix none | sort -u`, in the container: 19 crate versions including `dcbor` (cfg-if, chrono 0.4.45, half, hex, iana-time-zone, num-traits, paste 1.0.15, proc-macro2, quote, syn 2 and 3, thiserror and thiserror-impl, tinyvec, unicode-ident, unicode-normalization, zerocopy and zerocopy-derive). Given up with `dcbor`: `chrono` with its time-zone crate, which the profile never uses (no tag 1 dates), and `paste`, a build-time proc-macro that `cargo audit` reports as unmaintained (RUSTSEC-2024-0436, a warning, no vulnerability). The Core's `deny.toml` will need an advisory exception for it, with the reason and a review date (proposed for Story 2.5 below). `cbor2` brings one package, `@cto.af/wtf8` 0.0.6 (MIT, like `cbor2`); `npm audit` reports 0 vulnerabilities.
7. *`dcbor` collapses keys that are equal once normalized, and the first version of this spike did not test it.* `dcbor` normalizes text to NFC when it encodes, and its `Map::insert` keys entries by the encoded key and replaces an equal one. A map built with `caf\u{e9}` and `cafe\u{301}` as keys therefore becomes one entry, and the value the Core hashes and a member signs differs from the value it built and would execute. The first corpus deduplicated keys by their encoding, so it never exercised this. The profile encoder now refuses non-NFC text on both sides, `insert_unique` refuses a collapsing insertion, and `encode-invalid.json` holds both cases for every non-NFC special text (`keys_equal_after_nfc_do_not_collapse_silently`, `encode_invalid_values_are_all_refused`, `every encode-invalid value is refused by the profile encoder`).

**Review of 2026-10-16.** Every point of the coordinator's review was checked against the code. Applied: findings 2 and 7 above (tags count toward depth, non-NFC text and collapsing keys refused on encode), trailing bytes refused by the head scan on both sides (vector `00` followed by `deep` array heads), `require_round_trip` / `requireRoundTrip` extracted and unit-tested, encode refusals unit-tested (float, tag 0, 33 nested arrays, non-NFC text), a `cbor2` re-encoding error wrapped as a `Rejection`, the skew direction corrected (finding 5), committed vectors reduced from 9.5 MB to 1.93 MB with the large sets kept for the fresh run, and the dependency count recorded (finding 6). Already in place: `unicode-normalization` was pinned with `=0.1.25`. Refuted in part, with evidence: requiring *both* reasons to be NFC-related in a verdict disagreement cannot hold, because in a disagreement exactly one side refuses and the accepting side has no reason (`fuzz-036084`: Rust refuses as non-NFC, TypeScript on Unicode 16 accepts); the tolerance now requires the refusing side's reason to be NFC-related, which is the strictest condition that can apply. The newer-signer test uses real bytes and the real runtimes instead of a mocked relation, because the container's runtime is newer than the Unicode 16 tables that produce those bytes.

**Decision tasks settled** (recommended answers; the decision record is proposed below).

- Rust CBOR crate: **`dcbor`** 0.25.2. It refuses non-canonical heads, indefinite lengths, misordered and duplicate keys, trailing bytes, invalid UTF-8, non-NFC text and invalid simple values natively on decode (every hand-written case of those rules). Gives up: `cbor4ii` speed and serde integration, so closed types are mapped by hand in `vilicus-proto`, and the dependency weight of finding 6. It is not usable alone: findings 1, 2 and 7 make the profile layer of `src/profile.rs` (head scan before decoding, value check, round-trip comparison, NFC and unique keys on encode) a requirement, not an option.
- TypeScript CBOR decoder: **`cbor2`** 2.4.0 (MIT, one dependency). Gives up: a smaller decoder that would need its own canonical checks. It needs the same profile layer (finding 4).
- Profile details the spike had to fix, all in the decision record proposed below: the listed tag set is empty; integers are within [-2^63, 2^64 - 1] (the dCBOR range, which `cbor2` enforces natively and the Rust layer adds); nesting is bounded at 32 arrays, maps or tags; simple values are false, true and null; text is NFC under the Core's pinned Unicode version, refused rather than normalized on encode.

## Result

Command, from the repository root on the Windows development host with Docker Desktop: `bash spikes/canonical-cbor/run.sh`. Run of 2026-10-16, after the review fixes: exit code 0, 39 `PASS` and 0 `FAIL` lines, `RESULT PASS`. Environment printed: `rustc 1.99.1`, `node v22.23.2 (unicode 17.0)`, Debian 13.7, `dcbor` 0.25.2, `unicode-normalization` 0.1.25, `cbor2` 2.4.0. Checks: `vectors-sha256sums`, `fmt`, `clippy` (`-D warnings`, all targets), `rust-unit-tests` (10), `npm-ci`; on the committed vectors, 7 Rust tests (`rust.committed.*`) and 12 TypeScript tests (`ts.committed.*`, the 5 unit tests included); `fresh-generation`; on the fresh vectors, 5 Rust and 11 TypeScript tests (the committed-file comparison and the hand-written set apply to the committed directory only).

**AC1 (E19, AD-13): PASS.** For every corpus item, the TypeScript side receives the bytes `dcbor` produced, hashes them to the same SHA-256 as the Rust side, decodes them under the profile, and the decoded value is the described one (`ts.*.cbor2 decodes every Rust encoding under the profile to the described value`). Beyond the criterion, `cbor2` encodes each value from the notation, with unsorted map entries, to the same bytes and SHA-256 (`ts.*.cbor2 encodes every corpus value to the Rust bytes and hash`), the Rust side round-trips each item (`rust.*.corpus_encodes_hashes_and_round_trips`), and both encoders refuse the 19 values of `encode-invalid.json`. Committed corpus: 722 values; fresh corpus: 24 122; 0 mismatches on either side, both on Unicode 17.0. With the Unicode 16 runtime (Node 25.4, `node --test test/profile.test.ts test/corpus.test.ts test/rejections.test.ts` in `spikes/canonical-cbor/ts/`, committed and fresh vectors), every item decodes with the same SHA-256 and the encoding comparison reports 0 skewed items.

**AC2 (E19, AD-13): PASS with equal Unicode versions.** The 90 hand-written inputs (non-minimal heads, indefinite lengths, reserved additional information, unsorted and duplicate keys, floats including the integral floats of finding 1, invalid simple values, tags 0, 1, 2, 3, 24, 258, 55799 and a non-minimal tag head, integers below -2^63, invalid UTF-8, non-NFC text, truncations, oversized declared lengths, trailing bytes) are refused by both profile decoders (`rust.committed.invalid_inputs_are_all_rejected`, `ts.committed.every hand-written invalid input is refused`). Every fuzzed input gets the same verdict on both sides, and an accepted one re-encodes to itself on both sides (`rust.*.fuzz_verdicts_hold`, `ts.*.every fuzzed input gets the Rust verdict`): committed set 2 507 inputs, 340 accepted and 2 167 refused, every targeted mutation refused; fresh set 100 007 inputs, 12 794 accepted and 87 213 refused; 0 disagreements. With the Unicode 16 runtime, 1 fresh input (`fuzz-036084`) is refused by the Rust side as non-NFC and accepted by the TypeScript side, an input the Core never emits (finding 5). Without the profile layer, the raw libraries would not reject the same inputs (finding 3).

**AC3 (E19, D19): PASS for the Rust and TypeScript part, pending commit.** The vectors are in `spikes/canonical-cbor/vectors/` with `SHA256SUMS`, reproducible with `cargo run --bin gen_vectors -- vectors` (the committed-file test refuses a stale file), ready to be committed for Story 2.5 and later decoders. The Kotlin part has not run; it runs before the native app milestone. Bytes and rejections are identical with equal Unicode versions, so the fallback (switch the canonical form) is not taken and no fallback is recorded in `doc/decisions.md`; the Unicode skew of finding 5 never changes the bytes a signer hashes and is handled by the profile record proposed below.

**Verification run separately.** On the host: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` clean (10 unit and 7 vector tests); `node --test test/profile.test.ts test/corpus.test.ts test/rejections.test.ts` passes (12 tests, Unicode 16 runtime, skews reported as above); `npm audit` 0 vulnerabilities; `cargo audit` 0 vulnerabilities and 1 warning (`paste` unmaintained, finding 6).
