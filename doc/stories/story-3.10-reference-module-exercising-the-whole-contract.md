# Story 3.10: Reference module exercising the whole contract

As a project maintainer,
I want a reference module that uses every part of the module contract and is linked only into `vilicus-testbed`,
So that the platform is proven end to end in V0.1 without shipping a user-facing module.

**Acceptance Criteria:**

**AC1 (FR-22, I8, I36)**
**Given** `vilicus-mod-reference`
**When** it is registered
**Then** it declares tables with the full envelope, structured and free-text fields with maximum lengths, a reviewed vocabulary, and record kinds with data types including a local-only type (`health` or `journal`)
**And** it passes registration under the checks of Stories 3.2 to 3.4.

**AC2 (FR-22)**
**Given** the reference module's tools
**When** the capability matrix check runs in the testbed
**Then** a tier 0 tool and a tier 1 tool are each backed by a row of a testbed-only matrix fixture under `testing/`, `doc/capability-matrix.md` gets no reference-module row, and one record kind is declared exempt from elevation.

**AC3 (FR-22)**
**Given** the reference module's test suite
**When** it runs
**Then** it exercises a typed write with journal, an event and its consumer, an outbox effect intent, an undo handler and two migrations applied in sequence, each asserted.

**AC4 (FR-109, D102)**
**Given** the build outputs
**When** the crate graph and packaging checks run
**Then** the reference module is linked into `vilicus-testbed` only and never into `vilicus` or any package.

**AC5 (I6, AD-5)**
**Given** a second test module in the testbed that reads reference-module data
**When** it reads that data
**Then** the call goes through the reference module's typed API registered with the Core, which checks the caller's partition scope
**And** any attempt to obtain a handle on the reference module's file is refused

- Story 2.6 (testbed binary)

**Decisions and why** (drafted decision and document texts under Open points)
- *Where the exemption lives* (AC2, Story 3.2's open point): a flag of the record kind, `Table::elevation_exempt`, as D104 and PRD FR-28 describe it ("a fixed list of low-risk record kinds ... declared per module"), with the rule of D104 as a function, `accepts_without_elevation`: from an AI or plugin principal an exempt kind takes structured fields only, so a write giving free text, or a name the kind does not declare, still needs elevation. Deciding the elevation is the pipeline's (Story 10.6); no declaration rule refuses an exempt kind without a structured field, which would simply never spare a write. The matrix check does not compare a row's `exempt` Tainted session cell with the kinds a tool writes, since a tool does not declare its tables.
- *What a typed API is* (AC5): declared, not code. A module declares `Query` items, each one record of one of its tables by id and the fields it returns, with an access list of the modules allowed to call it, checked by `const fn` as every declaration is; the Core serves them. No code of the target module runs on another module's call, so no fault, time budget or writer of the target is involved, and a declaration a review reads says exactly what leaves the module. What it gives up: richer reads (lists, filters, joins) wait for the module read handle (Story 10.3), and a module cannot compute what it returns.
- *Where a read is made* (AC5, AD-9): inside the caller's handler, through the record port, `Records::read`, as AD-9 says ("a cross-module API call made inside a write handler is read-only, served from a read connection on the caller's thread"). Handlers keep D151's signatures, the record port of the call only. Each open file has a read handle beside its write handle, and the Core reads the target's file on it, never on its writer; a refused read ends the call, as a refused write does.
- *The caller's partition scope* (AC5, FR-19, AD-5): derived from the caller's file: its own partition, then, for a member's personal partition, the household's. A household or home call reads only its own partition, so a member's personal data never flows into a household file through a read (a copy across partitions is tier 2, FR-21), and no call reads another member's partition. The Core never asks for a file outside the scope. Whom the call acts for is bound to the file by the pipeline (Story 10.4).
- *A record read is an input of every later write* (AD-7, D147): the Core keeps the provenance of each record a call read and counts it as an implicit input of every write the call makes after the read, journaled as such; a carried snapshot of the same record (an event's) counts combined with the read, the most restrictive of both (D151). A module cannot lower a write's labels or data types by not naming what it read. What it gives up: a write of a call that read a record derives from it even when unrelated, the safe direction.
- *A file of the scope that is not ready* (review of the gate test): skipped, since ids are unique and a record held by another file of the scope is that record; a record found nowhere else is `module_unavailable` with the skipped file's retry class, as a typed call to that file would be (AD-54), rather than `not found`, which the Core cannot assert.
- *A query returns fields, not the envelope*: the reading module learns no taint, author or source; the Core keeps them.
- *Where the reference module's test suite lives* (AC3): in `vilicus-testbed`, the artefact gates that need a module run against (D102), on the testbed's own `REGISTRY` and `HANDLERS`, through the Core's unlock and bring-up paths; the reference crate holds the declaration and code and their build-time checks only. Its tier 1 tool carries an outbound effect under `reversible_external_state` so that its effect intent and its undo handler exercise what I13 requires of an exception class. It consumes its own topic and `reader` consumes it too, which shows both an own consumer and a cross-module consumer reading through the typed API.
- *The second module* (AC5): `reader`, in the testbed crate (compiled with the tests only, as its registry is), written against the module port alone; a separate crate would carry the same code.
- *How the testbed names storage types* (D140): `vilicus_core::testing`, behind the `testing` feature the packaging check refuses in a release artefact; it opens no file. Making `ModuleFile` and `Partition` public re-exports of the Core is left to the story whose code first needs them outside tests.
- *The reference module's dependencies* (Story 3.5's open point): strict: `vilicus-module-api` is its only normal or build dependency, registry crates included; dev-dependencies stay free. The rule is the reference module's alone: shipped modules are held by the graph's `mods` node.
- *The AD-9 gate* (Story 3.9's open point): a test of the testbed on three unlocked partitions; "unlocked" is what the Core holds before the key path exists: the partition's generation still current, its files serving. The run in the Debian VM against the `vilicus-testbed` executable with a member's real unlock is Story 14.1's.

**Deviations**
- *AC1, "passes registration under the checks of Stories 3.2 to 3.4"*: the `const` registry and `assert_valid` (3.2), `verify_migrations` (3.2, 3.7), the capability matrix check on the testbed's fixture (3.3) and the write path fuzz test over its four tables (3.4), all in the testbed. A reviewed-vocabulary label is shown refused when no adult confirmed it; no surface confirms one in V0.1 (FR-50), so no seeding entry was needed (Story 3.4's open point).
- *AC2, "one record kind is declared exempt from elevation"*: declared (`tallies`) and its rule stated by `accepts_without_elevation`; no call is elevated before the elevated queue exists (Story 10.6).
- *AC3, "the reference module's test suite"*: it runs in `vilicus-testbed`, against the testbed's registry and handler table, not in the reference crate (Decisions).
- *AC4*: shown by the crate graph and packaging checks as they were, and by the new rule holding the reference module to the module port; no new check of the testbed artefact.
- *AC5, "checks the caller's partition scope"*: the scope is derived from the caller's file; binding a call to the member it acts for, and opening only that member's files, is the pipeline's (Story 10.4). *"any attempt to obtain a handle on the reference module's file is refused"*: a module has no way to name a handle (the module port exports none, the reference module links the port alone, the second module holds the record port of its call only), its own connections refuse to attach the file (I6), and the Core reads only the file it asked for. Crates that depend on the Core (the binary and the testbed) still receive handles from a bring-up (Open points).

- *Story 10.3* (the pipeline): the module read handle and reads richer than one record by id; the mapping of `RecordError::UnknownQuery`, `QueryNotAllowed` and `Unavailable` into the client error enum (`module_unavailable` for the last).
- *Story 10.4*: the scope of a read derives from the caller's file; the pipeline opens for a token only the files of the member's scope, so the file a call runs on is one of them.
- *Story 10.5*: a record an AI or plugin call reads through a typed API raises that call's later writes, but not its session taint for the calls after it; the session's consumed taint and data types should take the read in.
- *Story 10.6*: the elevated queue decides from `Table::accepts_without_elevation`; nothing compares a matrix row's `exempt` Tainted session cell with the kinds its tool writes, since a tool does not declare its tables.
- *Story 5.1* (the Core process): a `Boundary` now holds the typed APIs of its call, read connections of its thread, so it is built on each writer thread and is not `Send`; each open file holds a read connection beside its writer, which doubles the connections per file (E32 measures the execution model without them).
- *The Core's surface*: `bring_up` is public and the `PartitionFiles` it returns hands out the write and read handles of a partition's files (`handle`, `ConsumerFiles::open`, `ApiFiles::reader`) to any crate depending on the Core, today the binary and the testbed only; no module crate can depend on the Core. Once the Core process holds them (Story 5.1), `bring_up` and `PartitionFiles` can become crate-private, the testbed reaching them through the `testing` module, which restores the registry's claim that no crate outside the Core gets a handle.
- *Story 14.1*: the AD-9 gate runs here as a test of the testbed on partitions unlocked as the Core marks them; its run in the Debian VM against the `vilicus-testbed` executable, with a member's real unlock and a `testbed` entry of `ci/release_gates.toml`, needs the testbed's `main` to start the Core.
