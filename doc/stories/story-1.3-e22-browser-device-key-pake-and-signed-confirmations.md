# Story 1.3: E22: browser device key, PAKE pairing and signed confirmations

As the owner,
I want to know whether a non-extractable browser key, OPAQUE-bound pairing codes and device-signed light confirmations work on every supported browser,
So that browser pairing, session binding and the elevated queue are built on a proven mechanism or on the fallbacks of D107.

**Acceptance Criteria:**

**AC1 (E22, AD-21, FR-15, NFR-9)**
**Given** a prototype page and a Rust verifier under `spikes/e22-device-key/`, on current and previous Chrome and Firefox, desktop and Android (Safari best effort)
**When** the page creates an ECDSA P-256 key with WebCrypto as non-extractable, reloads, and tries to export it
**Then** the key survives the reload, export is refused, and a per-request signature over the AD-21 byte string (SHA-256 of `vilicus/v1/req`, session id, increasing counter, method, path, SHA-256 of the raw body) verifies in Rust

**AC2 (E22, AD-21, D35, FR-16)**
**Given** `opaque-ke` 4.0.1 in the verifier and `@serenity-kit/opaque` 1.1.0 in the page
**When** a pairing code is used by the new browser, and separately observed or relayed by a third party
**Then** the legitimate run binds the code to the new browser's key registration, and the observed or relayed code fails

**AC3 (E22, D38, FR-28)**
**Given** a light confirmation whose canonical bytes are produced by the verifier
**When** the browser signs those bytes with its device key
**Then** the verifier accepts the signature for that request only, and rejects it for any other request bytes

**AC4 (D107)**
**Given** any part of AC1 to AC3 fails on a supported browser
**When** the result is recorded
**Then** the matching D107 fallback is recorded in `doc/decisions.md` and named in the results table

**Spike plan:**
- Question: do a non-extractable device key, PAKE-bound code pairing and signed light confirmations work on every supported browser (E22)?
- Method: prototype page plus Rust verifier; a browser matrix per AC; a relay and an observation test for the code.
- Pass criterion: AC1 to AC3 hold on current and previous Chrome and Firefox, desktop and Android.
- Timebox: 5 working days.
- Fallback on failure: the three fallbacks of D107: sessions re-proven by a passkey assertion every 15 minutes of activity, stated to the user; pairing codes issued only by `vilicus device pair`; approvals made by a step-up bound to the request hash.
- Result record: results table per browser in `doc/research-notes.md` (E22 status moved per its section 5); each fallback taken recorded as a decision record.

## Implementation Notes

**Location.** The spike lives in `spikes/browser-device-key/`, not `spikes/e22-device-key/` as AC1 names it; the path was set when the spike was assigned.

**What was built.**

- A standalone Rust crate (its own empty `[workspace]`, edition 2024, Apache-2.0, `publish = false`, `#![forbid(unsafe_code)]`) playing the Core and the Gateway. Pinned dependencies and why:
  - `opaque-ke` =4.0.1 (features `ristretto255`, `serde`, `argon2`): the PAKE AD-21 names, the version this story names. `sha2` =0.10.9 and `rand_core` =0.6.4 (`getrandom`) are the hash and RNG types its API is generic over.
  - `aws-lc-rs` =1.18.2: ECDSA P-256 signing and verification (`ECDSA_P256_SHA256_FIXED`), SHA-256, HKDF-SHA-256 and HMAC-SHA-256, as AD-18 takes its primitives from it.
  - `canonical-cbor` by path (`../canonical-cbor`, the AD-13 profile of story 1.9, not modified) and `dcbor` =0.25.2 to build the values it encodes.
  - `tokio` =1.53.3, `hyper` =1.12.0, `hyper-util` =0.1.21, `http-body-util` =0.1.5 (HTTP/1.1 server), `rustls` =0.23.46 and `tokio-rustls` =0.26.6 (TLS 1.3, aws-lc-rs provider, certificate chosen by SNI), `rcgen` =0.14.10 (test CAs), `serde` =1.0.229, `serde_json` =1.0.154, `base64` =0.22.1 (the URL-safe unpadded base64 of the browser package). `rustls` is one patch above the spine's 0.23.45, which `cargo audit` flags (RUSTSEC-2026-0346 to 0349, fixed in 0.23.46).
  - `src/device.rs`: the AD-21 byte string, the proof of possession, the session challenge and ECDSA verification. `src/pairing.rs`: the OPAQUE cipher suite, the code format, the key binding, and the labels of the Core's registration signature and identity-key tag. `src/confirm.rs`: the canonical bytes of a pending request and of a confirmation challenge. `src/core.rs`: the Core's state (enrollment tokens, devices, sessions, pairings, login runs, the login rate limit, pending requests, confirmation challenges) and every check. `src/http.rs`: the HTTPS front, the pages under the CSP, the test harness and the relay. `tests/core_flows.rs`: 22 tests that run every flow with Rust clients (an aws-lc-rs key standing in for WebCrypto, the `opaque-ke` client standing in for the WASM one), the relay, replay, rate-limit and expiry cases included; 5 unit tests in the modules.
- Three pages under `web/`, no framework, no bundler: `index.html` (enrollment, signed requests, light confirmations), `pair.html` (issuing and redeeming codes) and `control.html` (test only, see the CSP below), each loading one ES module with the per-response nonce. `static/common.js` holds the device key, the IndexedDB store, the AD-21 signer, the per-session request queue and the CSP probes; `static/confirm.js` holds the client check before a confirmation is signed. `web/package-lock.json` pins `@serenity-kit/opaque` 1.1.0 (MIT), served as `/static/opaque.js`, and `cbor2` 2.4.0 with its one dependency `@cto.af/wtf8` 0.0.6 (MIT), the decoder story 1.9 chose, served under `/vendor/` through an import map that carries the page nonce. The OPAQUE module is self-contained, with the WebAssembly inlined as base64 and compiled with `WebAssembly.compile`, so it needs no `'unsafe-eval'`, only `'wasm-unsafe-eval'`.
- CSP of the application and pairing pages, generated per response: `default-src 'none'; script-src 'self' 'nonce-<random>'; style-src 'self'; img-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; require-trusted-types-for 'script'; trusted-types lit-html`. The pairing page alone adds `'wasm-unsafe-eval'` to `script-src` (AD-19, AD-21). The test-only control page allows `'unsafe-eval'` and sets no Trusted Types directive, as a positive control for the probes.
- `browser/driver.mjs`, driven by `playwright-core` 1.64.1 (`browser/package-lock.json`): Chrome for Testing over the DevTools protocol, stock Firefox over WebDriver BiDi (Playwright's `moz-firefox` channel), both headless, so neither is a Playwright-patched build. Each browser of the story (the enrolled one, a new one, another new one, one behind the relay) is a separate persistent profile; closing and relaunching a profile is a browser restart. Certificates are validated: the driver adds the run's test CA to the user NSS database that Chrome reads (`certutil`), Firefox installs it at startup from an enterprise policy (`browser/firefox-policies.json`, `Certificates.Install`), and no certificate error is ignored.
- `browser/Dockerfile`: the official Playwright image `mcr.microsoft.com/playwright:v1.64.1-noble` pinned by digest, with `libnss3-tools`, Chrome for Testing 155.0.8059.84 (current stable major on 2026-10-16) and 154.0.8037.92 (the last 154 build published for testing; stable 154 ended at 154.0.8037.97), Firefox 158.0 (current release) and 157.0 (previous). Each archive is checked against a pinned SHA-256: Mozilla's `SHA256SUMS` for Firefox; for Chrome for Testing, which publishes no checksum, the hash taken at first download, so the pin is trust on first use. The final image runs as the unprivileged `pwuser`.
- `compose.yaml` and `run.sh`: the server answers `core.vilicus.test`, `relay.vilicus.test` and `rogue.vilicus.test` on a private compose network over HTTPS (TLS 1.3; the first two names carry a certificate from the run's test CA, the third from a second CA nobody trusts). `run.sh` runs fmt, clippy (`-D warnings`), the release build and the tests in `rust:1.99-trixie` (pinned by digest), fails on any ignored or missing test (`EXPECTED_TESTS`), installs the web packages with `npm ci` into a volume, builds the browser image, starts the server, runs the driver once per browser, fails a browser that passes fewer checks than `EXPECTED_CHECKS`, prints one `PASS` or `FAIL` line per check, and removes the compose project on exit.

**Test harness, and what it stands for.** `POST /__test/enrollment-token` stands for the FR-15 enrollment, `POST /__test/host-pair` for `vilicus device pair` (the Core draws the secret and runs the OPAQUE client side itself, so the code never transits the Gateway), `POST /__test/pending` for the assistant's elevated call, `POST /__test/advance-clock` moves the Core's clocks, `POST /__test/pairing-state` and `POST /__test/device-by-key` read the Core's state, and `POST /__test/reset-login-rate` clears the login rate limit so the matrix, which runs from one container, stays under it. The relay is the on-path attacker: on `relay.vilicus.test` it reads every request and response, records the pairing login messages, can replace the new browser's public key and proof with its own (`substitute-key`), and can replay the recorded messages to the Core; in `substitute-registration` mode it sits on the issuing browser's path to `core.vilicus.test` and replaces the Core's OPAQUE registration response with an evaluation under its own OPRF key, keeping the Core's server public key and signature. It forwards the pages and scripts unchanged; an attacker who serves modified code is the compromised Gateway that D35 and PRD section 8.2 exclude. The relay runs in the server process between the network layer and the Core's handlers, which is equivalent for the protocol: it sees and rewrites the same bytes a separate proxy would. The session id travels in an `x-vilicus-session` header; the product carries it in the `__Host-` cookie (architecture section 6).

**Decision tasks settled** (recommended answers; the decision record is proposed below).

1. *AD-21 byte string.* "Concatenated" is ambiguous with two variable-length fields, so: `vilicus/v1/req` (14 bytes), the session id (16 bytes), the counter (8 bytes, big-endian), the length of the method (4 bytes, big-endian), the method, the length of the path (4 bytes, big-endian), the path with its query, and SHA-256 of the raw body. The browser signs SHA-256 of that string with ECDSA P-256 and SHA-256 (WebCrypto `sign`, which hashes it once more); the signature is the 64-byte `r || s` form WebCrypto returns; the public key is the 65-byte uncompressed point of `exportKey('raw')`. The Core verifies with `ECDSA_P256_SHA256_FIXED`, then requires the counter to exceed the last accepted one; a refused request does not advance it (tested: after refused requests at counters 6 and 7, a correctly signed request at 6 is accepted). Gives up: 8 bytes over a bare concatenation.
2. *Ordering and persistence of signed requests.* The client sends the signed requests of one session one at a time, in counter order (a promise queue in `Session.post`), because two requests in flight can arrive out of order and the later counter then refuses the earlier one. Sessions live in the Core's memory and do not survive a Core restart: after one, the browser opens a new session with its device key. Gives up: concurrency within one session; a window of accepted counters would allow it, at the cost of tracking which counters in the window were used. The rejected alternative, writing the counter durably before each response, puts a write on every request.
3. *Proofs of possession.* A new public key is registered only with an ECDSA signature by that key over `vilicus/v1/device-pop`, a length-prefixed context and the key, where the context is the enrollment token or the pairing binding message. A session for a registered device opens with a signature over `vilicus/v1/session`, the device id and a single-use Core nonce (60 seconds); in the product the session comes from the passkey login, and this challenge is what binds it to the device key.
4. *OPAQUE configuration.* The suite of `@serenity-kit/opaque` 1.1.0 without its `p256` build: ristretto255 OPRF, 3DH over ristretto255 with SHA-512, Argon2id as the key stretching function at the package default (64 MiB, 3 passes, 4 lanes, zero salt, client side only), no identifiers, no context. The OPAQUE credential identifier of a pairing is `vilicus/v1/pair/` and 16 random bytes, so each pairing has its own OPRF key. Gives up: the P-256 suite (`@serenity-kit/opaque-p256`), which would match the device key curve but changes nothing here.
5. *Code format.* `HHH-SSSS-SSSS`: a 3-digit handle, not secret, that names the pending pairing (a new browser has no session yet, so the Core needs it to find the registration record), and an 8-digit secret, the OPAQUE password, drawn by the issuer (`crypto.getRandomValues` in the issuing browser, the Core's RNG for `vilicus device pair`) with rejection sampling. With 3 attempts, an online guess succeeds with probability 3 in 10^8 per code. Gives up: 11 digits to type; 6 secret digits would give 3 in 10^6.
6. *Attempts, uniform answers and the rate limit.* An attempt is counted at the OPAQUE login start, because a client that typed a wrong secret detects it alone and never sends the third message. Every login start gets an OPAQUE answer: a live pairing (registered, unused, unexpired, attempts left) spends an attempt and gets the real answer; an unknown, used, expired or exhausted handle gets OPAQUE's fake answer (`opaque-ke` with no registration record), which the client cannot tell from a wrong secret, so the handle space cannot be probed for live pairings. Each run is kept under its own login identifier, so a second start never cancels a run in flight. Every login start, valid or not, is charged to its source address: 10 per 60 seconds. The lock-out after 3 attempts remains a denial-of-service lever: anyone who reaches the API and guesses a live handle can spend its attempts, and the member then issues another code; the uniform answers and the per-source limit make that cost about 3 000 starts to cover every handle within a code's 2 minutes, which one source cannot make. The code is used up once the Core verifies the third OPAQUE message, whatever the binding outcome, so a relay that breaks the binding also burns the code.
7. *Key binding.* `@serenity-kit/opaque` exposes no OPAQUE `context`, and client identifiers are bound into the envelope at registration, before the new browser's key exists, so neither can carry the public key. The new browser sends its public key with an HMAC-SHA-256 tag under HKDF-SHA-256 (empty salt, the 64-byte OPAQUE session key, info `vilicus/v1/pair/bind`) over `vilicus/v1/pair/bind`, the handle, the login id and the public key, and a proof of possession over the same message. A relay that swaps the key lacks the session key and cannot produce the tag.
8. *Authenticating the Core to the issuing browser.* The first version compared the OPAQUE server public key with one fetched from the Core over the same channel, which proved nothing (review of 2026-10-16), and comparing that key cannot catch the attack that matters anyway: a relay on the issuing browser's path can keep the Core's server public key and replace only the OPRF evaluation, and the record the issuer then uploads lets it test the 10^8 secrets offline. Settled: the Core holds an ECDSA P-256 identity key and signs `vilicus/v1/pair/registration`, the handle and the registration response; the issuing browser verifies the signature with the identity key it pinned when it was registered, and refuses to finish otherwise. An enrolled browser pins the key at enrollment (trust on first use, at the moment the enrollment token is redeemed); a browser paired by code receives it with a tag under its binding key (`vilicus/v1/pair/core-key`), so the pin is authenticated by the OPAQUE run. Gives up: one signature per issuance and one more key the Core holds; the alternative, accepting the offline oracle, relies only on Argon2id costing more than the 2-minute life of a code.
9. *Light confirmation.* The Core encodes the pending request canonically (AD-13 profile) and hashes it; a challenge is a second canonical map with `kind` (`vilicus/v1/light-confirmation`), `decision`, `request_id`, `request_hash`, `device_id`, a 16-byte `nonce` and `expires_at` (wall-clock seconds, 300 seconds ahead). Before signing, the browser decodes the bytes with `cbor2` under the dCBOR options of story 1.9, refuses them unless they re-encode to themselves, and requires `kind` to be `vilicus/v1/light-confirmation`, `decision` to be `approve`, and `request_id` and `device_id` to name the request the member is approving and this device; it then signs the bytes exactly as received with ECDSA P-256 and SHA-256. The Core keeps the bytes it issued per nonce and verifies against them; a nonce approves once, only its request, only from its device; a decided request takes no new challenge, and a device gets no challenge for another device's request.
10. *Clocks.* Every lifetime (pairing codes, login runs, session and confirmation challenges, the rate window) is checked on a monotonic clock, so a wall-clock step neither expires nor revives anything; the wall clock appears only in the `expires_at` a confirmation shows.

**Findings.**

1. *Every part works on the four desktop browsers*, with no browser difference: the non-extractable key survives a reload and a browser restart in IndexedDB, `exportKey` refuses `pkcs8`, `jwk` and `raw` with `InvalidAccessError` before and after both, and every check of AC1 to AC3 gives the same result on Chrome for Testing 155 and 154 and Firefox 158 and 157, headless, with certificate validation.
2. *A DevTools-protocol evaluation bypasses the CSP's eval restriction in Chrome.* In the first run, the CSP probe called through Playwright's `page.evaluate` reported `eval` allowed on Chrome's application page, while the same probe blocked it on the pairing page, where an asynchronous step ran first. Chrome lets code evaluated through the DevTools protocol run `eval` despite the CSP (`Runtime.evaluate` has `allowUnsafeEvalBlockedByCSP`, true by default; that this is the mechanism is my reading, not verified in Chrome's source). The probes now run from each page's own module at load, and `eval` is blocked everywhere; the control page, which allows `eval`, shows the same probe reporting `allowed`, so a blocked result is not an artefact of the probe. The CI browser test of AD-19 must probe from the page's own scripts, or it can report a weaker policy than the page has and hide a regression.
3. *Trusted Types are enforced on all four browsers*, Firefox 157 and 158 included: `innerHTML` from a string throws `TypeError`, and creating a policy under a name other than `lit-html` throws `TypeError`; on the control page both succeed. `trusted-types lit-html` allows the first script that creates a policy named `lit-html` to own it, so any script that runs before Lit can take that name and then turn strings into trusted HTML; AD-19 relies on Lit creating it first. WebAssembly compilation is refused (`CompileError`) without `'wasm-unsafe-eval'` and allowed with it; `@serenity-kit/opaque` runs under the pairing page's CSP with no other relaxation.
4. *A relay on the issuing browser's path is caught only by a Core signature.* With `substitute-registration`, the relay's evaluation carries the Core's real server public key, so the OPAQUE client accepts it and a key comparison would pass; the issuing browser refuses only because the Core's signature over the response does not verify (`ac2.substituted_registration_response_refused_by_issuer`). Without that signature, the relay would hold an offline oracle for the code, and, by my analysis (not tested: it needs an OPAQUE client that opens the envelope with a known key rather than through the Core's OPRF), could complete a login with the Core using the uploaded record and pair its own key.
5. *Cost of an OPAQUE run in the browser*, with the default Argon2id: issuing took 142 to 222 ms and redeeming (login, binding, first signed request) 231 to 477 ms in the containers (driver `issue_ms` and `redeem_ms`); Android phones are slower and were not measured.
6. *Dependencies.* `opaque-ke` 4.0.1 brings a RustCrypto stack next to aws-lc-rs: `curve25519-dalek` 4.1.3, `voprf` 0.5.0, `argon2` 0.5.3, `hkdf` 0.12.4, `hmac` 0.12.1 and `sha2` 0.10.9. `argon2` 0.5.3 duplicates the major of the spine's `argon2` 0.6.0, which the spine allows only when a dependency forces it, listed in `deny.toml`. The `opaque-ke` README states an NCC Group audit of June 2021 on release 0.5.0, with fixes in 1.2.0; release 4.0.1 is three majors later, so it is not the audited code, and D28 allows audited libraries only. The browser package, a WASM build of `opaque-ke` by another publisher, has no audit that I found (not searched beyond its package). `cargo audit`: 0 vulnerabilities, 1 warning (`paste`, unmaintained, through `dcbor`, as in story 1.9); `npm audit` on both lockfiles: 0 vulnerabilities.
7. *ECDSA signatures are malleable.* WebCrypto does not normalize `s` and aws-lc-rs accepts both forms, so a second valid signature for the same bytes can be derived from the first. Replay protection here rests on the counter and the single-use nonces, never on signature uniqueness; the Core must never use a signature as an identifier or a deduplication key.

**Review of 2026-10-16.** Each point of the coordinator's review was checked; all held and were fixed, one with a different remedy.

- Login start: unauthenticated starts spent a handle's attempts, told live handles from dead ones, and a second start cancelled the run in flight. Fixed: runs are kept per login identifier, every start gets an OPAQUE answer (fake for a dead or unknown handle), and starts are rate-limited per source (decision task 6; tests `an_unknown_handle_gets_a_fake_answer`, `login_starts_are_rate_limited_per_source`, `recorded_pairing_messages_cannot_be_replayed`; driver `ac2.unknown_handle_answered_like_a_wrong_code`, `ac2.login_starts_rate_limited_per_source`). The lock-out as a denial-of-service lever is stated in the proposed record.
- Proof of possession at pairing untested: `a_right_tag_without_the_matching_proof_is_refused` (zero and foreign proofs, `BadProof`).
- Challenge for another device's request untested: the Rust test and `ac3.other_device_gets_no_challenge` (`unknown_request`).
- Server key compared with a key fetched over the same channel: the comparison and `/api/config` are removed; the relay mode `substitute-registration` shows that a key comparison could not catch the attack, and the Core's signature with a pinned identity key does (decision task 8, finding 4).
- Certificate validation off: `ignoreHTTPSErrors` is removed; the CA is installed per browser (NSS for Chrome, policy for Firefox), and `https.untrusted_ca_refused` loads a name signed by another CA: Chrome fails with `net::ERR_CERT_AUTHORITY_INVALID`, Firefox lands on `about:certerror?e=nssBadCert` (over BiDi its navigation error itself reads only "unknown error", so the driver reads the error page's address).
- Browser checks not counted: `EXPECTED_CHECKS` per browser in `run.sh`.
- Counter not advanced by refused requests untested: added to `signed_requests_verify_and_replays_are_refused`.
- Out-of-order requests and persistence: decision task 2; `ac1.concurrent_signed_requests_serialized` (ten requests issued at once, all accepted) and the control `ac1.control.out_of_order_requests_refused` (ten requests signed in order and sent last-first: the first to arrive is accepted, the nine others refused).
- The browser signed whatever bytes it received: decision task 9 and `ac3.client_signs_only_this_requests_confirmation` (a random 32-byte digest and a confirmation with a trailing byte refused as not canonical CBOR, another `kind` refused, another request refused; the honest confirmation accepted). The attacks of AC3 that need a signature over bytes the client check would refuse (another device signing this device's challenge) go through `approveUnchecked`, which skips the check, so the Core's own refusal is still tested; the check is shown refusing the same bytes (`refused:other_device`).
- Expiry between login start and finish, session challenge expiry, and device mismatch at session opening untested: `a_code_expiring_between_start_and_finish_is_refused`, `a_session_challenge_expires`, `a_session_challenge_is_bound_to_its_device`.
- Browser wording: "Chrome for Testing 155.0.8059.84 and 154.0.8037.92, headless", the trust-on-first-use hash pin, and the missing field trials are stated here and in the Result.
- Eval probe without positive control, and `lit-html` policy: the control page and `csp.control_page_shows_probes_detect_weaker_policy`; the probes assert that a policy under another name is refused (`csp.*_refuses_unlisted_policy`); the first-creator risk is finding 3 and a proposed AD-19 sentence.
- `issue_finish` did not check the device: it now requires the device that started the issuance (`only_the_starting_device_finishes_an_issuance`).
- Wall clock for lifetimes: decision task 10.

**Not covered here.**

- Android: not run (manual procedure below). Safari: not run (best effort, D107); Playwright's WebKit is not Safari.
- The browser checks what a confirmation is before signing but does not render it to the member; rendering is web client work.
- The Core's check that the CBOR request equals its own decoding of the raw body (AD-21) needs the Gateway's JSON-to-CBOR translation, which does not exist yet.
- FR-16 rules that are Core policy rather than the E22 mechanism: no code issued by a device younger than 24 hours, notification of a host-issued code, device listing and removal. Clearing site data (FR-15, the browser becomes unpaired) was not exercised.
- Chrome for Testing has no field trials (variations), unlike a user's Chrome, so a feature a trial turns off or on in the field is not covered.
- The enrolled browser's pin of the Core's identity key is trust on first use: a relay present at the enrollment itself could substitute it. A browser paired by code receives it authenticated.
- A compromised Gateway, which serves the page's code, defeats all three parts (D35, R18); nothing here tests or claims otherwise.

**Manual procedure for Android** (Chrome and Firefox for Android, current and previous release).

1. Start the compose `server` service on a machine of the phone's network, make the phone resolve `core.vilicus.test`, `relay.vilicus.test` and `rogue.vilicus.test` to it (local DNS entry), and install `ca.pem` from the `pki` volume as a user CA on the phone (Settings, Security, Encryption and credentials, Install a certificate, CA certificate). Check that `https://rogue.vilicus.test:8443/` shows a certificate error.
2. Create an enrollment token from the machine: `curl --cacert ca.pem -X POST https://core.vilicus.test:8443/__test/enrollment-token`.
3. On the phone, open `https://core.vilicus.test:8443/` and run, through remote debugging (`chrome://inspect` for Chrome, `about:debugging` for Firefox), the calls the driver makes, in its order: `await e22.probe()`, `await e22.enroll('<token>')`, `await e22.inspect()`, `await e22.startSession()`, `await e22.echo({})`, `await e22.requestAttacks()`, `await e22.concurrentEchoes(10)`; reload and repeat `inspect`, `startSession` and `echo`; close the browser from the task list, reopen it and repeat. Remote debugging evaluates through the DevTools protocol, so read the CSP result from `e22.probe()`, which the page computed at load (finding 2), and compare with `/control`.
4. Pairing: on a paired desktop browser, `await e22pair.issue()` on `/pair`; on the phone, in a profile with no device, `await e22pair.redeem('<code>')` on `/pair`; then the single-use, three-attempt, expiry, unknown-handle and relay steps of `browser/driver.mjs`, the relay ones on `https://relay.vilicus.test:8443/pair` after `POST /__relay/mode`, calling `POST /__test/reset-login-rate` before each redeem as the driver does.
5. Confirmations: create pending requests with `POST /__test/pending` for the phone's device id (`await e22.deviceId()`) and run `await e22.confirmationAttacks(a, b, c)` and `await e22.guardChecks(e, d)`.
6. Record each outcome against the driver's expected values, the browser versions, and the issue and redeem times.

## Result

1. `doc/decisions.md`: add a new decision record, "Browser device key, pairing code and light confirmation encodings", status Accepted, amending D35 and D38: "Context: AD-21 named the mechanisms of E22 but not their encodings, and E22 tested them on Chrome for Testing 155 and 154 and Firefox 158 and 157, headless (story 1.3, `spikes/browser-device-key/`). Decision: the per-request byte string is `vilicus/v1/req`, the 16-byte session id, the counter as 8 bytes big-endian, the method and the path with its query each preceded by its length as 4 bytes big-endian, and SHA-256 of the raw body; the browser signs SHA-256 of it with ECDSA P-256 and SHA-256, the Core accepts a counter only above the last accepted one, a refused request does not advance it, and the client sends the signed requests of a session one at a time. Sessions live in the Core's memory and do not survive a Core restart; the browser then opens a new one with its device key. A device public key is registered only with a proof of possession, an ECDSA signature by that key over `vilicus/v1/device-pop`, a length-prefixed context and the key. A pairing code is `HHH-SSSS-SSSS`: a 3-digit handle that names the pending pairing and is not secret, and an 8-digit secret drawn by the issuer, which is the OPAQUE password; a paired device registers it through signed requests and finishes only an issuance it started, and `vilicus device pair` registers it on the host. The Core signs each registration response with an identity key the issuing device pinned when it was registered (at enrollment, trust on first use; when paired by code, authenticated by the OPAQUE session key), and the device refuses an unsigned or wrongly signed response. OPAQUE uses ristretto255, 3DH with SHA-512, and Argon2id at 64 MiB, 3 passes and 4 lanes on the client, with one credential identifier per pairing. Every login start gets an OPAQUE answer, the fake one for an unknown, used, expired or exhausted handle, and is charged to its source address, at most 10 per 60 seconds; a start on a live pairing spends one of its 3 attempts; each run is kept under its own login identifier; the code is used up once the Core verifies the third OPAQUE message. The new browser binds its public key with an HMAC-SHA-256 tag under a key derived by HKDF-SHA-256 from the OPAQUE session key (info `vilicus/v1/pair/bind`) over the label, the handle, the login identifier and the key, plus a proof of possession. A light confirmation signs the canonical bytes of a Core challenge naming the request, its canonical hash, the device, a single-use nonce and an expiry; the signer decodes them as canonical CBOR and signs only a `vilicus/v1/light-confirmation` approving the request the member is looking at, for its own device; the Core verifies against the bytes it issued, a nonce approves only its request, from its device, once, and a device gets no challenge for another device's request. Lifetimes are checked on a monotonic clock. Consequences: an online guess succeeds with probability 3 in 10^8 per code; the lock-out after 3 attempts is a denial-of-service lever, since anyone who reaches the API can spend a live code's attempts, bounded by the uniform answers and the per-source limit, and the member then issues another code; a relay that breaks the binding also uses up the code; a relay present at a browser's enrollment can substitute the pinned identity key; the Core never uses a signature as an identifier, because ECDSA signatures are malleable; E22's desktop part passed and no fallback is taken there; Android is still to run."
