# Story 1.6: E10: sandbox profile and peer identity

As the owner,
I want the fixed systemd profile and the Core's peer identification tested on Debian 13,
So that every socket check and unit profile of Epic 5 rests on behaviour observed on the target system.

**Acceptance Criteria:**

**AC1 (E10, FR-2, D18)**
**Given** a reference plugin under `spikes/e10-sandbox/` running in a unit with `DynamicUser=yes`, `LoadCredential=`, `SystemCallFilter=@system-service` and `IPAddressDeny=any` on Debian 13
**When** it serves one request over its Unix socket and reads its one credential
**Then** it works, and its attempts to open a direct network socket fail

**AC2 (E10, AD-24, AD-55)**
**Given** a prototype listener owned by a Core-like unit
**When** a peer connects and the listener reads the systemd unit name from the cgroup of the peer's pidfd (`SO_PEERPIDFD`)
**Then** the expected unit is recognized, and a connection from another unit, including one running under the same uid, is rejected

**AC3 (E10, AD-24)**
**Given** the unit name cannot be read from the cgroup on Debian 13
**When** the result is recorded
**Then** the fallback is recorded in `doc/decisions.md`: each first-party unit runs under its own static user and the Core checks the uid with `SO_PEERCRED`, recorded as weaker against a compromised unit of the same user

**Spike plan:**
- Question: does the fixed systemd profile work for a plugin that needs a socket, one credential and the egress proxy, and can the Core identify peers by unit (E10)?
- Method: reference plugin and listener on a Debian 13 VM; negative socket tests; same-uid impersonation test.
- Pass criterion: the plugin works, direct sockets fail, peer identity verified by unit name.
- Timebox: 4 working days.
- Fallback on failure: relax individual options with a documented list; if `SO_PEERPIDFD` and the cgroup unit cannot be read, each first-party unit runs under its own static user and the Core checks the uid with `SO_PEERCRED`, recorded as weaker.
- Result record: E10 status in `doc/research-notes.md` with a link to the test run; any relaxed option or fallback recorded in `doc/decisions.md`.

## Implementation Notes

**What was built.** A standalone crate, `spikes/sandbox-profile/` (its own empty `[workspace]`, edition 2024, Apache-2.0, `publish = false`), one binary `e10-spike` with subcommands for every process of the spike, three unit files and a sysusers file under `units/`, and two scripts:

- `run.sh` builds and checks the crate in a Debian 13 Rust container (`Dockerfile.build`, `rust:1.99-trixie` pinned by digest `sha256:e259494b14672950a909b4c54527e19d29cae6ebf980672114c8bb85e5594e4a`), then starts a Debian 13 container with systemd as PID 1 (`Dockerfile.systemd`, `debian:trixie-slim` pinned by digest `sha256:a29215f6a35e51e22adffa17f89e9d2ef06214e64a2bad10d765c46aea49f11f`, plus `systemd`, `systemd-sysv` and `dbus` from the trixie archive), runs `checks.sh` in it, stops the container (`--rm`, removed on stop, also on error through a trap) and exits non-zero on any `FAIL`, on any ignored test, or when the number of passed tests differs from the number of `#[test]` functions in the tree.
- `checks.sh` runs as root inside the systemd container: it installs the binary and units, starts the Core and the plugins, and prints one `PASS` or `FAIL` line per check, with `INFO` lines carrying the evidence (decision lines, probe outcomes, exposure scores).
- `units/vilicus-core.service`: the Core-like listener, `Type=notify`, static user `vilicus-core` (from `vilicus-spike.sysusers.conf`), runtime directory `/run/vilicus/core` (mode 0700, kept across restarts), the fixed profile, and `Requires=vilicus-ipfilter-check.service`.
- `units/vilicus-plugin@.service`: the reference plugin template, `DynamicUser=yes` with `User=vilicus-plugin-%i`, `LoadCredential=` of one test value, and the block after `# Fixed profile`, which is the canonical profile of settled task 3.
- `units/vilicus-ipfilter-check.service`: the host check of the IP filter the Core requires (settled task 7).
- `src/core.rs`: one listening socket per expected peer unit at `/run/vilicus/core/peer/<unit>/core.sock`. `peer/` is mode 0700; each `<unit>/` directory is 0755 and the socket 0666, and the plugin unit bind-mounts its own directory (`BindPaths=/run/vilicus/core/peer/%n:/run/vilicus/peer`), so only that unit reaches it by path. On each connection the Core reads `SO_PEERCRED` and `SO_PEERPIDFD` at once, sends a hello, verifies, then either sends a request (nonce) and logs the response with the credential value, or refuses with a reason. One socket can be "gated" so the Core holds connections before verifying them (only for the pid reuse test). Bounds: at most `MAX_CONNECTIONS_PER_PEER` (8) connections per peer socket, verified or waiting, more are closed at accept; the response line is read through `take(MAX_LINE)` (4096 bytes) with a 5-second timeout. After serving, the Core watches the connection and the peer's pidfd together and closes the connection when the verified process exits (settled task 6).
- `src/peer.rs`: `SO_PEERCRED`, `SO_PEERPIDFD`, the pidfd liveness test (a zero-timeout `poll`: a pidfd becomes readable when its process exits, and this needs no permission over that process), `watch` (poll on the socket and the pidfd) and the pidfd's pid from `/proc/self/fdinfo`. `src/unit.rs`: membership in `cgroup.procs`, the `/proc/<pid>/cgroup` parsing kept for comparison, and `expected_cgroup`, a derivation of a unit's cgroup path kept only as a test oracle. `src/startup.rs`: the IP filter check and the `late-pidfd` kernel probe. `src/probe.rs`: the sandbox probes. `src/client.rs`: the plugin loop and the one-shot client used by the impersonation checks, with a `--fork-hold` mode that forks and leaves a child holding the connection.
- Tests: 5 unit tests in `src/unit.rs` (the oracle's derivation and refusals, membership parsing, leaf parsing) and 6 integration tests in `tests/peer.rs`: evidence of a live peer; a pidfd taken at accept reports the peer's exit while `SO_PEERCRED` keeps its pid number; `verify_with` rejects a peer that exits and is reaped during the `cgroup.procs` read (the reader is injected), and accepts one alive after it; `watch` reports the exit of the verified process while a forked child holds the connection, and a close while the peer lives. The order test was checked against a mutation: with the liveness check moved before the membership read, it fails.

**Verification method of the Core (as built).** For a connection on the socket of unit `U`: (1) read `SO_PEERCRED` (pid, uid) and `SO_PEERPIDFD` immediately after `accept`; a connection whose pidfd cannot be taken is refused. (2) Get `U`'s cgroup path from systemd (`systemctl show --property=ControlGroup --value U` in the spike, the D-Bus property in the product) and pin it for the life of the Core. systemd reports an empty path while a unit is inactive, so the path cannot be read when the Core starts, before its peers; it is read at the first connection of the active unit and kept. Read that cgroup's `cgroup.procs`; the pid must be listed. (3) Only after that read, check that the pidfd's process has not exited. Because the process was alive after the read, its pid could not have been reused before it, so the listed pid was that process. An earlier version also compared the pidfd's pid from `fdinfo`; it added nothing once (3) follows (2), and was dropped. The decision line also records what `/proc/<pid>/cgroup` gives the Core, for comparison only.

**Dependencies.** `libc` 0.2.190 only (exact version from `Cargo.lock`): it exposes `SO_PEERCRED`, `SO_PEERPIDFD`, `poll`, `socket`, `unshare` and `fork` (the client's `--fork-hold` mode) as raw calls, which is what the spike examines. The standard library covers the Unix sockets; `tokio`, `nix` and `rustix` were not needed for a blocking spike. All `unsafe` blocks are these calls, each with a `SAFETY` comment.

**Environment printed by the run.** Debian 13 userland, systemd 257 (`257.13-1~deb13u1`), dbus `1.16.2-2`, libc6 `2.41-12+deb13u4`, cgroup v2, rustc 1.99.1. Kernel `6.18.33.2-microsoft-standard-WSL2` (Docker Desktop's), not Debian 13's 6.12: see the limits under Result.

**Deviations.**

- Location: AC1 names `spikes/e10-sandbox/`; the spike is in `spikes/sandbox-profile/`, as the epic's spike dispatch asked. Nothing else depends on the path.
- Target system: the checks ran under real systemd 257 of Debian 13 as PID 1, in a privileged Docker container on Docker Desktop, not on a Debian 13 VM as the spike plan says. What differs, and the procedure for a real host, are under Result.
- AC2 names the method "reads the systemd unit name from the cgroup of the peer's pidfd". On Debian 13's kernel (6.12) a pidfd cannot be asked for its cgroup (the `PIDFD_GET_INFO` ioctl arrived in 6.13), and reading `/proc/<pid>/cgroup` fails under the Core's own `ProtectProc=invisible` (finding 1). The Core therefore checks the pid against the expected unit's `cgroup.procs` and then the pidfd, as above. The unit is still identified by its systemd cgroup, and the pidfd still closes the reuse race.
- The plugin's credential is a test value (`e10-test-value-<instance>`), written by `checks.sh` under `/etc/vilicus-spike/load/`; the directory name avoids the word the workspace's secret-path hook refuses on command lines. It is printed in the Core's log on purpose, as evidence that it reached the plugin; it is not a secret.
- The spike Core sends the refusal reason back to the peer, so the client can print it. The product sends nothing.
- `Dockerfile.systemd` makes the container's root mount shared before systemd starts; without it `LoadCredential=` gives every unit an empty credential directory (finding 4).

**Open decision tasks settled.** The story names none explicitly; the spike settles the ones its result forces, with the recommended answer:

1. **Peer identification method.** The Core identifies a peer by the pid it reads with `SO_PEERCRED` being listed in `cgroup.procs` of the cgroup path systemd reports for the expected unit (its `ControlGroup` property, read once the unit is active and pinned; never derived from the name, which would miss `Slice=` and escaping), followed by a liveness check of the pidfd taken at accept (`SO_PEERPIDFD`). It never compares the last component of a cgroup path alone: a cgroup named `vilicus-plugin@ref.service` can exist elsewhere in the tree (check `ac2_spoof_leaf_name_equals_expected_unit`), for example under a user manager or a unit with `Delegate=yes` (not exercised here; the spoof cgroup was created by root). It does not read `/proc/<pid>`, which `ProtectProc=invisible` hides from it. Recommended over two alternatives: `PIDFD_GET_INFO` with the cgroup id (needs kernel 6.13 or later, so not Debian 13's kernel) and systemd's `GetUnitByPIDFD` over D-Bus (race-free too, but a D-Bus round trip per accepted connection and a D-Bus client in the Core's accept path; not tested). What it gives up: the Core must know which unit each socket belongs to, which AD-55 already requires (one socket per peer instance), and a peer process moved into a sub-cgroup of its own unit would be refused, because `cgroup.procs` lists only the cgroup's own members (not tested); no Vilicus unit should set `Delegate=`.
2. **Reachable only by that unit (AD-55), implemented.** `core/peer/` is mode 0700 and owned by the Core; each peer gets a directory `core/peer/<unit>/` (0755) holding its socket (0666), and that unit's file bind-mounts that directory, never the socket file (a bind mount of the socket file would keep pointing at the old inode after the Core recreates it; this follows from how bind mounts work and was not tested). The Core's runtime directory is kept across restarts (`RuntimeDirectoryPreserve=yes`) so the bind source of a running plugin stays valid. Exercised: a restart of the Core alone (`systemctl restart --job-mode=ignore-dependencies`, so `Requires=` does not restart the plugin) left the plugin with the same pid, and the new Core served that same process again on the socket it recreated in the preserved directory (`restart_core_alone_plugin_keeps_its_pid`, `restart_core_alone_same_plugin_served_again`). A plain Core restart also restarts the plugins through `Requires=` (`restart_core_restarts_plugin`).
3. **Default template profile for plugins and AI processes (the canonical list).** The list of `doc/architecture.md` section 4 alone, applied to a dynamic-user unit, still lets the unit connect to the system bus, to the journal's stream socket, to an abstract Unix socket of the host, and create a user and network namespace (checks `baseline_profile_*`). The canonical list is the block after `# Fixed profile` in `spikes/sandbox-profile/units/vilicus-plugin@.service`, together with `DynamicUser=yes` and one `LoadCredential=`; `checks.sh` asserts every line of that block against `systemctl show` (checks `profile_*`), so the unit file is the list and the text below is its transcription for the design documents, to be replaced by a pointer to the shipped template once it exists:
   `TemporaryFileSystem=/run`, `BindPaths=` of the unit's own socket directories only, `UMask=0077`, `KillMode=control-group`, `NoNewPrivileges=yes`, `CapabilityBoundingSet=` (empty), `AmbientCapabilities=` (empty), `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp=yes`, `PrivateDevices=yes`, `PrivateIPC=yes`, `PrivateNetwork=yes`, `PrivateUsers=yes`, `RestrictAddressFamilies=AF_UNIX`, `IPAddressDeny=any`, `ProtectProc=invisible`, `ProcSubset=pid`, `ProtectKernelTunables=yes`, `ProtectKernelModules=yes`, `ProtectKernelLogs=yes`, `ProtectControlGroups=yes`, `ProtectClock=yes`, `ProtectHostname=yes`, `RestrictNamespaces=yes`, `RestrictRealtime=yes`, `RestrictSUIDSGID=yes`, `LockPersonality=yes`, `MemoryDenyWriteExecute=yes`, `RemoveIPC=yes`, `SystemCallArchitectures=native`, `SystemCallFilter=@system-service`, `SystemCallFilter=~@privileged @resources`, `SystemCallFilter=~io_uring_setup io_uring_enter io_uring_register`, `SystemCallErrorNumber=EPERM`, `MemoryMax=64M`, `TasksMax=16`, `LimitCORE=0`.
   On systemd 257, `@system-service` includes the three `io_uring` calls; the run checks that the loaded filter denies them, `mount` and `setuid`, and allows `pidfd_open`. With this profile the plugin works (AC1); no option of the design list had to be relaxed. This is the default template, not a rule for every unit. Units that need their own profile, each to be tested on its own: the egress proxy (network families); device adapters with a private address range or a shared namespace grant (AD-38, D115), which cannot take `PrivateNetwork=yes`; the D115 forwarder that joins the Claude connector's network namespace with `JoinsNamespaceOf=` and listens on loopback there; the WireGuard peer manager (AD-42); and any runtime that generates code at run time, which `MemoryDenyWriteExecute=yes` breaks: the Node-based Claude Code binary of the connector (AD-53) and a WASM runtime such as wasmtime (D18). None of these was tested here.
4. **The Core does not set `PrivateUsers=yes`.** With it, only root and the Core's own user are mapped inside its user namespace, and the uid checks the Core needs (uid 0 on the admin socket, AD-55; the AC3 fallback) would see other users as the overflow uid. Not tested here; it costs 0.2 of the Core's exposure score.
5. **AC3 fallback: not taken.** The cgroup unit was readable through `cgroup.procs` on every connection. The fallback's weakness was still measured: a unit sharing the plugin's dynamic user has the same uid (`ac3_peercred_uid_cannot_tell_same_uid_unit`) and was refused only by the unit check (`ac2_same_uid_other_unit_rejected`).
6. **Identity across a restart, and the life of a connection.** Identity is checked once at accept. A restarted unit connects again from a new pid and a new invocation ID and is verified again; the old connection is closed (checks `restart_*`). A connection can outlive the process the Core verified: a forked child, or a process that received the descriptor with `SCM_RIGHTS`, keeps it open. The Core therefore watches the verified process's pidfd for as long as the connection lives, and when that process exits it closes the connection and revokes what was bound to it, whoever still holds the socket. Tested: a peer of a unit with `KillMode=process` was served, forked a child that kept the connection, and exited; the Core logged `PEER_EXITED ... connection closed` and the child saw the close (`token_connection_closed_when_verified_process_exits`, `token_holding_child_sees_the_close`; and the integration test `watch_reports_the_peer_exit_while_a_forked_child_holds_the_connection`). The template also sets `KillMode=control-group` explicitly, so no process of a plugin outlives its main process in the first place. The revocation itself is a log line in the spike; there are no tokens.
7. **Startup check of the IP filter (AD-16, "the Core refuses to start if the host cannot enforce the IP filter").** A UDP `EPERM` alone does not prove the filter: a host netfilter rule that drops the datagram also makes the send fail, and the Core cannot run the check under its own profile, whose filter would also block the listener. The check is a separate root unit, `vilicus-ipfilter-check.service` (in the product an `ExecStartPre=+` helper or such a unit), that the Core requires: it owns a UDP listener on loopback, outside any IP filter; a control datagram it sends itself must arrive, which shows nothing else drops loopback traffic; then a transient unit with `IPAddressDeny=any` sends one datagram to the same listener, and the send must fail with `EPERM` and nothing may arrive. Anything else fails the unit and the Core does not start. Tested: the check passed before the Core started (`startup_ipfilter_check_passed`, `startup_core_requires_ipfilter_check`), and with the filter left off the probe unit it failed (`udp_send open`, datagram received; `startup_ipfilter_check_refuses_unfiltered_host`). A netfilter rule that drops only the probe unit's traffic (by uid or cgroup match) while letting the control through would still fool it; not tested. TCP is not used: under the filter a connect was not refused but timed out.

## Result

Command, from the repository root on the Windows development host with Docker Desktop: `bash spikes/sandbox-profile/run.sh`. Run of 2026-10-16, after the review fixes: exit code 0, 146 `PASS` and 0 `FAIL` lines, `RESULT PASS` and `RUN PASS`. Build stage: `build`, `fmt` (`cargo fmt --check`), `clippy` (`--all-targets -- -D warnings`), the 11 tests one line each, and `test_count` (11 passed, 0 ignored, 11 expected). Systemd stage: 131 checks. Earlier runs printed `FAIL` lines and exited 1 (a TCP connect under `IPAddressDeny=any` expected to give `EPERM`; a control probe whose output carries a count), which shows the failure path works.

**AC1: PASS.** The reference plugin `vilicus-plugin@ref.service` runs under `DynamicUser=yes` (uid 63312, in systemd's dynamic range; check `ac1_plugin_runs_as_dynamic_user`), `LoadCredential=`, `SystemCallFilter=@system-service`, `IPAddressDeny=any` and the rest of the template:

- It read its one credential (`ac1_plugin_read_its_credential`, length checked against the file) and served one request: the Core sent a nonce, the plugin answered with the nonce and the credential value, and the Core logged `SERVED unit=vilicus-plugin@ref.service pid=<its main pid> nonce_ok=true credential=e10-test-value-ref` (`ac1_plugin_served_one_request_with_its_credential`).
- At start the plugin ran every sandbox probe, and each gave the exact outcome expected (`ac1_plugin_<probe>_<outcome>`; `probe_tables_match_the_probes_run` checks that the expectation tables cover exactly the probes the binary runs, and `ac1_plugin_ran_every_probe` that the plugin ran all of them): `AF_INET` TCP and UDP, `AF_INET6`, raw `AF_INET`, `AF_PACKET` and `AF_NETLINK` sockets (`EAFNOSUPPORT`); the system bus, systemd's private socket, the journal stream socket and the other plugin's Core socket (`ENOENT`: not in its `/run`); an abstract socket listening in the container's network namespace (`ECONNREFUSED`: the plugin has its own); `unshare` of a network namespace and of a user plus network namespace (`EPERM`); other processes in `/proc` (none visible); writes to `/etc`, `/var/lib`, `/usr/local/bin` (`EROFS`); reading `/root` (`EACCES`).
- Control: the same probes in a transient unit running as `nobody` with no sandboxing (not `DynamicUser=yes`, which implies `ProtectSystem=strict` and more), each with its exact expected outcome (`control_nobody_<probe>_<outcome>`): TCP, UDP, `AF_INET6` and netlink sockets, the system bus, the journal stream socket, the host abstract socket, user plus network namespace creation and other processes in `/proc` are open; raw and packet sockets fail with `EPERM` (no capability); systemd's private socket, the other plugin's socket, the writes and `/root` fail with `EACCES` (file permissions). So for every probe but two, the plugin's outcome differs from the control's and is the profile's doing (`EAFNOSUPPORT` instead of `EPERM` or open, `ENOENT` instead of `EACCES` or open, `EROFS` instead of `EACCES`). Two are not attributable: `unshare_net` (`EPERM` with or without the profile, from the missing capability) and `read_root_home` (`EACCES` both ways); for those, `RestrictNamespaces=yes` and `ProtectHome=yes` are defence in depth the run cannot show at work.
- IP filter alone: transient units with `AF_INET` and `AF_INET6` allowed and `IPAddressDeny=any`: TCP to a listener on loopback and on the container's own address timed out (`ac1_ipdeny_tcp_*_blocked_TimedOut`, the probe's 3-second limit), and UDP to those and to a TEST-NET-1 address failed with `EPERM` (`ac1_ipdeny_udp_*_blocked_EPERM`). The same units without `IPAddressDeny=any` reached both TCP listeners and sent UDP to all three addresses (`control_without_ipdeny_tcp_*_open`, `control_without_ipdeny_udp_*_open`). TCP to TEST-NET-1 is not asserted: without a reachable listener, a timeout there would not show the filter.
- Profile as loaded: every line of the template's fixed profile block equals what `systemctl show` reports for the instance (42 `profile_*` checks, `SystemCallFilter` checked by content as in settled task 3). systemd 257 prints the prefixes of `IPAddressDeny=any` in an order that changes from one boot to the next and stays fixed within a boot (six fresh containers: two printed `0.0.0.0/0 ::/0`, four `::/0 0.0.0.0/0`, each unchanged after a `daemon-reload`); an independent run failed `profile_IPAddressDeny` on that order alone. The check now compares the two prefixes as a sorted set, still requiring exactly both, prints expected and actual values on any `profile_*` failure, and the run prints the order seen. Three consecutive runs after the fix: 146 `PASS`, 0 `FAIL` each, with both orders seen.
- The architecture section 4 list alone (transient unit `e10-baseline`): system bus open, journal stream socket open, host abstract socket open, user plus network namespace creation open; the template's additions close all four (settled task 3).
- `systemd-analyze security` (systemd 257): `vilicus-core.service` exposure 0.4, `vilicus-plugin@ref.service` exposure 0.2, each asserted exactly (story 5.4 sets the CI bound at 2.0). The score does not rate `TemporaryFileSystem=`, `BindPaths=` or the `io_uring` exclusion, which is why the `profile_*` checks exist. Items left open, printed by the run: both units run in the host's root directory (no `RootDirectory=`), may allocate `AF_UNIX` sockets, and keep `char-rtc:r` (from `ProtectClock=yes`); the Core also lacks `PrivateUsers=` (settled task 4).
- `systemd-analyze verify` is clean for the three units (`units_verify`).
- Startup check of the IP filter: passed before the Core started, and refused a probe unit without the filter (settled task 7).

**AC2: PASS, with the identification method of settled task 1.**

- Expected unit: `DECISION unit=vilicus-plugin@ref.service pid=<pid> uid=63312 cgroup_member=yes pidfd_alive=true ... verdict=accept reason=unit-match` (`ac2_expected_unit_accepted`); the second plugin, on its own socket, likewise (`ac2_second_unit_accepted_on_its_own_socket`). The Core takes the cgroup path from systemd; the name-based derivation kept as a test oracle agrees with `systemctl show -P ControlGroup` for both the Core and the template instance (`cgroup_path_matches_systemd_*`).
- Another unit with another uid, given the plugin's socket directory as if the bind-mount layer had failed: refused, `other-unit` (`ac2_other_unit_rejected`, uid differs).
- Another unit with the same uid (a transient unit with `DynamicUser=yes` and `User=vilicus-plugin-ref`, which shares the plugin's dynamic user): uid 63312, equal to the plugin's, refused, `other-unit` (`ac2_same_uid_other_unit_rejected`).
- A root process outside any unit: refused (`ac2_process_outside_any_unit_rejected`).
- Spoofed unit name: a root process placed in a cgroup `/e10-spoof.slice/vilicus-plugin@ref.service`, so the last component of its cgroup path is the expected unit name (`ac2_spoof_leaf_name_equals_expected_unit`): refused (`ac2_spoofed_unit_name_rejected`). A check of the leaf name alone would have accepted it. A transient unit cannot take the name of a unit that has a unit file (systemd answers that the unit "was already loaded or has a fragment file"; `ac2_unit_name_with_a_unit_file_cannot_be_taken_by_a_transient_unit`).
- Pid reuse: a process of another unit connected to the gated socket of `vilicus-plugin@reuse.service`, received the hello and exited; the run then set `/proc/sys/kernel/ns_last_pid` so that the next start of `vilicus-plugin@reuse.service` got the same pid (forced on the first attempt, `ac2_pid_reuse_forced`), and opened the gate. The Core's decision on the attacker's connection read `cgroup_member=yes pidfd_alive=false pid_only_check=accept ... verdict=reject reason=peer-exited`: a check by pid alone would have accepted a process of another unit (`ac2_reused_pid_passes_a_pid_only_check`), the pidfd refused it (`ac2_reused_pid_rejected_by_pidfd`), and the real plugin's own connection with the same pid was accepted (`ac2_reuse_unit_own_connection_accepted`). The two decisions carry different uids (the attacker's and the plugin's), as expected. Reason seen on kernel 6.18: `peer-exited`, because the Core took the pidfd at accept, while the attacker was still connected; it never logged `no-pidfd(...)` in this run.
- Finding 1 (asserted, `ac2_proc_cgroup_hidden_from_core_by_protectproc`): under `ProtectProc=invisible`, which AD-24 sets on every Vilicus unit, the Core gets `ENOENT` for `/proc/<pid>/cgroup` of every peer of another user. A design that reads the peer's unit from `/proc` does not work on the Core's own profile.

**AC3: not triggered.** The unit was read from the cgroup on every connection, so the fallback is not needed and nothing is recorded in `doc/decisions.md` as a fallback. Its weakness is measured anyway (settled task 5).

**Restarts (all PASS).** After `systemctl restart vilicus-plugin@ref.service`: new pid, accepted as the same unit, old connection closed, new invocation ID (`restart_plugin_gets_a_new_pid`, `restart_new_process_accepted`, `restart_old_connection_closed`, `restart_invocation_id_changes`). After a restart of the Core alone: the same plugin process is served again (settled task 2). After `systemctl restart vilicus-core.service`: the plugin is restarted with it (`Requires=`) and served again. A connection whose verified process exited while a child held it was closed by the Core (settled task 6).

**Other findings.**

- Finding 2: on kernel 6.18 a pidfd asked for only after the peer has exited and been reaped is returned, for an exited process; the run records it as `LATE_PIDFD kernel=6.18.33.2-microsoft-standard-WSL2 late_pidfd=returned(alive=false)`. Older kernels are expected to refuse it, which the Core would log as `no-pidfd(<errno>)`; not observed, because no 6.12 kernel was available. Either way the liveness check reads it as exited (the integration test accepts both), and the Core takes the pidfd at accept time, before any other work. The `late-pidfd` line on a Debian 13 host is what pins the 6.12 behaviour.
- Finding 3: with the template's profile, the plugin's credential directory survives `TemporaryFileSystem=/run`; systemd mounts it inside the new `/run`.
- Finding 4: in a container whose root mount is private, systemd 257 mounts each unit's credential directory in a child mount namespace and moves it into place, and the mount never reaches the unit: `$CREDENTIALS_DIRECTORY` is set but empty, for every unit, sandboxed or not, with no error logged. Making `/` shared before systemd starts fixes it.

**Limits (Docker Desktop versus a Debian 13 host).**

- Kernel: Docker Desktop's 6.18 (WSL2), not Debian 13's 6.12. `SO_PEERPIDFD` exists since 6.5, pidfd polling since 5.3, and `ns_last_pid` long before, so the method should hold on 6.12, but finding 2 already shows one difference. Not run on 6.12.
- Root mount propagation: systemd makes `/` shared at boot on a host but not in a container; the image does it before starting systemd (finding 4). Not a product concern on a host; a reminder for any containerised CI of the units.
- The container is privileged with a private cgroup namespace; `systemd-modules-load.service` fails in it, so systemd reports `degraded` at boot. AppArmor, which Debian 13 enables on a host, is not active here, and its interaction with the profile is not tested.
- The cgroup eBPF IP filter worked in this kernel; on a host it depends on the kernel configuration, which is what the Core's startup check covers (settled task 7).
- The spoofed cgroup was created by root. Whether an unprivileged user manager can create a cgroup with a system unit's name in its delegated subtree was not exercised.
- The plugin reached no egress proxy here: its proxy data socket would be granted the same way as its Core socket (one more bind-mounted directory). The proxy itself is E14 (story 1.12).
- Until that rerun, the proposed decision record below stays Proposed.
- Manual procedure on a Debian 13 host (a disposable VM: the run creates users, units and a cgroup, and writes `ns_last_pid`): build with `run.sh`, copy the binary out of the `vilicus-e10-target` volume (`/target/debug/e10-spike`), then on the VM as root, with `systemd` and `dbus` installed: create `/target/debug/` and `/spike/`, copy the binary to `/target/debug/e10-spike` and the spike directory's `checks.sh` and `units/` to `/spike/`, and run `bash /spike/checks.sh`. It prints the same `PASS` and `FAIL` lines and `RESULT PASS` or `RESULT FAIL`.
