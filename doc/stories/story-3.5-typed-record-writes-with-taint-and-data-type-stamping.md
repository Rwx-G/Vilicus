# Story 3.5: Typed record writes with taint and data type stamping

As a project maintainer,
I want modules to write only through a typed record API on which the Core stamps the envelope, taint and data types,
So that no module can choose its own provenance label and derived data never launders into `trusted`.

**Acceptance Criteria:**

**AC1 (FR-18, AD-6)**
**Given** the typed record API of `vilicus-module-api`
**When** a module inserts, updates by id with an expected `rev`, or deletes by id
**Then** the Core stamps `id`, `source`, `author`, `created_at`, `updated_at` and bumps `rev` in the write transaction
**And** an update whose expected `rev` differs from the stored one is refused.

**AC2 (AD-7, I9)**
**Given** a write by a non-member principal deriving a record
**When** it does not declare its input record ids
**Then** it is refused
**And** when it declares them, the stored taint is the maximum of the inputs' taints, any `member` or `external` input storing `external`.

**AC3 (D103, I43)**
**Given** a derived record
**When** it is written
**Then** its stored `data_types` is the union of its inputs' sets, computed by the Core
**And** a write declaring a smaller set is refused (storage property test over random input sets).

**AC4 (FR-20, D70, D99, I35)**
**Given** a write a member makes or explicitly approves
**When** it is stored
**Then** its structured fields are stored `trusted` with that member as `author` and provenance to its inputs
**And** free text drafted in a tainted session stays `external` even when edited, while text the member wrote in full in an empty field is stored `trusted`.

**AC5 (D104, I35)**
**Given** a member-written field that contains 8 or more consecutive words of the assistant's draft
**When** it is stored
**Then** it is stored `external`, by a verbatim word-sequence test and not an edit ratio.

**AC6 (AD-6, AD-7, I21)**
**Given** any write
**When** it is stored
**Then** stored taint is never `member`
**And** a write whose principal is `Plugin` is stored `external` whatever taint the plugin claims.

## Implementation Notes

**What was built**
- `crates/vilicus-types/`:
  - `rev.rs`: `Rev`, a record's revision, 1 at insert (`Rev::FIRST`) and one more at each update (`next`, `None` past `i64::MAX`); `Rev::new` refuses a value below 1, and the envelope check reads `rev` through it.
  - `taint.rs`: `EffectiveTaint::for_viewer(stored, author, viewer)`, the read-time view of `doc/architecture.md` section 5.4 rule 4 (a `trusted` record authored by a member other than the viewer reads as `member`; with no viewer, every member-authored `trusted` record does). `TextTaint`, the closed set `trusted` < `approved_draft` < `external` (`as_taint`: an approved draft counts as `external`). `RecordLabels`, a record's two labels: `taint` for its structured fields and `text_taint` for the record read with its free text, never below `taint` (`new` refuses such a pair, `of` raises the text label to the structured one); `overall` (the stricter, `text_taint`), `is_approved_draft`, `most_restrictive` label by label, and `for_viewer(author, viewer, Projection)`, where a `Projection::Structured` read sees `taint` and a `Projection::WithFreeText` read sees `text_taint`. Story 10.5 reuses both for reads.
- `crates/vilicus-module-api/`:
  - `records.rs`, the module port (AD-9): `trait Records` with `insert(table, fields, inputs) -> Written`, `update(table, id, expected: Rev, fields, inputs) -> Written`, `delete(table, id)`. A module gives the values of declared fields and the ids of the records the write is derived from; no method takes an envelope value, and none runs SQL. `WriteError` names the declaration's tables and columns only. `Id` and `Rev` re-exported.
  - `declaration.rs`: `ENVELOPE` gains `text_taint` (`TEXT NOT NULL`) after `taint`; the registry's statement comparison (D144), the field-name rule and the fuzz test derive from it.
- `crates/vilicus-core/src/record/`:
  - `call.rs`: `run_call(handle, module, call, stamper, body)`, one call of a module in one `BEGIN IMMEDIATE` transaction on the module file's write handle; `body` receives a `&mut dyn Records`. The call commits only when `body` returns `Ok` and no write was refused; the first refused write ends the call (every later write gets `CallRefused`), an error of `body`'s own is `RecordError::Aborted`; a refusal, a failed `COMMIT` or a panic, in `body` or in the Core, rolls back. `Call { principal, source, session, consumed, authority, read, implicit_inputs }`, built by the pipeline (Epic 10): `session` is the session's taint (section 9.3); `consumed: Consumed { data_types, taint: EffectiveTaint }` what an AI or plugin session read, `Consumed::NOTHING` otherwise; `Authority::OwnAction { member }`, `Approved { member, written, drafts }` or `Unapproved { author, acting_for }`; `read` holds the provenance of records of other files the call read; `implicit_inputs` the records every write of the call derives from without the module naming them (a rule's or a playbook's definition, an event's emitting record). `check_call` refuses (`InconsistentCall`), before any write, an authority that does not fit the principal, a `source` outside the principal's closed mapping, and a consumption that does not fit the principal or its session. `Stamper` supplies the time and the random bits of a new UUIDv7. `CallOutcome { value, changes }`, each `RecordChange { table, id, before, after, inputs }` being what Story 3.6 journals, `inputs` listing the declared then the implicit inputs.
  - Per write: insert stamps `id`, `source`, `taint`, `text_taint`, `data_types`, `author`, `created_at` = `updated_at` = now, `rev` 1; update reads the stored row in the transaction, refuses a stale `expected` or a missing record, restamps `source`, both labels (never lower), `data_types`, `updated_at` and `rev` + 1, and `author` only when it keeps no value the record holds; delete reads the stored `rev` and deletes. Inputs are resolved by the Core, each id once: a record of the file is read in the transaction with its free text, in whichever of the module's tables holds it, its envelope held to its stored form; otherwise a record of `Call::read`; otherwise `UnknownInput`; then the call's implicit inputs. `RecordProvenance { id, labels, author, data_types, free_text }`, whose `Debug` leaves the text out.
  - `provenance.rs`, the stamp:
    - labels: a `Plugin` or `Adapter` principal stores both `external`, whatever else holds. A member's own action or approval stores `taint` `trusted`; its free text is `trusted`, except text that repeats a run of `DRAFT_RUN_WORDS` (8) words of an input that is not `trusted` for that member (`external`), and, for an approval from a tainted session, text other than one the member wrote in full that repeats no run of a draft (`approved_draft`). Any other call stores as `taint` the most restrictive of its session taint, of each input's `text_taint` as `acting_for` sees it (`member` and `external` storing `external`), of the record an update changes, and, for `AiTask` and `Plugin`, of the session's consumed taint; its free text takes the same label, except that free text an `AiTask` writes is `external`. An update stores, label by label, the most restrictive of what it computes and of the record's stored labels.
    - `repeats_a_run`: words are the maximal runs of alphanumeric characters, compared in lowercase; a run is taken within one source.
    - data types: the record kind's declared set for an own or approved write, otherwise the union of the inputs' sets (the declared set without inputs, a plugin's or adapter's); every write of `AiTask` and `Plugin` adds the session's consumed types (`floor`, which the row writer also enforces); an update adds the record's stored set; a type the kind does not declare is refused (`UndeclaredDataType`).
    - author: the member for an own action or an approval; for an unapproved write, the author the call gives; on update, the stored author while the update keeps a value the record holds (a field it does not give, a value given unchanged, free text repeating a run of the record's own free text).
    - inputs: required (`MissingInputs`) for an unapproved write of any principal but `Plugin` and `Adapter` that has neither declared nor implicit inputs.
  - `mod.rs`: the row writer split into `insert_row` and `update_row`, which run inside a transaction their caller holds, and `insert` and `update`, which keep a transaction of their own for the tests and the write path fuzz test. Both refuse an envelope whose `data_types` misses a type of the write's floor (`DataTypesBelowInputs`) and an envelope giving one label without the other (`MissingColumn`) or a `text_taint` below `taint` (`InvalidEnvelope`). `check_stored_rows` checks the pair of every stored row. `in_write_transaction` holds the transaction in a guard that rolls back when dropped uncommitted.
  - `envelope.rs`: the `text_taint` rule and `check_labels`; `rev` checked through `Rev::new`.
  - `fuzz.rs`: valid envelopes carry a valid pair of labels; `text_taint` outside its set, and a `text_taint` below `taint` on insert and update, are refused cases.
  - `tests_call.rs`, the tests of this story; `tests.rs` exposes its helpers to it and wraps the row writer for its own tests.
- `crates/vilicus-core/src/registry/tests.rs`: the literal module's statement carries `text_taint`; `text_taint` of another shape, in another order or with a `DEFAULT` fails registration.
- No dependency and no crate graph edge added: `vilicus-module-api` and `vilicus-core` already depend on `vilicus-types`; `Cargo.lock` is unchanged.

**Decisions and why** (the review's coordinator decisions A, B, C1 and C2 are binding; drafted texts under Open points)
- *Two labels per record* (decision A, replacing the one taint per record of the first pass): `taint` labels the structured fields, `text_taint` the record read with its free text. `text_taint` is defined as the stricter of the structured label and the free text's own, so it is never below `taint`, a record without free text has `text_taint` = `taint`, and "the stricter of the two" is always `text_taint`: a derivation counts it, a reader of free text sees it, a reader of structured fields only sees `taint`. What it gives up: a record whose structured fields become `external` makes its free text `external` too, even an approved draft.
- *Marking an approved draft* (minor 8, PRD DC-59): the read path must tell a member-approved assistant draft, which reaches a planner as quoted data, from other `external` free text, which reaches it only through the reader (D104; without a mark, approved drafts would again be unreadable to every planner, the problem D104 solved). The minimal sound representation is a third value of `text_taint`, `approved_draft`, between `trusted` and `external`, rather than a boolean column: one column, and the most restrictive of several labels stays a maximum, so a record whose free text mixes an approved draft with any other `external` text is `external` and goes through the reader. `approved_draft` counts as `external` everywhere else (`TextTaint::as_taint`): derivation, session taint, promotion. Which approved text is a draft: from a tainted session, a draft as drafted, an edited draft, and a member-written text repeating 8 words of a draft (D99, D104).
- *Model text no member approved* (decision B): `external` even from a clean session (section 5.4 rule 2, AD-6 "model free text no member approved"); the structured fields of the same write follow the inputs and the session. Text a rule, a playbook, an event consumer or a display computes is not model text and follows its inputs (rule 1).
- *Updates never lower a label* (decision C1): label by label, an update stores the most restrictive of its computed labels and the record's, so an own-action or web update never promotes `external` to `trusted`, even a full rewrite; promotion stays with the host CLI (D45, D112). The first pass's "rewriting every field makes it `trusted`" is withdrawn.
- *An update keeps the author of what it keeps* (M1): the stored `author` stays while the update keeps a value the record holds: a field it does not give, a value it gives unchanged (a web form resubmitting a record, M2), or free text repeating 8 words of the record's own free text, which is still that text, edited. Only an update rewriting every value the record holds restamps the author; `source` always names the last writer. What it gives up: Ella's change of a field of Noé's note is attributed to Noé, so Noé's assistant reads it `trusted`; structured fields do not taint a session (D70), and a free-text change keeps Noé's authorship only when it keeps 8 of his words.
- *Copying text that is not `trusted` for the member* (M2, section 5.4 rule 5): a member's own or approved free text repeating 8 consecutive words of an input whose `text_taint`, as that member sees it, is not `trusted` (an `external` record, or another member's) is `external`; the structured fields stay `trusted`. Another member's input counts, as it does for a derivation (AD-7), because a member's `trusted` copy would hand that member's assistant the other adult's text as trusted. The copy test is not run against the stored record of an update: an `external` record stays `external` by decision C1, and a copy of another member's stored text keeps that member as author (M1), so the copy reads `member` to the editor; the test would be dead code.
- *Data types* (decision C2, M3): an own or approved write holds the record kind's declared set (a member typing a record holds whatever the kind may hold); an `AiTask` or `Plugin` write folds in the types its session consumed, so declared inputs only add; a consumed type the kind does not declare refuses the write, approved or not (fail-closed, D103), rather than narrowing the set. What it gives up: wider sets on member records, which the provider policy reads; and an AI session that read a type the target kind does not declare cannot write there, which E23 may count.
- *Consumed taint* (minor 6): `Consumed::taint` is the most restrictive effective taint the session saw, `member` for another member's structured fields included (they do not taint the session, D70, yet a record derived from them is `member` derived and stores `external`, AD-7). `check_call` holds it to the session: a tainted session consumed something not `trusted`, an untainted one nothing `external`, and only `AiTask` and `Plugin` consume; for an AI session `session` is then redundant with it for the stored taint, but an event's `session` (its emitting call's taint, AD-27) still counts alone.
- *Implicit inputs* (minor 7): rules, playbooks and event consumers derive from records their call carries, `Call::implicit_inputs` (the definition an adult validated, the emitting record), which stand for declared inputs; a rule Ella validated, acting for her, stores `trusted` with her as author. The Core keeps them in the call; the pipeline of Epic 10 supplies them.
- *The source of a call* (nit 9): a closed mapping from the principal: `member(<the acting member>)` for `Member` and `Cli`; `ai_task` or `scheduled_task` for `AiTask` (a scheduled task acts as an AI task); `plugin` or `import` for `Plugin` (an import arrives as outside content); its own kind for `Event`, `Rule`, `Display`, `Adapter` and `Playbook`; `system` and `module(<name>)` are the Core's own writes, which no call makes.
- *A panic rolls the call back* (minor 5): the write transaction is a guard that rolls back when dropped uncommitted, so a panic unwinding through `run_call`, in module code or in the Core, leaves no transaction open; catching it and marking the module faulted stays the boundary of AD-9 (Story 3.9).
- *Which writes must declare inputs*: every insert and update of a call no member made or approved, except a plugin's and a device adapter's, whose writes are content from outside the household, stored `external` whatever their inputs (AD-7, I21); implicit inputs count. A declaration is at least one id; an update may name the record itself.
- *Where inputs come from*: the module names ids; the Core reads each one's labels, author, data types and free text, from the written file in the transaction, or from `Call::read`, the provenance the Core kept when it served the call a record of another file (no transaction spans two files, AD-5). An id the Core does not know is refused, so a module cannot invent a lower-labelled input.
- *Effective taint of inputs*: an input reads as the member the call acts for sees it (`acting_for`), the read-time view of section 5.4; with no such member (an adapter, a display), every member-authored `trusted` input reads as `member` and stores `external`.
- *The author of an unapproved write* is the pipeline's (`Unapproved::author`): the conventions name it for `Member`, `Cli`, rules, displays and adapters; for an AI task, the member it acts for, so its writes read as `member` to the other adult, like that member's own data.
- *The approval's texts*: `written` are the texts the member wrote in full in an empty field, `drafts` the model's texts as drafted; a free-text value is `trusted` only when it equals one of `written` and repeats no 8-word run of a draft.
- *The verbatim test* (D104 says "8 consecutive words", "verbatim"): words are maximal runs of Unicode alphanumeric characters, compared in lowercase, so spacing, punctuation and case do not hide a copy; a run lies within one source. What it gives up: a copy with one word changed every 7 words passes, and a member retyping a draft of fewer than 8 words stores it `trusted`, which is the threshold D104 chose.
- *One transaction per call*: AD-9 has handlers run on the writer thread and a panic roll back "the transaction"; Story 10.7 undoes every record one write changed. A refused write therefore ends the call, even when module code swallows the error, so a call never commits half of its writes.
- *Clock and ids*: the Core has no durable clock (AD-30, Story 5.2) nor a random source yet, so `run_call` takes a `Stamper`; `vilicus-types` stays pure (`Id::new_v7` takes both).
- *Where it lives*: the port in `vilicus-module-api`, the implementation and the provenance rules in `vilicus-core` (AD-1: the Core decides). `run_call` is public but needs a `Handle<Write>`, which only the Core opens, so no crate outside the Core can write a row.

**Deviations**
- *AC1, "the Core stamps ... `author`"*: on update the Core keeps the stored author while the update keeps a value the record holds (M1); it restamps `source`, which names the last writer.
- *AC1, "deletes by id"*: without an expected `rev`, as AD-9 writes it; the deleted record's `rev` is in the call's outcome for the journal.
- *AC2, "a non-member principal"*: read as a call no member made or approved; a member's approval of an AI task's request is a member's write (AC4), and plugins and adapters write content from outside the household rather than derive it. *"The stored taint is the maximum of the inputs' taints"*: the structured label is; each input counts with its `text_taint`, the call's implicit inputs and, for `AiTask` and `Plugin`, what the session consumed count too (decision C2), and an AI task's free text is `external` (decision B).
- *AC3, "its stored `data_types` is the union of its inputs' sets"*: for an unapproved write of a principal other than `AiTask` and `Plugin`; an `AiTask` or `Plugin` write holds that union and the types its session consumed, and a member's own or approved write its kind's declared set (decision C2). *"A write declaring a smaller set is refused"*: no module and no model can declare a set, since the port has no such parameter (I43); the refusal is the row writer's, for an envelope any Core code computes, shown by the property test on insert and update.
- *AC4, "provenance to its inputs"*: the call's outcome lists, for each record, the inputs of its write (`RecordChange::inputs`), which the tests check; storing them is the `_journal` row of Story 3.6 (AD-26).
- *AC4, AC5, "stored `external`"*: stored as `text_taint` `approved_draft`, an `external` label that a planner reads as quoted data (D104), with the structured fields `trusted`.
- *AC6, "whatever taint the plugin claims"*: a plugin has no way to claim one: the port takes no envelope value, and an envelope column given as a field is refused (`UnknownColumn`). The stored labels of a plugin's write are `external` even when its call is approved, its session clean and its inputs `trusted`.
- The first pass's deviation "AC4, one taint per record" is withdrawn: with `text_taint`, AC4 is met as written.
