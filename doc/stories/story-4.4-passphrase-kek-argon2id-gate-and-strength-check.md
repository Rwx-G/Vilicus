# Story 4.4: Passphrase KEK, Argon2id gate and strength check

As a member,
I want my passphrase to unwrap my data key through Argon2id only after I have proven my first factor, and to be refused when it is weak,
So that unlock is costly to guess offline and cannot be used to exhaust the host.

**Acceptance Criteria:**

**AC1 (FR-11, AD-18, E12)**
**Given** a member's passphrase
**When** the passphrase KEK is derived
**Then** Argon2id runs with the parameters set by E12, and those parameters are stored in the wrapper header
**And** a wrapper whose header parameters fall below the memory floor recorded by E12 is refused

**AC2 (FR-11, AD-9)**
**Given** an unlock request
**When** no successful first factor (passkey login, or the host CLI path) is attached to it
**Then** Argon2id is never started
**And** derivations run on the Core's bounded blocking pool under a global concurrency limit, so a burst of requests beyond the limit waits or fails with a retryable error instead of starting more derivations (test with more concurrent requests than the limit)

**AC3 (FR-11, E12)**
**Given** the reference host (4 cores, 8 GB RAM, SSD, no GPU, Debian 13 amd64)
**When** a single unlock runs with the E12 parameters
**Then** key derivation completes within the 2-second unlock target (PRD assumption), measured by a benchmark kept in the repository
**And** if E12 took its fallback, the lower concurrency limit and the longer unlock it recorded are the named constants, with the memory floor unchanged

**AC4 (FR-7, FR-110)**
**Given** a candidate passphrase at enrollment or at a passphrase change
**When** the Core checks its strength
**Then** the check uses French and English dictionaries and refuses a passphrase below the threshold with a message key, in the Core, never only in the browser
**And** the candidate passphrase is never logged or stored outside the derivation

**AC5 (D128, FR-11, E12)**
**Given** a version 1 passphrase wrapper
**When** it is written
**Then** it uses Argon2id version 0x13, t = 3, p = 4, m = 384 MiB, a 16-byte random salt and a 32-byte KEK, over the passphrase normalised to NFC and encoded as UTF-8, as named constants in `vilicus-types`; m is provisional until the reference-host run of E12 replaces it
**And** a header is refused before it is queued when its cost is below the floor (at least one RFC 9106 section 4 option in both memory and passes, so m >= 64 MiB and t >= 3 below 2 GiB) or above the ceiling (m 1 GiB, m times t 4 GiB, p 8), as the test `unlock_refuses_a_bad_header_before_queuing` of Story 1.8 does while the only slot is held
**And** a wrapper written with an older cost is unlocked with its header's cost and rewritten with the current one at that unlock, which then costs two derivations.

**AC6 (D128, AD-9, DC-80)**
**Given** every Argon2id derivation of the Core (passphrase, backup secret, admin recovery code)
**When** it is requested
**Then** it goes through one limiter: at most two derivations at once, through a FIFO tokio `Semaphore` acquired before the blocking-pool permit so no async worker thread blocks; a request that cannot start within 4 seconds is refused as retryable and the time it waited is never returned to the client; one request in flight per member; after a failed passphrase the member's next attempt is delayed with an exponential backoff
**And** the Argon2id working memory never exceeds the limit times m, at most 1 GiB, checked at compile time over the constants and the ceiling (test with a burst of more simultaneous requests than the limit: arrival order kept, refusals after 4 seconds, peak memory bounded).

**AC7 (D128, D129, D131)**
**Given** the `argon2` crate
**When** a derivation runs
**Then** it is `argon2` `=0.6.0` without its `parallel` feature, so `rayon` is not in the Core's tree (a dependency check fails if it appears): the four lanes run in order on one blocking-pool thread, under the key-operation guard of Story 4.2 AC8
**And** it derives with `hash_password_into_with_memory` into a buffer the Core owns and wipes after each derivation, on success and on error, because `hash_password_into` frees its blocks without wiping them (Story 1.8, "Memory wipe"); a test checks the buffer is all zeros afterwards.

**AC8 (D129, D28)**
**Given** the exception to D28 for `argon2` and `blake2`
**When** the passphrase-wrapping code is written
**Then** an internal security review of both crates and of Vilicus's use of them, assisted by the most capable model available, is committed first, with every finding closed or accepted
**And** CI runs the RFC 9106 Argon2id vectors, the reference implementation's Argon2id vectors without secret or associated data ("password", "somesalt", m = 64 MiB, t = 2, p = 1), a cross-test against the reference implementation phc-winner-argon2, a dev-dependency only, that agrees on 10 000 random cases over p in {1, 2, 4, 8}, and OpenSSL 3.5's `EVP_KDF-ARGON2` as a second oracle; no document calls the crate audited (gate E12-3).

**AC9 (E12, D128)**
**Given** the reference host
**When** E12 runs there with the adopted model, by the procedure of Story 1.8 (Result, "Not run here"): `E12_HOST=reference bash spikes/argon2id-params/run.sh`, idle, in the same session as E32 (Story 5.1 AC7)
**Then** m is picked from {256, 384, 512} MiB under the serial, limit-2 model with the limit times m at most 1 GiB, and the picked value replaces the provisional constant (gates E12-1, E12-2)
**And** the constant is not changed on the strength of a VM or emulation run (gate E12-5).

**Decisions and why** (drafted decision text under Open points)
- *The locked working memory* (review F1, owner decision). Each derivation maps its own locked region: `block_count()` blocks then a passphrase buffer of three times `PASSPHRASE_MAX_LEN` (UAX #15's bound on NFC growth), whole pages, between guard pages, advised as the pool is. Per derivation rather than preallocated, so that 1 GiB is not locked while no one unlocks; the page faults of `mlock` are inside the measured unlock time. The wipe is volatile 64-bit writes (one per eight bytes of up to 1 GiB), then `munmap`, which also unlocks. A refused `mlock` undoes the mapping and returns `WorkingMemoryLock`, whose message names `LimitMEMLOCK`; there is no unlocked fallback.
- *The budget, not limit times m, bounds what is locked.* A header up to the ceiling's 1 GiB is accepted (D128), and two of them at once would hold 2 GiB, beyond the "at most 1 GiB" of AC6. The limiter therefore counts each admitted derivation's blocks against `ARGON2ID_MEMORY_BUDGET_KIB` (1 GiB) besides the concurrency limit: two derivations at the current cost run side by side (768 MiB), a header at the ceiling runs alone. The build asserts the limit times the current m and the ceiling's m within the budget. `LimitMEMLOCK` must cover the pool, the budget and one passphrase page per admitted derivation: `LimitMEMLOCK=1032M` covers 1 GiB plus margin; the burst measured `VmLck` 786 452 KiB at two current-cost derivations.
- *The limiter without tokio.* No async runtime is in the tree before story 5.1, and no dependency was to be added. The limiter is a runtime-agnostic future: requests queue in arrival order at `admit_derivation`, only the oldest may start (so a ceiling-sized request is not overtaken), a permit's drop wakes the next one, the waker is stored under the lock that checked admissibility so none is lost, and the 4-second bound is a timer the caller's runtime makes from the limiter's own constant (`tokio::time::sleep` in story 5.1). A refusal carries no time. The permit is bound to the cost it admitted, so a derivation cannot run at a cost the budget did not count. The limiter is a static of `vilicus-crypto`, and `derive_passphrase_kek` needs its permit: every Argon2id derivation goes through the one limiter by type.
- *Where each check lives.* The cost, the salt, the encoding and the derivation are `vilicus-crypto`'s, before the limiter (`CheckedCost`) and inside it; the first factor, the per-member state and the backoff are the Core's (`vilicus_core::unlock`), which knows members. NFC is done in the Core, which already links `unicode-normalization` (D130), lazily: `vilicus-crypto` takes the characters and encodes them into its locked buffer inside the guarded call, so the normalisation's own buffers live on the scrubbed stack, and no new edge to that package was added.
- *The first factor.* `FirstFactor` has no product constructor: the passkey login (7.6) and the host path (9.4) will make it. `prepare` takes the factor as an `Option`, because a request as received may carry none, and refuses before it reads anything.
- *The backoff* starts at 1 s after the first failed passphrase and doubles to at most 5 min, cleared by a success (`[ASSUMPTION]` values, named constants). Only a wrapper that does not open counts as a failure; a refusal of the limiter or of key memory does not.
- *The salt* is 16 bytes of `getrandom(2)` (U6: "from the operating system generator"), not aws-lc-rs's DRBG, which nonces use.
- *A wipe during a derivation* (the open point of story 4.2). The crate has no step between which the pool could be checked, so the bound is accepted: a derivation running when the pool is wiped runs to its end, past `WIPE_WAIT` when longer; the guarded call returns `Wiped`, its KEK slot and working memory are wiped on drop, and no KEK is returned (two tests). The working memory is not in the pool, so the pool's wipe does not overwrite it while the derivation uses it; it is wiped when the derivation ends, or released by the kernel if the process exits first, locked, never swapped or dumped.
- *Real-cost tests.* The floor (64 MiB) and the version 1 cost (384 MiB) lock more than a CI runner's `RLIMIT_MEMLOCK` (story 4.2's tests lock tens of KiB there). Unit tests use costs below the floor through `CheckedCost::below_the_floor`, a test-build constructor, and the two Core tests at real costs are `#[ignore]` with that reason, run by the `argon2id` job in a container whose limit is unlimited, beside the oracle.
- *The oracle outside the workspace* (owner decision). Its manifest has its own `[workspace]`, its lockfile is a subset of the workspace's, so it builds offline from `vendor/`; it depends on `vilicus-crypto` with `testing` and on `vilicus-types`. The reference implementation is linked through a hand-written binding of `argon2id_hash_raw` to Debian's `libargon2-dev` (no crate added); OpenSSL runs as `openssl kdf ... ARGON2ID`, one process per derivation, which proved simpler than binding `EVP_KDF`. `check_workspace.py` holds it to `[oracle.argon2id]`.
- *Test BLAKE2b in the harness.* H0 is a pattern U3 asks for and only BLAKE2b computes it; no crate may name `blake2` (U1). The harness's `material.rs` recomputes it with a test-only BLAKE2b-512 (RFC 7693), as it already recomputes SHA-256 states; the check `pattern-recomputation-blake2b` holds it, on every run, to the first block of each lane the argon2 crate writes at one pass. It is test code of the example, never product code.
- *U5 by source text.* `the_crate_is_called_only_as_the_review_requires` reads the crate's product sources: the argon2 crate is named in `argon2id.rs` and, for the block type alone, in `memory.rs`; one context, Argon2id version 0x13; one `Params::new` with `Some(PASSPHRASE_KEK_LEN)`; one `hash_password_into_with_memory`; none of the secret, associated data, key id, other variant or version APIs. Like story 4.1's shape test, it reads text and refuses the ways it knows.
- *The benchmark* is the product's own path, the version 1 cost through the limiter and the locked memory, alone and as two simultaneous unlocks, then the candidates {256, 384, 512} MiB under the selection rule of story 1.8 with the adopted model (serial lanes, limit 2); its pick is judged against the constant only when `E12_HOST=reference`.

**Deviations**
- *AC2, AC6, "a FIFO tokio `Semaphore` acquired before the blocking-pool permit"*: tokio is not in the tree before story 5.1 and no dependency was approved. The limiter is the runtime-agnostic admission future above, with the semantics D128 asks of the semaphore (FIFO, acquired before any thread is taken, a timed refusal); story 5.1 awaits it on the runtime with `tokio::time::sleep` as its timer, then runs `Prepared::unlock` with `spawn_blocking`. The tests compose the steps with `testing::block_on` and threads.
- *AC2, "an unlock request ... no successful first factor attached"*: no first factor is produced before stories 7.6 and 9.4, so the refusal is tested on `prepare` and `UnlockGate::begin`, and no product path can start an unlock yet.
- *AC3, AC9*: the reference host is not available. The benchmark and the procedure are written (Open points); the emulation numbers are information, and m stays at its provisional 384 MiB (gate E12-5), although the emulation's rule picked 512 MiB.
- *AC4*: not met (decision task above).
- *AC5, "rewritten with the current one at that unlock"*: `Unlocked::rewrap` makes the change; writing it needs the household key's set key, which an unlock reaches through story 4.6's HK, so the composed write is stories 9.3 and 9.4's (tested here with `testing::household_key`).
- *AC6, "peak memory bounded"*: shown by the limiter's own accounting in the unit tests and by `VmLck` sampled during a real burst at the version 1 cost in the `argon2id` job (786 452 KiB, the bound exactly), not in `cargo test`, which cannot lock that much.
- *AC8, "a dev-dependency only"*: the phc-winner-argon2 cross-test is the oracle crate outside the workspace, the owner's decision for this story, which keeps it out of the workspace's dependency graph altogether.
- *U8, "the backup secret and recovery secret lengths"*: their encodings are stories 4.5 and 4.8's; the coverage list uses text secrets of 16 to 64 characters.
- *Environment*: builds and gates ran in containers of the pinned image whose target directory and cargo home were `tmpfs` mounts, on a copy or a fresh clone of the branch; the working copy is a Windows checkout with CRLF line ends, so `cargo vet` ran on store files converted to LF, as a Linux checkout has them. `ci/key_memory.py` itself was not run (it makes named volumes); its five groups ran with its options from a runner that copies in the release harness built in the build container, as in story 4.3.

**Open points**
- *Design documents* (coordinator; none edited here but `doc/key-management.md` and `doc/qa/argon2-review.md`):
  - **Drafted D156**, "Argon2id in locked working memory, one limiter counting a memory budget, and the passphrase unlock", amending D128, D129, D131 and D154: "Context: story 4.4 builds the passphrase KEK of D128 with the `argon2` crate under D129. The internal review (`doc/qa/argon2-review.md`, F1) found the Argon2id blocks equivalent to the KEK once a derivation is done, which D131 had left wiped but unlocked; D128 bounds the working memory by the limit times m while accepting headers up to the ceiling's 1 GiB, two of which would hold 2 GiB; it names a tokio semaphore before tokio is in the tree; and no record says how a derivation that outlasts the pool's wipe ends, where the passphrase's buffer lives, or where the cross-test oracles run.
