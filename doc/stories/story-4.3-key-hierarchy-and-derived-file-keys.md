# Story 4.3: Key hierarchy and derived file keys

As a member,
I want each encrypted file opened with its own key derived from my partition root,
So that one file key reveals no other file and partition isolation rests on keys, not on code paths.

**Acceptance Criteria:**

**AC1 (D3, AD-5)**
**Given** a partition root (member DEK, household key or, for Core metadata, the instance key)
**When** the Core opens a `<module>.<partition>.db` file
**Then** the file's raw SQLCipher key is derived with HKDF-SHA-256 and the versioned label `vilicus/v1/db/<module>/<partition>/<generation>` of `doc/key-management.md` section 2
**And** two files of the same partition, or the same module in two partitions, get different keys (property test)

**AC2 (AD-5)**
**Given** a derived file key
**When** the file is created or re-keyed
**Then** its key epoch (partition root version, generation) is written atomically in the clear sidecar `<file>.epoch` and repeated in the file's `_meta` table
**And** an epoch mismatch between the sidecar and `_meta` refuses the open with a typed error

**AC3 (D9)**
**Given** the instance key delivered to the Core
**When** keys for Core metadata and the audit database are derived
**Then** Core metadata keys derive from the instance key and the audit database key derives from the audit key with the label `vilicus/v1/audit/db`
**And** no derivation from the instance key opens a personal or household partition file (test over every V0.1 label)

**AC4 (D4, AD-4)**
**Given** the `wrappers.db` schema
**When** it is created
**Then** it holds every member DEK wrapper (one per KEK) and member public key with format version, generation and algorithm identifiers, in its own file separate from `core.db`
**And** losing `core.db` or the instance key does not prevent unwrapping a member DEK from `wrappers.db` (test)

**AC5 (AD-4)**
**Given** a module that needs its data
**When** the Core hands it access
**Then** it receives an opened, partition-scoped handle, never a key or a path to a key

**Decision tasks:**
- [x] Decide how `wrappers.db` is authenticated as a whole (`doc/stories/deferred-work.md`, gate AD36-1): the AD-36 construction authenticates each record, not the set, so deleting a record raises no alert and restoring an older file can bring back a vetoed or suspended member's valid record (D119). Gives up: every wrapper write also rewrites the set MAC and the counter; deferring again keeps the limit of D119 stated instead.

**Decision task, gate AD36-1** (owner approval of the recommended option). `wrappers.db` is authenticated as a whole by a monotonic counter, a MAC over the record set under a key derived from the household key, and a cross-check of the counter with `core.db`; every wrapper write also rewrites the set MAC and the counter. As built:
- The set key is `HKDF-SHA-256(HK, vilicus/v1/hk/wrappers-set-mac/ || 0x00 || len || hk_version)`, held for one operation in a slot.
- The MAC is HMAC-SHA-256 under it over: the label `vilicus/v1/wrappers/set` and its end byte; the format version (1), the algorithm identifier (0x0001, HMAC-SHA-256), the household key version, the counter (`u64`) and the record count (`u32`); then each record, in ascending byte order, preceded by its `u32` length. The order makes the input the set's, whatever order the records are read in.
- A record is one row of `sqlite_master` (type, name, table name, SQL), the schema, or one row of a table of `RECORD_TABLES` (`_meta`, `member_dek_wrappers`, `member_public_keys`): its table's name with a `u16` length, then each of the columns `RECORD_TABLES` names for it, in that order, never `SELECT *`, tagged (null, integer as `i64`, blob or text with a `u32` length). The `wrapper_set` row, the counter and the MAC, is the set's state and no record; a test fails on a table that is neither, or on a column list that is not the table's.
- The schema is checked, not only covered (review, H1): at open, at each snapshot and inside each write's transaction, `sqlite_master` must be exactly what `SCHEMA` makes in an in-memory database, so a planted trigger, a view, a rebuilt table or any other object is refused (`WrappersSchemaChanged`) before a statement of the Core runs on it, and the connection's authorizer denies every action a trigger or a view would carry out.
- The stored MAC is the format version, the algorithm identifier, the household key version, then the tag (40 bytes); another version or algorithm is refused, never read.
- A write runs in one `BEGIN IMMEDIATE` transaction: it checks the schema again, verifies the set as it is (a fresh file, counter 0 with no MAC, holds no DEK wrapper and no public key) under a verify key, applies its changes, raises the counter, seals the new set under a seal key (the same key, or the next household key version's for a rotation's rewrite) and stores the MAC, then checkpoints the WAL empty, so a removed wrapper does not stay there; a checkpoint that fails after the commit is returned beside the committed counter, never as the write's failure (review, L5). A set changed behind the Core's back fails the verification, and the write is refused: the Core never seals a tampered set.
- The cross-check gives `Matches`; `Unchecked` when `core.db`'s copy is missing (core.db or the instance key lost: the DEK still unwraps, AC4); `Ahead { by }` when `wrappers.db` is ahead (by one: a crash between the two writes); `RolledBack` when it is behind. The copy is `core.db`'s, which story 5.2 creates, so `open_verified` takes it as a parameter. `open_verified` reads the set and its rows in one transaction, verifies the MAC, then cross-checks the counter, and returns `Verified`, the only way the Core reads the set's records; the one read before it is the unlocking member's own DEK wrapper (`unwrap_own_dek`), since the household key that checks the set is reached only through that DEK (review, L6).
- The crash window (review, Info): a crash between the commit of `wrappers.db` and the update of `core.db`'s copy leaves `Ahead { by: 1 }`; until the Core next verifies and updates its copy, an attacker who restores the file of the previous counter makes it read as `Matches`, so that one write is lost unseen. Story 5.2 closes it: it writes the expected counter into `core.db` as an intent before the commit of `wrappers.db`, and a start that finds `wrappers.db` one behind an unconfirmed intent cannot tell a crash before the commit from that rollback, so it alerts the member whose write was pending instead of passing silently.
- Staging, because the household key has no constructor before story 4.6: here, the set key and its MAC exist, tested with `vilicus_crypto::testing::household_key`, a stand-in compiled with the `testing` feature only; no product path seals a set yet, since no product path writes a wrapper. Story 4.6 completes it: the first member's ceremony creates HK and makes the first write of `wrappers.db` with HK's set key, so no set is ever written unsealed. The unlock path, in the web client and at the host (stories 9.3 and 9.4), then calls `open_verified` once it holds HK, before any record but the unlocking member's own DEK wrapper is used; story 4.7's AD-36 checks read their records through `Verified`.

**Decisions and why** (drafted decision text under Open points)
- *Role types over one slot.* Each role is its own type, so a DEK cannot key a household file and the instance key has no method that derives a module file's key: the partition of a file key comes from its root, never from the caller. The registry is the one list of derivations; the build refuses a call site whose parent role its entry does not name, and a test runs every entry and compares the child it names with the role of the key produced (review, L1: the build check of the child, the call site restating it, could not fail), which makes the AC3 test, which walks the registry, a statement about the code rather than about a list. A role key's bytes stay in the crate: `HoldsKey::symmetric` takes a token only the crate makes, and `derive_key` is not exported but under `testing` (review, M1).
- *The context of a file key* is the module's name, the partition (a kind byte, 0x01 household, 0x02 home, 0x03 then the 16-byte member id), the root's version and the generation, each with its D153 length prefix, under the label `vilicus/v1/db/`. Key management section 2 writes `vilicus/v1/db/<module>/<partition>/<generation>`; the root version is added so the key binds the whole epoch the sidecar names, and the partition is binary, as D119 binds the member id.
- *Labels.* An HKDF label followed by context fields ends with `/`, one with none does not (`vilicus/v1/partition/home`, `vilicus/v1/audit/db`); a wrap purpose or a MAC domain does not end with `/` either, its context being bound inside the seal's or the MAC's input after the label's end byte (`vilicus/v1/wrap/member-dek`, `vilicus/v1/wrappers/set`, as story 4.1's `vilicus/v1/wrap/member-private-key`). Three labels are new: `vilicus/v1/core/db` (no document names the label of `core.db`'s key), `vilicus/v1/hk/wrappers-set-mac/` and `vilicus/v1/wrappers/set`; and the purpose `vilicus/v1/wrap/member-dek`.
- *The instance key's credential* is read straight into a slot, with no intermediate buffer, and must be exactly 32 bytes; its version is the caller's (the sidecars name the root version, and story 5.1 or 5.2 says where the Core reads it).
- *The storage layer takes a lent key text* (`FileKeying`) rather than a `vilicus-crypto` type, which would be a new edge (AD-3): the Core wraps a `FileKey` in `keys::KeyText`, and only the call that keys a connection runs under the guard, not the open around it. Only test code implements it over a fixed text (`TestKey` in the storage tests, `vilicus_core::testing::TestKeyText`, compiled in test builds and with the `testing` feature): the product's only implementation is the Core's lent file key (review, Info). Its length is checked against `vilicus_crypto::SQLCIPHER_KEY_TEXT_LEN` in the Core, the one crate that sees both.
- *Re-key.* `sqlite3_rekey_v2` re-encrypts every page in one transaction of its own; the WAL is emptied before, so no frame under the old key stays, and after, so the file alone holds the new pages. The pending-sidecar protocol of `write_epoch` (D143) frames it, and the file is read back under the new key on a fresh connection, its `_meta` at the new epoch, before the pending sidecar is renamed: SQLCipher ignores the return of the re-key's commit and installs the new key anyway, so the call's success proves nothing (review, L4).
- *`wrappers.db` is a plain SQLite file* (architecture section 5.2: "not encrypted by the instance key"), set up like a writer and run under the write policy, which refuses schema changes, `ATTACH` and the writes of `_meta`.
- *Tests that need a household key* use `vilicus_crypto::testing::household_key` through a dev-dependency of `vilicus-core` on `vilicus-crypto` with its `testing` feature, the edge of its normal dependency and no new package, so `cargo test -p vilicus-core` runs them too (review, L2); `check_packaging.py` refuses the feature in release artefacts only, and passes.
