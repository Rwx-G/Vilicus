## 1. Principles

1. Data is protected by random keys, never directly by passwords or passkeys. Secrets only wrap keys, so a factor can be added, removed or changed without re-encrypting data.
2. Every member key has several independent ways to be unwrapped. Losing one way loses nothing.
3. The passkey is never the only way in: a passphrase is mandatory, and an offline recovery secret is generated at enrollment.
4. The instance admin is separate from data keys. The admin runs the system, not the members' data. No admin operation re-wraps a member's key.
5. The Core sees unlocked keys. This is **not zero-knowledge**. The protection is against stolen disks, stolen backups and offline attackers, and against other members and other modules. It is not a protection against a compromised running host (`threat-model.md`, A7).
6. Use audited libraries and standard constructions only. No home-made primitives. The one recorded exception is HPKE from the `hpke` crate, which has no paid audit and gets an internal security review, a cross-test against an independent implementation and the RFC 9180 test vectors, and an external review before V1 instead (see D61); the internal review and the cross-test gate V0.1 (D74). They are done when the RFC 9180 test vectors pass, the cross-test against the independent implementation, used as a dev-dependency only, agrees on 10 000 random cases, and a written review with every finding closed or accepted is committed (D107). This documentation never calls it audited. The gate is passed except its CI job (D120). Further exceptions for the OPAQUE libraries and the `argon2` crate are proposed, not decided (D123, D129).

Partition roots are the member DEK (personal partition), HK (household partition) and the home partition root (home partition). Derivations use HKDF-SHA-256 with a version and a domain label in `info` such as `vilicus/v1/db/<module>/<partition>/<generation>`. The algorithm suite is fixed by spine AD-18: wrapping uses AES-256-GCM with random 96-bit nonces; passphrases and the backup secret use Argon2id; HK and inbox rows are sealed with HPKE (RFC 9180, base mode, DHKEM(X25519, HKDF-SHA256), AES-256-GCM). AES-GCM and HKDF come from aws-lc-rs; HPKE comes from the `hpke` crate, with the primitive crates it depends on, under the D61 exception, and is used only under the usage rules of its review (D120). Every wrapper stores its algorithm identifiers (section 9).

All wrappers and member public keys live in `wrappers.db`, not in `core.db`, so losing the instance key never loses the ability to unlock member data (`architecture.md` section 5.2). A member public key in `wrappers.db` is accepted for wrapping only after the Core verifies a MAC under a key that an attacker who can write the disk does not hold (spine AD-36, threat T23). The construction (D74):

1. **Key pair owner.** The Core generates the member key pair and the personal inbox key pair during the enrollment ceremony, so neither the browser nor a compromised Gateway can substitute a public key at enrollment.
2. **At `vilicus member add`.** The authorizing adult is unlocked by their passphrase, so the Core holds HK. It derives an enrollment authentication key from the enrollment token, `HKDF-SHA-256(token, info = "vilicus/v1/enroll-auth/" || member_id)`, and stores it in `wrappers.db` wrapped under a key derived from HK (`HKDF(HK, info = "vilicus/v1/hk/enroll-wrap/" || member_id || hk_version)`). Only a hash of the token, under a different label, is kept to check the token.
3. **At enrollment.** The member presents the token; the Core derives the same enrollment authentication key, generates the key pairs and stores, next to the public keys, a tag `MAC(enrollment key, member_id || member public key || inbox public key)`. The token and the derived key are then discarded.
4. **At the next adult unlock after the delay.** The Core unwraps the enrollment authentication key with HK, verifies the tag, and only then writes the permanent authentication: a MAC over the same fields under `HKDF(HK, info = "vilicus/v1/pubkey-mac/" || member_id || hk_version)`. Every later HK wrap first checks that MAC. A tag that fails verification is refused and alerted to every adult; HK is not wrapped.
   **Confirmation of HK at unlock** (proposed, D121). HPKE base mode authenticates no sender, so a disk writer who holds a member public key can seal an HK' of its choice to it, and can compute the permanent MAC under HK' as well. The proposed confirmation: when a member first receives HK, the Core writes a commitment to HK and its version under a key derived from the member's DEK, and at every later unlock refuses an opened HK that does not match it, with an alert. **Open**: the first receipt of HK has no such anchor; whether it is confirmed by the authorizing adult, by a value under the instance key, or accepted as a trust-on-first-unwrap point is to be decided before FR-8 code (R55).
5. **First member.** HK is created in the same ceremony as the first member's key pairs, so the Core writes the permanent MAC at once.
6. **Inbox public keys.** A personal inbox public key carries the enrollment tag, then a MAC under a key derived from that member's DEK, checked at each of their unlocks; the household inbox public key carries a MAC under a key derived from HK, checked at each adult unlock. Because the Core seals rows while the partition is locked, it also checks, at sealing time, a MAC under a key derived from the instance key. Honest limit: an attacker who holds the instance key and can write the disk can substitute an inbox public key and read the rows sealed until the next unlock of that partition, where the substitution is detected and alerted.
7. **Limit.** The enrollment token is typed in a browser and transits the Gateway. A compromised Gateway that also writes `wrappers.db` could forge the enrollment tag; separate processes and file permissions keep these two capabilities apart (`architecture.md` section 4).

The construction and the internal HPKE review and cross-test of D61 are V0.1 gates (D74), with the done state and fallback of D107. The key prototype (`spikes/ad36-key-prototype/`, D119) fixed the encodings below; its README holds the byte layouts. A test there checks that every label, algorithm identifier and fixed field length in the code appears in the README, and known-answer tests, computed outside the crate, pin the byte composition of the MAC input, the derivation contexts and the store encoding.

- **Member identifier.** Every `info`, MAC input and HPKE `info` binds the Core's opaque 16-byte UUIDv7 member identifier in binary, never a display name, so the binding is stable across a rename. The token's printed text encoding is fixed by the enrollment story, not by the key prototype.
- **Derivations.** Every derivation above is HKDF-SHA-256 with no salt and a 32-byte output. In each `info`, the label comes first, then `|| member_id`, the only variable-length part, then, where present, `|| hk_version`, a fixed-width `u32` big-endian. No label is a prefix of another, so no two contexts collide.
- **Token check.** The hash kept to check the token is `HKDF-SHA-256(token, info = "vilicus/v1/enroll-token-check/" || member_id)`, compared in constant time and erased when the token is used, so a token works once.
- **Enrollment key wrap.** AES-256-GCM with a random 96-bit nonce under `HKDF(HK, info = "vilicus/v1/hk/enroll-wrap/" || member_id || hk_version)`; the wrap stores that HK version, and its additional data is the wrapper's format version, its algorithm identifier, the HK version and the member identifier, so a wrap moved to another record or relabelled to another version does not open. A wrap made under another HK version than the unlocking adult's is refused as stale, not as tampering, and the member is added again. The wrap and the enrollment tag are erased once the permanent MAC is written.
- **MAC input.** The enrollment tag and the permanent MAC are HMAC-SHA-256 over the same canonical input: the member identifier, the member public key and the inbox public key, each preceded by its `u16` big-endian length, the public keys in their stored encoding with format version and algorithm identifier, so neither field boundaries nor algorithm identifiers can shift under the MAC. MACs are verified in constant time.
- **HK wrap.** HPKE base mode with `info = "vilicus/v1/hk/wrap/" || member_id || hk_version` and, as additional data, the permanent MAC tag, so a wrap opens only next to the MAC it was made with. The permanent MAC carries the HK version that keys it; a later wrap is refused unless that version is the unlocking adult's and the MAC verifies.
- **Stored values.** Every key, wrap and MAC value in `wrappers.db` starts with a format version and an algorithm identifier (section 9); an unknown version or identifier is refused, never repaired.

Result, against an attacker modelled as raw edits of `wrappers.db` without HK: a substituted member or inbox public key, an edited enrollment tag, and an edited or moved enrollment key wrap are refused at the next adult unlock with an alert, and HK is not wrapped; a public key and permanent MAC edited after the first wrap, or a MAC copied from another member, make every later wrap refuse, and an edited inbox public key of an active member makes that member's own unlock refuse; a wrong, foreign or reused token is refused with nothing written. An honest enrollment receives HK. What the prototype does not show: the Gateway limit of step 7, which is a process separation property; the inbox key MACs of step 6, which ship with the home milestone (D107); and the D61 review of the `hpke` crate itself. Limits it states: nothing authenticates `wrappers.db` as a whole, so deleting a record raises no alert and restoring an older `wrappers.db` (rollback) can bring back a valid record of a member since vetoed or suspended; a disk writer can relabel a pending wrap's HK version so that a tampered enrollment is reported as stale rather than as tampering, though it still gets no wrap; the prototype has no adult or child role; and its alerts are returned to the caller, not persisted, since recording them in the audit log and delivering them to every adult belong to the Core.

### Home partition and sealed inboxes

The home partition is a third partition kind, one per instance, whose file keys derive from the instance key, so the house keeps working while every member is locked (see D53, spine AD-37). Only the `home` module writes it. Honest consequence: root on the host, or the thief of a disk without a TPM, or of a whole host whose TPM a signed live image unseals (D108), can read the home partition; it holds current state, a short event window and adapter secrets, not history. The secrets that let a device open the house are not among them: they are entered at the host CLI and sealed to the host's TPM under a signed boot policy, so the instance key alone does not give the credentials that unlock, disarm or open through a vendor, a radio or a router, and a host without a TPM cannot run such adapters (D78, D108). The other adapter secrets (lights, heating, a read-only presence account) stay readable by whoever holds the instance key. A radio coordinator that carries physical security devices counts as such an adapter, so its network key is sealed this way (D78, D108).

History destined for a personal or the household partition never goes to the home partition. From the home milestone (in V0.1 every event stays within its source partition, D107), the Core seals it, on a module's request, into that partition's sealed inbox `inbox.<partition>.db`, a SQLCipher file under a key derived from the instance key (`vilicus/v1/inbox/<partition>`, D114): each row is sealed with HPKE to the partition's inbox public key, with its record type and payload version inside the sealed payload, and authenticated with a MAC under a key derived from the instance key. Sensitive history always takes this path, even while the target partition is unlocked. The household sealed inbox is the inbox of the household partition. Ingestion is described in sections 4 and 5.

**Integrity limit** (D93). Because the MAC key derives from the instance key, whoever holds the instance key (root on the host, the thief of a disk without a TPM, the instance admin with a backup and its backup secret) can forge inbox rows: the inbox boundary protects confidentiality, not integrity, against the instance key holder. An ingested row is therefore stored `external` unless it carries a MAC under a key derived from the household key, which the Core adds only to rows it produces while an adult is unlocked (a disclosure grant, D64); ingestion is journaled and reviewable by the member, and runs continuously while the target partition is unlocked, not only at unlock. Such a MAC proves only that the Core of an unlocked adult produced the row, which an operator who is an adult can also do (R19): ingestion accepts it only when its grant identifier names a live grant the recipient was notified of at creation, its author is that grant's owner and never the recipient, and its fields match the grant's registered derivation; the MAC input binds the grant identifier, owner, recipient and a sequence number (D93).

### Backups

A backup seals the instance key and the audit key to the backup public key with HPKE (section 9), so a systemd timer runs `vilicus backup` as root without anyone typing the backup secret; the Core and the audit writer each return their key already sealed to the backup public key over their admin sockets (spine AD-31), and an S3-compatible off-host target with write-only or object-lock credentials receives the archive (D85, D106). Within each backup, the passphrase wrappers and the file names are additionally sealed to the backup public key, so a stolen backup offers no passphrase wrapper to guess offline; recovery-secret and HK wrappers stay as on the host (D106). Unwrapping needs the backup private key, which is re-derived from the backup secret only for a restore or a content check and never stored. The manifest carries a monotonic backup sequence number and a MAC under a key derived from the audit key; `vilicus backup verify` checks a backup, and CI runs a restore drill. `vilicus restore` writes the unwrapped instance and audit keys as new credentials bound to the new host's TPM, or as file credentials without one, then discards the backup private key. A passphrase change does not reach older backups, and the DEK does not change with it; completing a recovery rotates the DEK (section 6). The secrets that open the house are never in a backup (D78, D108); the sealed delegation sub-keys are (section 7), and so are the plugin state stores (D95).

### Disclosure grants

A disclosure grant (see D64, spine AD-49, PRD FR-92) adds no key. The Core runs the grant's registered derivation in the owner's partition while that partition is open, returns closed types only, keeps the value's source data type, stores it with the taint of its inputs (ai-safety I9) and the granting member as author (so the recipient's assistant reads it as `member` taint, D104), then seals it into the recipient's personal sealed inbox like any other sealed row; the recipient's next unlock ingests it. The recipient never receives a key, a wrapper or a handle to the owner's partition, and revoking the grant stops future runs without any rotation. A value already delivered stays in the recipient's partition.

## 3. Enrollment of a member

V0.1 scope: a passkey authenticates and the passphrase unlocks; unlocking with the passkey PRF is a later addition (PRD section 4.4, E1, E2). Passkeys are bound to the instance name, so the instance name and its certificate are fixed before the first enrollment (see D51, PRD FR-65).

1. **First member.** Bootstrap runs in this order: bootstrap token, then the instance name and its certificate, then the instance admin's passkey on that name, then the instance admin's out-of-browser destination, confirmed by redeeming the token of a test notification, then the first member; no WebAuthn ceremony runs over the temporary self-signed certificate (D76, D105, E24). The person running the wizard then enrolls as the first member (PRD FR-7). While no member exists, `vilicus member enroll-first`, run by root with the admin recovery code typed at the prompt, prints an enrollment token (D101), so an interrupted wizard never leaves the instance without a way to enroll its first member; the command is refused as soon as one member exists.
2. **Further adults.** An existing adult, any adult, authorizes a new adult from the host CLI with `vilicus member add` and their own passphrase, which prints an enrollment token (128 random bits, single use, 15 minutes). The instance admin alone cannot complete any step (see D34, PRD FR-8). This replaces the invitation link completed by a short code of revision 1. The Core also derives the enrollment authentication key from the token and wraps it under a key derived from the authorizing adult's HK; it authenticates the new member's public keys (D74, spine AD-36, section 2).
3. The member opens the enrollment page with the token, enrolls a **passkey**, chooses a **passphrase** (strength check against French and English dictionaries, not a composition rule, PRD FR-110), and configures an out-of-browser destination, confirmed by redeeming the token of a test notification sent to it (D105).
4. The Core generates the **member DEK** with its CSPRNG during the enrollment ceremony (it sees the key anyway, see principle 5) and wraps it under the passphrase KEK. The Core also generates the member key pair and the inbox key pair of the personal partition at the same time (D74); their public keys go to `wrappers.db` with their enrollment tag (section 2), the private keys are wrapped by the DEK. The new member's personal partition is usable at once.
5. The Core generates a **recovery secret** of at least 128 bits of entropy (grouped characters with a checksum, language neutral, D113), shows it once, and requires the member to re-type part of it to prove it was copied. The Core derives the recovery KEK, wraps the DEK, and discards the secret.
6. Enrollment is only completed with **exactly one passkey, the printed recovery secret confirmed as above, and a redeemed test notification** (PRD FR-7, D105); further passkeys are added afterwards with a step-up, each raising an out-of-browser alert (PRD FR-56). The wizard says plainly that losing every authenticator, the passphrase and the printed secret destroys the personal partition.
7. **Household key.** For the first member, HK is created and wrapped for that member. For a further adult, every other adult is notified, a delay with a veto runs, and HK is wrapped to the new member's public key at the next adult unlock after the delay (section 5).
8. With a passkey step-up, a member adds or removes a passkey; removing the last one is refused, and each change raises an out-of-browser alert stating how many passkeys and paired devices the member now has (PRD FR-10, FR-56). In V0.1 this changes no wrapper. Once PRF unlock exists, each additional authenticator is a new wrapper, created from an unlocked session so the existing unwrapped DEK can be re-wrapped for it.
9. **Re-enrollment.** A member who lost every passkey, or whose passkeys stopped working after an instance rename or a restore, gets a new enrollment token from `vilicus member reenroll <member>` at the host CLI, which requires that member's own passphrase, never another adult's (D77). The member is notified on every channel. With the token and the passphrase, the member enrolls a passkey in the browser and redeems a test notification (D105); no wrapper changes while passkeys wrap no data key. Completing a re-enrollment ends the member's unlock window and revokes every other passkey, paired device, web session and channel binding of that member, except those the member explicitly keeps on the completion screen; the out-of-browser alert lists what was revoked.

Secrets typed or shown in the browser transit the Gateway: the passphrase at enrollment and at each change, and the recovery secret shown at enrollment and at the end of a recovery. A compromised Gateway can read them, like the unlock passphrase (R3 in `architecture.md`); `vilicus unlock` avoids this for unlocking only.

### Passkey wrapping details

Later addition, not in V0.1. The design below is kept for when PRF unlock lands.

- The WebAuthn PRF extension (built on the CTAP hmac-secret extension) is evaluated **per credential**: the secret is specific to the authenticator and credential, so there is one wrapper per authenticator and a synced passkey from one provider does not produce the same secret on another provider.
- Per credential, the Core stores a random PRF input salt. The client evaluates PRF with that input, obtaining a 32-byte output; the KEK is `HKDF-SHA-256(prf_output, salt = credential_salt, info = "vilicus/v1/kek/passkey/" || member_id || credential_id)`.
- The PRF output is computed **client-side** and sent to the Core (over TLS, through the Gateway) in the same exchange as the login assertion. The Core derives the KEK, unwraps the DEK, keeps the DEK in memory for the session, and drops the KEK. The Core therefore sees the PRF output and the DEK. This is stated everywhere as a limit (R3 in `architecture.md`).
- Not every authenticator, browser and OS supports PRF; support differs between platform and roaming authenticators and between password managers acting as passkey providers. Where PRF is unavailable the passkey authenticates the login and the passphrase unlocks the data. Compatibility is a **test item** (`research-notes.md`, E1, E2).
- A passkey wrapper would tie data access to the instance name: an instance rename makes every passkey unusable (see D51). While passkeys wrap no data key, a rename loses no data (section 11).
- The PRF output is an unsigned client extension result: the Core cannot verify that it came from the authenticator, and the signed authenticator data may carry no trace of the evaluation (a CTAP `hmac-secret` output appears only when the browser uses that extension, and the Chromium virtual authenticator leaves none). The only check on the output is that the AEAD unwrap of the DEK succeeds; a wrong output fails it. Observed in E2 (story 1.17).

### Passphrase wrapping details

- KEK = Argon2id(passphrase, salt, m, t, p) with a per-wrapper random salt; the parameters are stored in the wrapper header so they can be raised later. Parameters are tuned on the target hardware (floor chosen from current published guidance, ceiling from acceptable unlock latency on a small host; target in PRD FR-11, parameters set by E12). Because the Core does the work, unauthenticated requests must not be able to trigger it freely: the passphrase path runs only after a first authentication factor, with a global concurrency limit.
- Proposed values, provisional until E12 runs on the reference host (D128): the passphrase is normalised to Unicode NFC and encoded as UTF-8 before derivation, so the same passphrase typed on two devices derives the same KEK. The floor is RFC 9106 section 4: the cost is at least one of its two options in both memory and passes (a project rule); the OWASP minimum is sized for login hashing and is not the floor for a KEK an attacker can attack offline. Version 1 wrappers use Argon2id version 0x13 with m = 384 MiB, t = 3, p = 4, a 16-byte random salt and a 32-byte output. The Core refuses a header whose cost is below the floor or above the ceiling (m at most 1 GiB, m times t at most 4 GiB, p at most 8) before it queues the derivation. The Argon2id working memory is a buffer the Core owns and wipes after each derivation. When the cost is raised, a wrapper is rewritten at its next unlock, which then costs one derivation at the old cost and one at the new.

## 4. Unlocking

| Path | Needs | Result |
|------|-------|--------|
| Passkey + passphrase (V0.1) | Authenticator for login, passphrase for unlock | Login then unlock |
| Host unlock (V0.1) | `vilicus unlock` on the host with the passphrase of the member being unlocked, never another adult's (D77) | Unlock without the passphrase transiting through the Gateway; sets an unlock window and is audited (PRD FR-57) |
| Fallback login (TOTP) + passphrase | TOTP code and passphrase | Login and unlock on a device with no passkey; the session cannot do tier 2, pairing or step-up |
| Passkey with PRF (later) | Authenticator present, user verification | Login and unlock in one gesture |
| Recovery | See section 6 | Slow path with waiting period |

After unlock the Core holds the DEK (and the HK for adults) in locked memory. Opening a module database for a partition derives its key at that moment. Unlock completes, for the member, when the keys are derived and the session is usable; each file then goes through re-key, migration, inbox ingestion (section 2) and outbox delivery in the background, in that order, and HK wraps for an adult run last (section 5, spine AD-54). Ingestion continues while the partition stays unlocked (D93).

**Unlock window.** At unlock the member chooses a duration up to a maximum (see D36; values in PRD FR-12). The window starts at unlock and ends at the unlock time plus that duration, whatever the web sessions do; a web session that outlives it keeps working without partition access until the member unlocks again; extending sets a new end no later than now plus the maximum and needs the passphrase (D113). The web session and the unlock window are distinct: logging out ends the web session, not the window. Locking on demand and the kill switch end the window immediately; when it ends, the member's keys are dropped from memory. Choosing, extending or ending a window is audited, and the member sees the remaining time. Each member is unlocked independently. Cost, stated plainly: a member's keys stay in memory without an active web session for up to the window maximum, which aggravates R1.

An instance restart locks every member. There is no auto-unlock: member and household keys are never on disk in usable form. The cost is that unattended restarts leave personal and household partitions locked until a member unlocks; the design pays that cost deliberately, with background tasks waiting (section 7). The home partition is the exception: its keys derive from the instance key, so it opens at start and the house runs with every member locked (section 2, see D53).

## 5. The household key

- The household partition uses a household key HK with a **version**. HK is created at the first member's enrollment and wrapped for that member (PRD FR-7). Every adult member holds a wrapper of HK sealed to their own public key (HPKE), whose private half is wrapped by their DEK. Any unlocked adult opens the shared partition, and any unlocked adult can create or replace the wrapper of a locked adult without that adult's secrets, after verifying the MAC of that adult's public key (spine AD-36, D74, section 2). If no adult is unlocked, nothing about the household partition changes until one is. Children members read and write the household partition through the Core's policy under an adult-granted capability, not by holding HK, unless the household chooses otherwise (open, to decide with the first real use).
- **Household sealed inbox.** Sensitive household history (household presence, door, window and alarm events), always, and other household-partition data produced while every adult is locked is sealed to the household inbox public key (section 2). At the next adult unlock, after migrations, the Core ingests the rows in sealed order as `Event` writes, not undoable, then deletes them, and keeps ingesting while an adult is unlocked; a row is stored `external` unless it carries a household-key MAC that ingestion accepts (section 2), and every ingestion is journaled and reviewable (D93, spine AD-37). The household sealed inbox ships with the home milestone (D107).
- **Adding an adult** is authorized from the host CLI by an existing adult with their passphrase (see D34, PRD FR-8, section 3). Every other adult is notified, in the primary channel and on the out-of-browser notification channel, and a delay starts; during the delay any other adult can veto with a passkey step-up, or at the host CLI with `vilicus member veto` and their own passphrase, which revokes the new member. When no other adult exists, nobody can veto: the authorizing adult is notified at each step and can cancel during the delay (D88). When the delay ends without a veto, the next time an existing adult unlocks, the Core verifies the new member's enrollment tag, writes the permanent MAC of the public key and wraps HK to it (D74, section 2); the new member is notified. The instance admin cannot do any step and cannot see HK. This replaces the signed confirmation from every other adult of revision 1, which needed the native app.
- **Removing a member** follows the same pattern (see D34): the passphrase of an adult other than the one removed, a delay with notification to every adult, and a veto by any adult other than the initiator and the removed member. It comes after V0.1 (PRD FR-9).
- **Suspending a member** is in V0.1: `vilicus member suspend` revokes the member's sessions, devices, channel bindings and unlock window at once and drops their keys from memory, but changes no key: data and wrappers are kept and HK is not rotated (D77). Honest consequence: a suspended adult's HK wrapper still opens the household partition from a copy of `wrappers.db` together with their passphrase or recovery secret; only removal with rotation ends that. A member may also suspend their own account with `vilicus member suspend` and their own passphrase (D101). **Lifting a suspension** is an H action approved in the app by another adult with a step-up bound to that action (D71), followed by the delay and veto of adding an adult, with every adult notified; it needs no passphrase and changes no key (D87). Before the native app the step-up runs in a browser served by the Gateway, so this path carries the residual risk R40 in `architecture.md`.
- **Rotation on departure.** When a member leaves: a new HK version n+1 is generated; wrappers for the departed member are deleted; the new key is wrapped for the remaining adults. The household inbox key pair is versioned with HK and rotates with it; the previous private key is kept until the rows sealed to it are ingested. Because the permanent MAC of each public key is keyed by HK and its version (section 2, D119), the rotation first verifies every permanent MAC under HK n and rewrites it under HK n+1, and only then wraps HK n+1; a public key whose MAC fails is refused and alerted, not wrapped. Pending enrollments wrapped under HK n are refused as stale, not as tampering, and those members are added again. Data is re-encrypted in the background soon after the rotation (deferred, not instantaneous) with visible progress (the household sees how much remains), and the old version remains available to remaining adults until every file is rekeyed, then is destroyed. Per PRD FR-9, the rotation runs while the initiator is unlocked, and the guarantee "not decryptable with the former keys" holds per file once that file is rekeyed. Backups taken before the rotation are treated as exposed to the departed member. What rotation protects: data written after the departure, and the old data once rekeyed against any later leak of the departed member's wrapper. What it does not: anything the departed member already read, copied or exported.
- **Threshold recovery.** A household recovery key is split among adults with Shamir secret sharing (2 adults of N required) and wraps HK as an additional wrapper. It is used when no single adult can unwrap HK any more (for example every adult lost their DEK access but at least two kept their share) and it prevents any single adult, or the admin, from resetting household access alone. Each share is printed and stored by its adult, separate from that adult's personal recovery secret. For a two-adult household, N equals 2 and k equals 2, so the benefit over individual wrappers is small and the cost is real; the feature is optional there. Whether to ship it in v1 is **open** (D7).

## 6. Recovery

- Every member has a printed **recovery secret** from enrollment. It is the only factor of last resort. No admin function can reset it.
- **Start on the host** (see D39, PRD FR-14). The member types the recovery secret at the host CLI prompt of `vilicus member recover`, never through a channel that would pass it to the AI. No web route can start a recovery. A member without host access depends on the operator to start it (PRD section 8.2).
- **Waiting period and alerts.** Recovery starts a waiting period (value in PRD FR-14). The member and every other adult receive a content-free alert on the out-of-browser notification channel (see D47) and in the primary channel; the host journal records it. The member can cancel from any authenticated session, and existing sessions and devices keep working meanwhile.
- **Acknowledgement, capped.** The waiting period runs its base length and is extended until the member acknowledges the alert, up to a cap (values in PRD FR-14), and runs to its cap while an adult has had no working out-of-browser destination for 24 hours (D105), and every adult receives a reminder each day. Another adult's acknowledgement never shortens it. The acknowledgement is a one-time token carried by each alert (128 random bits, single use, valid for that alert only): the member opens it on a device they control and redeems it at the Core, whose acknowledgement endpoint accepts nothing else and is rate limited (D75). Without a redeemed token, the waiting period runs to its cap. What it gives, stated plainly: protection against an attacker who cannot read the member's push channel. It does not hold against a compromised member device or a compromised Gateway, which can redeem a token it sees or drop the redemption; against those, the cap and the daily reminders to every adult remain. This replaces the per-device acknowledgement of revision 1: the alert path does not depend on an open browser, so dropping web notifications alone does not silence it.
- **Finish in the browser.** After the period, if not canceled, the CLI prints an enrollment token. In the browser, with that token and the recovery secret, the member sets a new passphrase, enrolls a passkey and receives a new recovery secret. The old wrappers are deleted and the old secret no longer works. Completing a recovery rotates the member DEK (section 8): wrappers of the old DEK left in older backups, under the old passphrase or the old recovery secret, open nothing written after the recovery (D106). It also ends the member's unlock window and revokes every other passkey, paired device, web session and channel binding of that member, except those the member explicitly keeps on the completion screen; the out-of-browser alert lists what was revoked.
- Recovery of the household partition (threshold) follows the same waiting period and alerts all adults.
- If a member loses every authenticator, the passphrase and the recovery secret, the personal partition is **permanently lost**. The Core cannot help, by design. Data of the household partition survives if another adult exists.
- A recovery attempt with a wrong secret is rate limited and audited. TOTP and passkey fallback are never valid for recovery.

## 7. Background tasks and delegation

Background tasks (mail polling, calendar sync, shopping list preparation, and scheduled tasks such as a morning briefing or reminders) need a database open while no human is present. Options, in order of preference:

1. **Unlocked members only.** The task runs while its member's partition is unlocked, which now includes the unlock window after the web session ends (see D36, section 4). Default for everything.
2. **Sealed inbox (for ingest tasks and history).** A task that only needs to *write* into a locked partition asks the Core to seal a row into that partition's sealed inbox (section 2, spine AD-37); it never holds a database key, and the next unlock ingests the inbox. This keeps the database closed. It applies to personal partitions and, through the household sealed inbox, to the household partition.
3. **Home rules need no member key.** Home rules are deterministic code in the Core, running on home partition data under keys derived from the instance key, with every member locked, without a model and without a member key (see D57). History they produce for a locked partition goes through its sealed inbox.
4. **Delegation sub-key**, only when a scheduled task must also *read* a personal or household partition while its member is locked. Not in V0.1, available after V0.1 (see D62, spine AD-43, PRD FR-88). A member opts in per scheduled task: creating a delegation is an H action with a step-up, and a sub-key on a household-partition module also follows the delay and adult veto of rights changes. The sub-key is a random key that encrypts a copy of the database key of **one module file in one partition** (for example the meals file of the household partition for a shopping task). It is sealed by the instance key in `core.db` so the task can run while the member is locked, bound to the scheduled tasks that use it, and listed in the member's settings. The Core keeps a run descriptor per delegated task in `core.db`: the fire time and staleness limit in clear, and the structured definition sealed under the sub-key, so a run reads its own definition while its owner is locked; schedule times are therefore visible to the instance key holder (D111, R34). A sub-key never opens a plugin's state store: a member-owned plugin runs only while its owner is unlocked (D111). Any data type may be delegated. A run that holds the sub-key reads the delegated module file and writes only through the owner's sealed inbox, never into the file itself (D94). It never grants access to HK itself, to the member DEK or to other modules or partitions, and it **dies with revocation, the member's removal or the module's deactivation**: each of these destroys the sub-key and marks the module file for re-keying at the owner's next unlock, when the partition key is at hand; until that re-key, the copy of the sub-key in older backups still opens the file (D94, section 8).
5. **Otherwise wait.** If the partition is locked and the task has no other path (no sub-key), it waits for the member's next unlock within its staleness limit (value in PRD FR-87). A late task runs at most once within that limit; past it, the run is canceled and recorded. The member gets a content-free notification in the app and the web client (PRD FR-88).

A TPM with PCR binding is recommended, and required, with unified kernel images, on a host that runs adapters driving physical security devices (D78, D108), because whoever holds the instance key (a stolen disk with the TPM unsealed, or a disk without a TPM, or root on the host) can read the home partition (see D53) and, after V0.1, any delegated module file. Delegated data is readable by root on the host, by the instance admin with a backup and its backup secret, or by the thief of a disk on a host without a TPM, for as long as the sub-key exists; the household accepts this internal risk (D62, PRD section 8.2). It trades some at-rest protection for availability. The default is no delegation; when delegations exist, the member's settings list them and the audit log records creation, use and revocation.

## 8. Rotation

| Key | Trigger | Procedure |
|-----|---------|-----------|
| Passphrase | User request, suspected exposure | New Argon2id wrapper, old one deleted; older backups keep the old wrapper, so a change declared as a suspected exposure offers a DEK rotation (D106) |
| Passkey | New authenticator, lost authenticator, instance rename | V0.1: register or remove the credential with a step-up, no wrapper involved; after a rename or a restore, or when every passkey is lost, re-enroll with an enrollment token from `vilicus member reenroll` and the member's own passphrase (see D51, D77, section 3). With PRF unlock: add wrapper (unlocked session), delete wrapper of a lost one |
| Recovery secret | After use, or on request | Generate new, show once, delete old wrapper |
| Member DEK | Completed recovery; suspected key exposure | Generate new DEK, rekey every member database file, re-wrap the member key pair and inbox key pair, and re-issue or revoke every delegation of that member when delegations exist; heavy, offered as a maintenance task |
| Household key | Member departure; suspected exposure | Section 5 |
| Inbox key pair | Rotation of its partition root | New version with the root; the previous private key is kept until the rows sealed to it are ingested, then destroyed (spine AD-37) |
| Database keys | Part of DEK or HK rotation, or per-file `generation` bump | Rekey the file, bump `generation` in the derivation, and write the new epoch atomically to the file's `<file>.epoch` sidecar and `_meta` table (section 2) |
| Delegation sub-key | Revocation, member removal, module deactivation | Destroy the sub-key and mark the module file for re-keying (per-file `generation` bump) at the owner's next unlock, after which the delegated database key is useless; until then a copy of the sub-key in an older backup still opens the file; scheduled tasks bound to it wait for unlocks again (section 7, D62, D94; after V0.1) |
| Instance key | Admin request, TPM change | Re-encrypt `core.db`, rekey the home partition files (their root derives from the instance key) and the state stores of household-owned plugins (D95), re-seal delegation sub-keys when they exist. How inbox rows authenticated under the previous key are verified is **open** (section 12) |
| Backup secret | Admin request, suspected exposure | The Core generates a new secret and shows it once, derives the new backup key pair, stores the new public key in `core.db` and discards the private key; the change raises an out-of-browser alert to every adult and follows the delay and veto of rights changes; later backups are sealed to it, earlier backups stay sealed to the previous one and need the previous secret (D85, D106) |
| Security adapter secrets | TPM change, restore on another host, vendor credential change, change of the boot signing key | Entered again at the host CLI and sealed to the current TPM under the signed boot policy; never restored from a backup (D78, D108) |
| Audit key | Admin request | New chain segment, old head hash anchored |
| Algorithms | Deprecation of a primitive | Wrapper header carries an algorithm identifier; new wrappers use the new one; old ones are rewritten at the next unlock |

### Migrations and keys

A schema migration runs on a copy of the file, which is swapped in only on success; a failure keeps the previous file, stops only that file's module for that partition and alerts the instance admin (D84). For keys this means:

- Before copying, the Core closes every connection to the file, runs `checkpoint(TRUNCATE)` and checks that no WAL content remains; it then migrates and fsyncs the copy, renames the original to `<file>.pre-<version>` (the cold copy), renames the copy into place and fsyncs the directory (spine AD-23).
- The copy is encrypted under the same database key and `generation` as the file it replaces, so its key epoch sidecar does not change, so a migration never needs a key the partition does not already have open. A member or household file therefore migrates only while its partition is unlocked, and a home partition file at start.
- A migration and a re-key (a `generation` bump from a DEK or HK rotation or a delegation revocation) never run on the same file at once. A re-key also covers, or destroys, any previous file kept after a failed migration and any pre-migration copy of that file; otherwise a revoked delegation sub-key or a departed member's old key would still open it.
- `vilicus upgrade check` reports pending and failed migrations from `core.db` metadata; it needs no member key and opens no partition file.

## 9. Wrapper format and crypto agility

Every wrapper is a versioned structure: format version, algorithm identifiers (KDF, KEK derivation, AEAD, and the HPKE suite for public-key wrappers), KDF parameters, salt or credential reference, nonce or HPKE encapsulated key, ciphertext, tag, creation time and wrapper id. Keys never appear unversioned. The identifiers of version 1 are those of spine AD-18: AES-256-GCM with a random 96-bit nonce, HKDF-SHA-256, Argon2id, and HPKE base mode with DHKEM(X25519, HKDF-SHA256) and AES-256-GCM. The same format, as an HPKE public-key wrapper, seals the instance key and the audit key to the backup public key in a backup (spine AD-31, D85). The version lets the Core refuse to downgrade, rewrite old wrappers during an unlock, and run two algorithms side by side during migration.

This is the entire preparation for future primitive changes at rest. Symmetric 256-bit keys are not the weak point. The asymmetric part at rest is X25519 in the HPKE wrappers of HK and in sealed inbox rows: a future quantum computer able to break X25519 would open them from a copy of `wrappers.db` or of an inbox. The algorithm identifier lets them move to a hybrid KEM once one is available from an audited library; that is a condition, not a current property. Hybrid transport is handled in `architecture.md`, section 15.

## 10. Memory handling

DEKs, HK, the home partition root and derived keys live in locked memory (`mlock`), are zeroized on drop, and are never logged, swapped or dumped; the locked memory is one guarded pool allocated at start, excluded from core dumps and wiped in fork children, and the Core does not start if it cannot lock it; each key operation is followed by a scrub of the stack it used, and AEAD and HKDF objects live for one operation (E16, D131); core dumps are disabled; keys are not passed to modules, plugins or AI processes (modules receive opened handles; the AI receives data only through tools). Process crashes drop keys and lock the instance: a panic outside a module handler and a SIGTERM wipe the pool before the process ends, and the other abort paths leave the keys in memory only until the kernel releases the process's pages at exit, without any dump (E16, D131). Inside HPKE, copies of secrets stay in freed memory whatever the build features: HKDF states, a copy of the DH output, the ephemeral seed, copies of private keys made by serialization and comparison, the clamped scalar of each X25519 operation, and, on x86_64, the GHASH key of each AES-GCM context, which the runtime-detected `polyval` backend never wipes; the Core opens wrapped keys in place into locked memory and scrubs the stack after each HPKE call, and the residue is of the same class as the root attacker below (D120, D131). This reduces exposure but does not stop a root attacker (R1), and the unlock window lengthens the time member keys stay in memory (section 4).

## 11. Loss and failure matrix

| Situation | Outcome |
|-----------|---------|
| Lose one authenticator | Nothing lost; remove it, enroll another |
| Lose all authenticators, remember passphrase | V0.1: `vilicus member reenroll` with the member's own passphrase prints an enrollment token, and the member enrolls a new passkey; no recovery flow and no waiting period (D77, section 3) |
| Lose passphrase, keep an authenticator | V0.1: the passkey does not unwrap data, so this is the recovery flow. With PRF unlock: unlock with the passkey, set a new passphrase |
| Lose all authenticators and passphrase, keep recovery secret | Recovery flow with waiting period, started on the host (section 6) |
| Lose everything for one member | Personal partition lost. Household partition survives if another adult can unwrap HK |
| Lose everything for all adults | Household partition lost unless threshold shares remain |
| Admin account lost | No data impact. The admin recovery code, printed only on the host console at bootstrap and stored only as an Argon2id hash, is redeemed by root with `vilicus admin recover`, which prints a one-time admin enrollment token; it restores system control only, and no web route accepts it (D101) |
| TPM replaced or reset, or unsealing fails after a firmware change | A kernel update does not break unsealing, because the instance key is sealed to the Secure Boot policy only (PCR 7). After an unseal failure, the instance admin restores the instance key from a backup with the backup private key, re-derived from the backup secret, as the recovery runbook states (D96). A pcrlock hook re-seals the instance key before a Secure Boot database or SBAT update (D108). The secrets that open the house are lost after a TPM reset or a change of the boot signing key and are entered again at the host CLI; until then those adapters do not run (D78, D108) |
| Instance key lost (TPM change, restore on a new host without the backup secret) | Metadata in `core.db`, the home partition (devices, rules, modes, current state, adapter secrets) and every delegation sub-key are lost, so each delegation is created again and its scheduled tasks wait for unlocks meanwhile; sealed inbox rows can no longer be authenticated; member data stays unlockable from `wrappers.db`, and each file's key epoch is read from its `<file>.epoch` sidecar, so files re-keyed earlier still open; the admin rebuilds `core.db` and the household reconfigures the home (see D53). A backup restored with its backup secret brings the instance key back (see D52) |
| Backup secret lost | The backup private key cannot be re-derived, so no backup sealed to it can be restored: restoring costs what losing the instance key costs; member data stays unlockable with member secrets. Scheduled backups keep running, but stay unrestorable until a new backup secret is generated (D85, D106) |
| Instance renamed | Every passkey is unusable; each member re-enrolls a passkey with a token from `vilicus member reenroll` and their own passphrase; no data lost while passkeys wrap no data key (see D51, D77) |
| Restore from a backup | Every paired device (household displays included), web session, enrollment token and channel binding is invalidated; members log in with a passkey and re-pair their browsers, so an old backup cannot bring back a revoked device (see D52). A member with no usable passkey gets one through `vilicus member reenroll` with their own passphrase (D77). A restore checks the manifest's MAC and sequence number before writing anything. On another host, the secrets that open the house are entered again at the host CLI (D78, D108) |
| Member suspended | Nothing lost; the member cannot log in or unlock, and keys and data are kept (D77, section 5) |
| Migration fails | The previous file is kept and only that file's module stops for that partition; no key changes (D84, section 8) |
| Attacker obtains the recovery secret | The waiting period and the out-of-browser alerts are the defense; member cancels. Starting recovery also needs host CLI access |
| Attacker obtains the disk | Sees metadata and the home partition if they also have the instance key (for example a disk without a TPM), and, after V0.1, every delegated module file; no other personal or household data. `audit.db` and the inbox files are SQLCipher files, so without the audit key and the instance key they show no metadata (D114). The secrets that open the house stay sealed to the TPM under a signed boot policy, which a live image does not satisfy (D78, D108) |
| Attacker obtains backup | As stolen disk if they also have the backup secret: backups carry the sealed delegation sub-keys, so a backup plus its backup secret exposes delegated data (D62); without the backup secret, no metadata, no home partition, no delegated data and no passphrase wrapper to guess offline, because passphrase wrappers and file names are sealed to the backup public key (D106). A backup never holds the secrets that open the house (D78, D108) |
| Attacker writes the backup public key | Detected: it lives in `core.db`, whose pages are authenticated under the instance key; an attacker who also holds the instance key can redirect later backups to a key they hold, which adds the audit key to what the instance key already gives them; `vilicus backup verify` with the backup secret detects it |
| Departed member keeps an old wrapper copy | Can read data of versions they already could, not newer versions after rotation |
| Weak passphrase | Argon2id raises cost, does not fix a weak secret; passkey with PRF is preferred once available |
