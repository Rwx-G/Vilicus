# Story 3.6: Core journal tables and caller idempotency

As a project maintainer,
I want the Core to own the journal, outbox and consumption tables of every module file and to deduplicate writes by caller call id,
So that every write is undoable, retries never apply twice and outbound effects are never retried blindly.

**Acceptance Criteria:**

**AC1 (AD-26)**
**Given** a newly registered module file
**When** the registry creates it
**Then** it contains the Core tables `_meta`, `_journal`, `_outbox`, `_consumed` and `_dead_letter`
**And** the file has two migration tracks, Core first then module.

**AC2 (AD-26, FR-29)**
**Given** a write through the typed record API
**When** it commits
**Then** the same transaction records in `_journal` the before and after images, the `rev` before and after, the principal and the declared input record ids.

**AC3 (AD-28, AD-26)**
**Given** two calls with the same principal and the same `call_id` against one file
**When** the second arrives
**Then** it is deduplicated and returns the first call's result
**And** a call that writes nothing is not deduplicated.

**AC4 (AD-28, NFR-3)**
**Given** a handler needing an outbound effect
**When** it runs
**Then** it writes an effect intent row with a business idempotency key to `_outbox`, the outcome is recorded after commit as `done`, `failed` or `unknown`
**And** an `unknown` outcome is reported to the member and never retried blindly; only the Core retries, with the same key.

**AC5 (FR-24, AD-26)**
**Given** a consumer's effect on an event
**When** it commits
**Then** the event id is recorded in `_consumed` in the same transaction.

**AC6 (FR-29, D113, E17, D132)**
**Given** journal entries in a personal or household partition older than 30 days
**When** retention runs
**Then** they are deleted under `secure_delete` = ON in one `DELETE FROM _journal WHERE created_at < cutoff`, followed in the same maintenance step by a TRUNCATE checkpoint through `sqlite3_wal_checkpoint_v2` (Story 3.1 AC10), retried until it reports not busy and the WAL is empty; E17 took no fallback (D132)
**And** a file inspection test, reusing the procedure of Story 1.11 (`spikes/secure-delete-wal/src/pages.rs` decrypts every page of the file and every frame present in the WAL, `src/scan.rs` searches 16- and 8-byte windows), finds no run of 8 bytes or more of any deleted before-image, after-image or `call_id` in the file, the WAL or the shm, with the live rows found as the control.

**AC7 (D132, E17)**
**Given** a record shredded by destroying its wrapped record key
**When** the deletion completes
**Then** the wrapped key row is deleted under `secure_delete` = ON and followed by a TRUNCATE checkpoint, and no run of 8 bytes or more of the destroyed wrapped key remains in the file or the WAL, `_journal` included, while the record's ciphertext and the kept keys remain
**And** the test includes the negative control of Story 1.11 (`journaled_shredding_keeps_keys_until_journal_rows_go_*`): a journaled delete of the key row leaves the key readable in `_journal` until those journal rows go.

**AC8 (E17, D132)**
**Given** a reader holding an old snapshot on the file
**When** the retention purge's TRUNCATE checkpoint runs
**Then** the checkpoint reports busy and is retried, and the WAL is empty and no deleted value remains once the reader ends (gate E17-2, not exercised by the spike).

**Decision tasks:**
- [x] Decide how a wrapped record key stays out of `_journal` (D132, Story 1.11 settled task 4). Recommended: never journal it, the typed record API excluding the wrapped record key from before- and after-images, because it keeps the key out of the journal entirely. Gives up: an undo of a shredding cannot restore the key, which is the intent of shredding; the alternative, deleting the journal rows that hold the key in the same step, keeps the undo image but adds a second delete to every shredding. Settled as recommended: never journaled, the key kept in the Core table `_record_keys`, which no image holds and module SQL cannot read (Implementation Notes, Decisions; drafted D148).

**Decisions and why** (drafted decision and spine texts under Open points)
- *The decision task, wrapped record keys* (D132, Story 1.11 settled task 4): never journaled, as recommended. A wrapped record key lives in the Core table `_record_keys` of the record's file (`doc/architecture.md` section 5.1: "stored wrapped in the same database"), never in a module table, and a journal image holds exactly the module table's envelope and declared fields, so no image can hold a key. A key in a module column would be readable, and copyable, by module SQL, which defeats shredding however the journal treats it; a Core table no module SQL reads closes both. Gives up: an undo cannot restore a shredded record's key, which is the intent; and a table AD-26 does not list.
- *The Core migration track*: embedded in `vilicus-storage`, where the Core tables and their policy are, run by the same runner as a module's migrations under a policy of its own, `Policy::CoreMigration`, which changes Core tables only, so module SQL can still never touch them and Core SQL never touches a module's table. `_meta` is written by `create` before either track, because it holds both tracks' versions and the epoch every open checks; "no row means 0" (D144) still holds for both tracks. What it gives up: `_meta` is outside the Core track, so a change to `_meta` itself would be a change to `create` and a Core migration together.
- *The deduplication key*: AD-26 names "the pair (principal, `call_id`)"; `Principal` is the closed set of kinds (AD-8), and two members' calls are both `Member`. The key is the principal, the `source` the call's records carry (which names the member of a `Member` or `Cli` call, the task of an `AiTask` call, the rule of a `Rule` call, closed by `check_call`), and the `call_id`, so another member's or another task's call with the same id is another call, and a forged id cannot read a stranger's result. Gives up: nothing AD-28 needs; a member's `Member` and `Cli` calls with one id are two calls.
- *What a call wrote*: a journal row or an effect intent, read in the call's transaction before the module's code runs; a call that only requested an effect is deduplicated too, since repeating it would request the effect again. A call that wrote nothing left no row and runs again (AD-26). A rolled-back call left nothing, so its retry runs.
- *The first call's result*: its changes (table, id, revisions, inputs) read back from the journal, and its effect intents from the outbox, equal to what the first call returned. The module's own return value is not stored: it is a Rust value of any type, and what a tool returns to its caller is the pipeline's (Epic 10), built from the changes.
- *Journaled inputs*: each input's id with the labels, author and data types the Core read for it, and whether the call carried it (implicit) or the module named it. An implicit input is a snapshot no later read can give back (D147), and an undo recomputes from the journaled inputs (Story 10.7 AC4); free text is not journaled.
- *Images and their encoding*: the stored row read in the transaction, each column with its name, so an image survives a later migration that adds a field. The encoding is a plain length-prefixed sequence (`journal.rs`), not the canonical CBOR of D130: the profile refuses text that is not NFC, which free text may hold, and `dcbor` would normalize it, so an image would not be the stored row.
- *Effect intents*: unique in their file by business idempotency key, so "a retry or a duplicate proposal does nothing twice" (`doc/architecture.md` section 9.2, step 7) holds across calls: a second request of a key returns the first intent and writes nothing. An outcome is recorded once per attempt, from `pending` only; only `failed` goes back to `pending`, keeping id and key, so the Core is the only one to retry and always with the same key; `unknown` is reported (`UnknownEffect` names the member who made or approved the call, or the one it acts for) and refused by the retry.
- *Consumed events*: the consumer's name comes with the delivery (`EventDelivery::consumer`), given by the pipeline, since consumers are declared with events in Story 3.8. A delivery is only an `Event` call's, and every `Event` call has one (AD-27). The `_consumed` check runs in the transaction, before the module's code, so a second delivery runs nothing, the guarantee AD-10 asks of consumers.
- *Private Core tables*: module SQL can read neither the journal (earlier states of every record, deleted ones included), nor the outbox (effect payloads), nor the record keys; `_meta` and `_vocabulary` stay readable as before.
- *The checkpoint retry*: bounded, `CHECKPOINT_ATTEMPTS` (10) attempts each waiting up to the busy timeout (100 ms) with a 20 ms pause, as Story 3.1 built it. A reader that outlasts them makes the purge, or the shredding, fail with `CheckpointIncomplete` rather than claim the WAL empty; the rows are deleted, and the next purge or checkpoint completes it. An unbounded retry would hold the file's writer thread behind a reader.
- *Where retention lives*: the cutoff by partition kind is the Core's (`journal_retention`, `purge_expired_journal`); the storage layer deletes before the cutoff it is given.

**Deviations**
- *AC1, "it contains the Core tables `_meta`, `_journal`, `_outbox`, `_consumed` and `_dead_letter`"*: and `_vocabulary` (AD-26, D146) and `_record_keys` (the decision task). `_meta` is written by `create` before the two tracks, not by the Core track (Decisions).
- *AC3, "returns the first call's result"*: the first call's changes and effect intents, not the module's own return value (Decisions). *"the same principal"*: the same principal and `source` (Decisions).
- *AC4, "After commit the Core performs the plugin call"*: no plugin protocol exists before Epic 10, so the Core does not yet call a plugin; the file's side is built and tested: the intent in the call's transaction, `effects_to_perform`, the outcome recorded after the commit, the retry of a `failed` intent only. *"reported to the member"*: `record_effect_outcome` returns the report (`UnknownEffect`, the intent and the member); sending it is the alert path's (Epics 8 and 10).
- *AC6, "retried until it reports not busy and the WAL is empty"*: up to `CHECKPOINT_ATTEMPTS` times, then a typed failure (Decisions). *"reusing the procedure of Story 1.11"*: ported into `vilicus-core`'s tests (`inspect.rs`), since a product crate never depends on a spike, with `aws-lc-rs` for AES-256-CBC where the spike called OpenSSL through `openssl-sys`. *"no run of 8 bytes or more of any deleted before-image, after-image"*: an image is a stored row, and its column names, labels, `source` and times are shared with every live image, so the needles are what is the deleted row's own: each before and after image's free-text value (random text, 48 or 3000 characters, the long ones in overflow pages) and each call id; record ids are not needles, since the tests' ids share all but a counter.
- *AC7, "the record's ciphertext"*: the record cipher is not built (Epic 4, the mail and memory modules); a random free-text field stands for the ciphertext and 48 random bytes for the wrapped key, as in the spike. The negative control's journal rows, which image the key row as the rejected alternative would, are planted with SQL outside the storage layer, since no product path can journal a key.
